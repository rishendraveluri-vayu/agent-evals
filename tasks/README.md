# Task set (SP4, [Rishi designs]). One folder per task: tasks/<id>/task.json, see docs/api-contract.md.

Engine tests: folders named `engine-*` are synthetic tasks for the run engine (scripts/sp3_kill_test.py) with fake models. They are not part of the task set.

For a conversation task, the simulated client's hidden facts must agree with the task's client file, which the agent reads through its tools; a hidden fact that contradicts the file makes the client argue with its own records (seen 4 Nov). The API shows the simulator the profile, the debts and the latest month's transactions (D30).

Required tools: list them once in `task.json` as `"required_tools": ["calculate_emi"]` when the rule is only "these tools must have been called"; the runner records it in every trial's `checks.json`, and a `{"type": "required_tools"}` grader makes it count towards the pass. Use a `tool_called` grader instead when the arguments or the number of calls matter. `docs/proposals/grader-format.md` has both.

Arithmetic tools: since 5 Nov the toolset (`finance/v2`, D54) also has `add`, `subtract`, `multiply`, `divide`, `percent_of`, `percent_change` and `round`, so every figure in an answer can come from a tool. A figure one of them returned counts as supported in the provenance check only when the numbers it was given are themselves supported (D56), so a sum the agent states (₹14,120 + ₹9,000 = ₹23,120) passes only when it came from `add` and both inputs came from a tool, the client's file or the client's message. `required_tools` and `tool_called` may name them. A task's expected numbers are unchanged: the arithmetic tools compute what the agent would otherwise have written itself.

Unit facts and reference rates (D58, toolset `finance/v3`): an arithmetic input of 7, 12, 28 to 31, 52, 100, 365, 366, 1,00,000 or 1,00,00,000 needs no source (so `multiply([emi, 12])` counts), and `reference_rates` returns documented, dated market rates (FD, savings, PPF, CPI, repo, long-run equity; approved by Rishi, 5 Nov) that count as sources, so a task may expect an agent to take a rate it volunteers from that tool; a rate the task itself states still belongs in the message or the client file.

The task set (D53, 5 Nov) is the 21 `draft-*` folders, every `task.json` at version 2. The ids keep their `draft-` prefix so they stay linked to the trials recorded under them; the tasks are no longer drafts. Split A: 11 `discovery` and 10 `held_out` (the headline compares on held-out tasks only, and prompt v2 is written from discovery traces only; `docs/experiment.md`). Every required grader carries a `severity` (critical, major or minor); a judge grader carries the most severe of its criteria's, since the format has one severity per grader. Changing a split, a hidden fact or a client file changes the task's core: give it a new `version`, and its recorded trials keep the old one.

`scripts/make_draft_tasks.py` writes them and computes every expected number with the finance server's calculators: run it from `services/finance-mcp` (`uv run python ../../scripts/make_draft_tasks.py`); it rewrites every task's `task.json` and client file, and its `HELD_OUT` and `SEVERITY` tables are where the split and the severities live. A `unit_test` grader's file (`grader.py`) sits next to `task.json` and is hand-written, not generated; `graders/tests/test_task_graders.py` tests each one on hand-made trials and checks the set against D53. Most client-file tasks use Meera's file (the finance server's example client); `draft-convo-phone-loan` has its own synthetic client, Rohan. The reasoning for the set, its severities and its split is `docs/proposals/tasks-review.md`.

Verify, don't trace (D61): a rupee figure the agent works out in prose is verified when the checker can recompute it in one step from figures the answer shows and sources it had (₹14,120 + ₹9,000 = ₹23,120; "₹12 lakh in a year" is ₹1 lakh a month), and counted as `derived_in_prose`, a measure beside the pass rate; a wrong sum is unsupported, so `provenance` at 0 still fails it.
