## Key question 1: How do the major agentic benchmarks specify and grade tasks, and which grader type does each use?

### Takeaway
Nearly every widely used agent benchmark grades the *final state* or a *short verifiable answer* with deterministic code (unit tests, DB/state diffs, (quasi-)exact match) and uses an LLM judge only as a fallback for free-text sub-checks; the two benchmark families that lean on a model judge (BrowseComp, GDPval, parts of TheAgentCompany and tau2-bench 2.0) constrain it to short-answer equivalence or pairwise preference. Trial-level outcomes are binary almost everywhere; partial credit appears only where tasks are decomposed into checkpoints (TheAgentCompany) or sub-tests (SkillsBench/Terminal-Bench pytest).

**SWE-bench family**
- SWE-bench Verified is "a subset of 500 samples from the SWE-bench test set, which have been human-validated for quality"; evaluation is "by unit test verification, using post-PR behavior as the reference solution" — [HF dataset card](https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified). Reviewers checked for clear problem statements, correct test patches, and solvability with the given information — [swebench.com/verified](https://www.swebench.com/verified).
- SWE-bench Lite is "~300 tasks" — secondary summary, [systems-analysis.ru](https://systems-analysis.ru/eng/SWE-bench_(benchmark)) (not verified against swebench.com).
- SWE-Bench Pro: each problem gets a human-written problem statement plus a list of requirements and, when relevant, an interface specification; the requirements "describe expected behavior without prescribing an implementation." Annotators verify fail2pass tests for relevance and for being "too broad"; environments are validated by running gold tests several times and dropping problems that fail consistency. Trivial edits (1–10 lines) are excluded; each repo contributes 50–100 instances. Reference solutions average 107.4 lines changed across 4.1 files, vs 161 of 500 Verified problems needing only 1–2 line changes — [arXiv 2509.16941v2](https://arxiv.org/html/2509.16941v2).
- SWE-Bench Pro public-set Pass@1 (Sep 2025): Claude Sonnet 4.5 43.6%, Claude Sonnet 4 42.7%, GPT-5 (high) 41.8%; commercial set: Claude Opus 4.1 17.8% — [arXiv 2509.16941v2](https://arxiv.org/html/2509.16941v2).

**tau-bench / tau2-bench / tau3-bench**
- tau-bench reward r = r_action x r_output, each 0/1: r_action checks that the final database matches the unique ground-truth DB; r_output checks that agent messages contain required information such as specific price strings. The paper notes r = 1 is "necessary but not sufficient" (an agent could issue a return without user confirmation and still pass) — [arXiv 2406.12045](https://arxiv.org/html/2406.12045).
- tau2-bench grading uses up to five criteria per task: database checks, status assertions on world state, NL assertions on interaction history, communicate-info checks, action matching; telecom uses only assertion functions — [arXiv 2506.07982v1](https://arxiv.org/html/2506.07982v1).
- tau2-bench release 2.0.0 (19 Oct 2026, "Multilingual and Voice"): "Scores are not comparable with 1.x"; six language packs; new tau-Entity intake domain of 200 outbound-call tasks; communication checks became LLM-judged (NL-assertion judge gpt-5.4-mini-2026-03-17); user simulator moved from gpt-4.1 to gpt-5.5 at low reasoning effort; `tau2 judges` is diagnostic only, not part of reward — [tau2-bench RELEASE_NOTES.md](https://raw.githubusercontent.com/sierra-research/tau2-bench/main/RELEASE_NOTES.md).
- tau3-bench (2026) ships inside the tau2-bench repo, adds a banking knowledge-retrieval domain and voice evaluation; a Harbor listing describes 375 tasks across airline, retail, telecom, banking knowledge — [Sierra](https://sierra.ai/resources/research/tau-3-bench-knowledge), [Sierra voice](https://sierra.ai/resources/research/tau-3-bench), [Harbor hub](https://hub.harborframework.com/datasets/sierra-research/tau3-bench) (task count is from the Harbor listing, not verified against Sierra).

**GAIA**
- Answers are "a number, a short string, or a comma-separated list"; scoring is quasi-exact match with type-dependent normalisation (numbers without commas/units unless specified, strings without articles/abbreviations). Levels: L1 up to ~5 steps and at most one tool (146 q), L2 5–10 steps (245 q), L3 arbitrarily long (75 q). 166 released with annotations; 300 answers held back for the leaderboard. Humans 92% vs GPT-4 with plugins 15% (Nov 2023) — [arXiv 2311.12983](https://arxiv.org/html/2311.12983).

**WebArena / WebArena-Verified**
- WebArena uses three rule-based evaluators: string match (exact, must-include, fuzzy via LLM), URL match of final URL, and program_html which extracts page elements by locator and compares to ground truth — [WebChoreArena](https://arxiv.org/pdf/2506.01952) (describes the WebArena protocol it inherits).
- WebArena-Verified (ServiceNow; PyPI Jan 2026, Docker Feb 2026) re-audited "every task, reference answer, and evaluator ... to eliminate brittle string matching and ambiguous success"; statuses are success / failure / partial_match / error and the overall score is 1.0 only if all evaluators succeed; 812 tasks plus a 258-task Hard subset — [project site](https://servicenow.github.io/webarena-verified), [results](https://servicenow.github.io/webarena-verified/evaluation/evaluation_results), [GitHub](https://github.com/ServiceNow/webarena-verified), task counts via [BenchLM](https://benchlm.ai/benchmarks/webarena-verified) (secondary).

**OSWorld**
- 369 tasks; each with "a custom execution-based evaluation script"; humans >72.36% vs best model 12.24% at release (Apr 2024) — [arXiv 2404.07972](https://arxiv.org/abs/2404.07972).
- OSWorld-Verified (Jul 2025): 8 Google Drive tasks may be excluded (361-task run accepted) — secondary, [BenchLM](https://benchlm.ai/md/benchmarks/osworld-verified.md).

**TheAgentCompany**
- 175 tasks (69 SWE, 28 PM, 14 DS, 15 Admin, 29 HR, 12 Finance). Each task is split into weighted checkpoints; most evaluators are deterministic Python checks of environment state or trajectories. 51 tasks (29%) fall back to an LLM (Claude-3-5-Sonnet-20241022) after deterministic keyword matching fails; LLM evaluators are "mainly used in well-defined tasks that require simple information extraction and classification." Partial score S_partial = 0.5 x (checkpoints passed / total) + 0.5 x S_full. Top result at paper time: Gemini 2.5 Pro 30.3% full completion, 39.3% partial — [arXiv 2412.14161](https://arxiv.org/html/2412.14161).

**Terminal-Bench 2.0**
- 89 tasks; each has "a unique environment, human-written solution, and comprehensive tests"; tests check the final container state rather than specific commands. Grading is pass/fail per trial. Top (Jan 2026): Codex CLI + GPT-5.2 62.9% ± 3.0; Terminus 2 + Claude Opus 4.5 57.8% ± 2.5; Terminus 2 + Gemini 3 Pro 56.9% ± 2.5 — [arXiv 2601.11868](https://arxiv.org/html/2601.11868).

**BrowseComp**
- 1,266 questions; model-based grader checks semantic equivalence to a single short reference using the Humanity's Last Exam grading prompt. GPT-4o 0.6%, GPT-4o with browsing 1.9%, o1 9.9%, Deep Research 51.5% (Apr 2025) — [arXiv 2504.12516v1](https://arxiv.org/html/2504.12516v1).

**MLE-bench**
- Headline metric: share of attempts earning any Kaggle medal (bronze+) against the private leaderboard; best at release (Oct 2024) o1-preview + AIDE medals in 16.9% of competitions. Dolos plagiarism detector run on all medal-winning submissions found no plagiarism; a GPT-4o rule-violation detector scans logs — [arXiv 2410.07095](https://arxiv.org/pdf/2410.07095), [repo](https://github.com/openai/mle-bench).

**GDPval (judge-graded)**
- 1,320 tasks across 44 occupations (220-task public gold set); tasks authored by professionals with >= 4 years experience (average 14); expert graders see unlabelled deliverables and rank them with rubrics; each pairwise comparison averages > 1 hour; an experimental automated grader agrees with experts 66% vs 71% inter-human agreement. Original paper: Claude Opus 4.1 beat or tied experts on 47.6% of tasks, GPT-5 39.0% — [arXiv 2510.04374](https://arxiv.org/html/2510.04374v1), [OpenAI PDF](https://cdn.openai.com/pdf/d5eb7428-c4e9-4a33-bd86-86dd4bcf12ce/GDPval.pdf).

**2025–2026 successors (released or updated)**
- Terminal-Bench 2.1 (6 May 2026): revision fixing 28 of 89 tasks, task count unchanged — [tbench.ai](https://www.tbench.ai/news/terminal-bench-2-1). Terminal-Bench 3.0: contribution call targeted 100 tasks at <= 30% solve rate for best models; third-party pages show a 74-task v0.1 with top score ~42.7–43.5% — [tbench.ai TB3 call](https://tbench.ai/news/tb3-contribution-call), [Snorkel](https://snorkel.ai/leaderboard/terminal-bench-3-0/), [Turing blog, 3 Aug 2026](https://www.turing.com/blog/introducing-terminal-bench-3-0) (counts not confirmed on tbench.ai).
- SWE-Bench Pro Verified (arXiv Sep 2026, v3 9 Oct 2026): adds anti-reward-hacking safeguards against "leakage of gold solutions or hidden evaluation information" and minimal task refinement; says some models "perform substantially worse than previously evaluated" — [arXiv 2609.08149](https://arxiv.org/abs/2609.08149).
- OSWorld 2.x: Epoch reviewed "OSWorld 2.1" (108 tasks) on 28 Sep 2026 — [Epoch review](https://epoch.ai/benchmarks/osworld-2-1/review); the dataset lives at [xlangai/osworld_v2_tasks](https://huggingface.co/datasets/xlangai/osworld_v2_tasks/discussions/2) with ongoing per-task fix PRs.
- Harness-Bench (May 2026): built to measure harness effects across model backends on shared tasks; concludes capability should be reported at the model–harness pairing level — [arXiv 2605.27922](https://arxiv.org/pdf/2605.27922) (task count differs between versions: 300 tasks/1,408 scored modules vs 106 tasks/5,194 trajectories; unresolved).
- HAL (Oct 2025, ICLR 2026): standardized harness across 9 benchmarks, 9 models, 21,730 rollouts, ~$40k — [arXiv 2510.11977](https://arxiv.org/abs/2510.11977).

### Inferences
- The field's default for an agent task is: isolated environment + deterministic end-state check + binary trial outcome. Judges are used to *compare* a short answer to a reference or to adjudicate NL sub-assertions, not to decide success from scratch. This matches the platform plan (exact match, unit tests, state checks, LLM judge as a fourth grader).
- Partial credit via checkpoints (TheAgentCompany) and sub-tests (pytest) is the practical way to get graded signal from a 20-task set without a judge; several sources (Anthropic, below) recommend it for multi-component tasks.
- tau2-bench 2.0 moving communication checks to an LLM judge while keeping it out of reward for `tau2 judges` shows the current compromise: judges for diagnosis, deterministic checks for the score.

### Gaps
- AgentBench per-environment metrics (F1 for KG, "game progress" for lateral-thinking puzzles) come from secondary summaries that conflict; the paper itself was not opened beyond the abstract.
- SWE-bench Lite's exact count and construction (300 instances filtered for self-contained fixes) was not verified against swebench.com.
- Harness-Bench's final task count is unresolved between versions.
- OSWorld 2.0/2.1's official release notes, task count and grading changes were not found; only Epoch's review and the HF dataset were reachable.

## Key question 2: What went wrong with these benchmarks and how was it found (contamination, broken tasks, grader bugs, saturation, scaffold overfitting, pass@k vs pass^k)?

### Takeaway
Every major agent benchmark that has been independently audited has been found to have 15–60% of tasks or trials affected by grader or specification defects, found mostly by (a) humans reading transcripts of inconsistent or "impossible" successes, (b) trivial/adversarial agents, and (c) continuous CI-style validation; contamination of public task sets is now treated as demonstrated for SWE-bench Verified. pass^k was introduced because per-task consistency, not best-of-k, is what customer-facing deployments need, and pass^k collapses much faster than pass@1 suggests.

### Cited Findings

**SWE-bench Verified: creation (Aug 2024) and retirement (Feb 2026)**
- Creation: 93 Python-experienced software developers screened 1,699 random test-set samples, each labelled three times; criteria were whether the issue is underspecified and whether FAIL_TO_PASS tests filter out valid solutions, each scored 0–3 in severity; 68.3% of samples were filtered out, leaving 500; GPT-4o rose from 16% to 33.2% on the verified set; problem categories were underspecified issue descriptions, overly specific or unrelated unit tests, and unreliable dev-environment setups — [OpenAI, 13 Aug 2024](https://openai.com/index/introducing-swe-bench-verified/) (page blocks fetching; figures confirmed via search snippet and [longtermwiki mirror](https://www.longtermwiki.com/source/e1f512a932def9e2)).
- Retirement: OpenAI's 23 Feb 2026 post "Why we no longer evaluate SWE-bench Verified" says improvements "increasingly reflect how much the model was exposed to the benchmark at training time." Audit: 138 problems that o3 did not consistently solve across 64 runs, each reviewed by at least six experienced engineers; 59.4% had material flaws in test design or problem descriptions; 35.5% were "overly narrow tests" demanding one implementation (denominator unclear); GPT-5.2 solved 31 tasks classified as "nearly impossible," and in one Django task the model's chain of thought contained release-note information about a parameter absent from the problem statement; OpenAI said all frontier models tested "have seen at least some of the problems and solutions during training" and recommended SWE-bench Pro — [OpenAI post](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/) (403 on fetch), details via [The Decoder, 23 Feb 2026](https://the-decoder.com/openai-wants-to-retire-the-ai-coding-benchmark-that-everyone-has-been-competing-on/), [Pebblous summary](https://blog.pebblous.ai/blog/swe-bench-verified-retired/en/), and [Epoch review](https://epoch.ai/benchmarks/swe-bench-verified/review).
- Epoch AI (reviewed 3 Sep 2026) rates SWE-bench Verified "Flawed": OpenAI's audit covered 27.6% of tasks and found 59.4% of those flawed, a floor of 16.4% of all tasks broken; 100% of tasks and solutions are public; "RDI identified a reward hack that achieves a perfect score"; Epoch's earlier 13 Jun 2025 review already flagged scaffold dependence — [Epoch](https://epoch.ai/benchmarks/swe-bench-verified/review).
- Memorisation evidence (Jun 2025, NeurIPS 2025): models identify the buggy file path from the issue text alone with up to 76% accuracy on SWE-bench Verified vs up to 53% on repos outside SWE-bench; verbatim 5-gram reproduction up to 35% on Verified/Full — [The SWE-Bench Illusion, arXiv 2506.12286](https://arxiv.org/abs/2506.12286).
- "Insufficient test cases": ABC cites prior work finding 24% of the top-50 leaderboard positions incorrect because tests miss wrong patches — [ABC, arXiv 2507.02825](https://arxiv.org/html/2507.02825).

**SWE-Bench Pro: recommended Feb 2026, retracted Jul 2026**
- OpenAI's "Separating signal from noise in coding evaluations" (reported 8–10 Jul 2026) audited SWE-Bench Pro with Codex-based investigator agents plus human review (five engineers per flagged task) and found roughly 30% of the 731 public tasks broken (200–249 depending on method). Four defect categories: overly strict tests enforcing implementation details not in the prompt; underspecified prompts missing requirements that hidden tests check; low-coverage tests letting incomplete fixes pass; misleading prompts. Structural cause: tests "written to validate one contributor's PR don't necessarily measure model capability." OpenAI: "we retract our earlier recommendation to adopt SWE-Bench Pro," and called for benchmarks "built by experienced software developers specifically to test model capabilities." A ~70% "noise ceiling" is reported by one outlet but not confirmed — [OpenAI post](https://openai.com/index/separating-signal-from-noise-coding-evaluations/) (403), via [DEV Community](https://dev.to/thegatewayguy/openai-just-found-30-of-swe-bench-pro-is-broken-and-retracted-their-own-recommendation-3nlh) and [Ground Truth, 8 Jul 2026](https://groundtruth.day/news/openai-says-a-top-coding-benchmark-is-saturated.html).
- SWE-Bench Pro Verified (Sep–Oct 2026) names two failure sources: "reward hacking, enabled by leakage of gold solutions or hidden evaluation information" and "misleading problem statements and improperly scoped tests" — [arXiv 2609.08149](https://arxiv.org/abs/2609.08149).

**tau-bench: task fixes and the "do-nothing" agent**
- Original paper: of 40 sampled retail failures, 4 (10%) were typos or ambiguity in the user instruction, which the authors fixed; remaining agent-side failures were ~55% wrong argument/wrong info, 25% rule-following, 19% partial resolution of compound requests — [arXiv 2406.12045](https://arxiv.org/html/2406.12045).
- ABC (Jul 2025): a trivial agent returning empty responses passes 38% of tau-bench airline tasks, more than a GPT-4o agent (35%); airline has 38% intentionally unsolvable tasks and retail 6%; some tasks use verbatim DB text as ground truth so dumping the database passes; listing all possible answers inflates scores ~40% — [arXiv 2507.02825](https://arxiv.org/html/2507.02825).
- tau2-bench re-verified retail/airline tasks "through an iterative review, checking for underspecification, overspecification, and non-unique solutions," without giving a count. User-simulator error rates (Table 2): airline 47% of conversations had a simulator error (13% critical), retail 40% (12%), telecom 16% (6%) — [arXiv 2506.07982v1](https://arxiv.org/html/2506.07982v1).
- tau2-bench 0.1.3 (26 Aug 2025) "removed default natural-language assertion checks that were causing evaluation failures." Release 1.0.1 (Jul 2026) fixed banking_knowledge grading: extra read calls no longer fail tasks (#329), int/float argument normalisation (#397), gold trajectories 077–086 made agent-realisable (#402), sort order aligned to docs (#403), contradictory cash-back rate reconciled (#388); task 074 gold refund corrected from $8.00 to $14.50. Re-grade impact: no passing simulation flipped to failing; pass^1 gains +0 to +9.02 points (gpt-5-5 largest, +35/−0 flips) — [RELEASE_NOTES.md](https://raw.githubusercontent.com/sierra-research/tau2-bench/main/RELEASE_NOTES.md).
- tau3-bench advertises "75+ task fixes across the existing domains" — [evalscope tau3 page](https://evalscope.readthedocs.io/en/latest/benchmarks/tau3_bench.html) (secondary; not found in the official release notes).

**OSWorld**
- OSWorld-Verified (Jul 2025): ~300 feedback items from MoonShot, HUD, OpenAI, ByteDance Seed, Anthropic, Simular, HKU reviewed over ~1 month; ~2 months for ~10 people. Issue classes: web structure changes (HTML parsing, URL-based checks, `possibility_of_env_change` flag), anti-crawling/CAPTCHAs, time-sensitive booking tasks, instruction ambiguity (added formats/paths/scope; preferred adding alternative gold answers over rewording), evaluation robustness (tolerant file/image/spreadsheet/colour/unit comparisons), environment stability (VM image 50GB→25GB, fonts, VLC audio). Eval time dropped from 10+ hours to minutes with 50 parallel environments. Lesson: "Providing reliable rewards consumes more human resources than we imagined" — [xlang.ai blog](https://xlang.ai/blog/osworld-verified).
- ABC: 13 of 46 OSWorld Chrome tasks broken by website changes to HTML selectors, underestimating UI-TARS by 28 points absolute — [arXiv 2507.02825](https://arxiv.org/html/2507.02825).
- Epoch review of OSWorld 2.1 (28 Sep 2026): stratified sample of 50 of 108 tasks; 40 errors in 36 tasks (72%): 24 grader false negatives (exact string match; LLM judge rejecting an equivalent item name), 12 false positives (uploading every document scores 100%; a one-word message scores 50%), 4 infeasible tasks/checkpoints; up to 50.4% of audited score affected (upper bound); leading agent Astra lost ~20.8% of its score on affected tasks to mis-grading; verdict "Flawed" — [Epoch](https://epoch.ai/benchmarks/osworld-2-1/review).

**WebArena / other ABC findings**
- WebArena substring matching accepts extra irrelevant content and the LLM judge accepts empty replies on "N/A" tasks: 1.4–5.2% overestimate. KernelBench fuzzer varies only tensor values, overestimating correctness by ~31 points. SWE-Lancer: agents can read/overwrite test files in a ZIP, enabling 100% without solving tasks. CVE-Bench: time-based SQL-injection check passed any query containing SLEEP (32.5% overestimate); blocking an unrestricted outbound server cut success 10% — [arXiv 2507.02825](https://arxiv.org/html/2507.02825).

**Terminal-Bench: defects found post-release**
- "Benchmarks as Software" (ICML 2026): continuous-validation pipeline (CI checks + LLM-as-judge) found task-side defects in 28 of 89 TB 2.0 tasks (31%): overspecified instructions, underspecified verifiers, environment drift. Scores rose up to 12 points across 19 agents; ranking stable (Spearman 0.958); 28.8% of tokens charged to failed trials on changed tasks were spent on work TB 2.1 verifies as solvable. Harness effect on TB 2.1: codex→terminus-2 with the same OpenAI model cut accuracy up to 29.9 points, closed by raising the per-task budget — [ICML 2026](https://icml.cc/virtual/2026/82793).
- TB 2.1 breakdown: 9 tasks external-dependency drift, 8 resource-budget mismatches, remainder misspecification (e.g., `query-optimize` tests expected Spark SQL while instructions asked for PostgreSQL); "no task is unsolved in Terminal-Bench 2.1"; Z.AI's "Terminal-Bench 2.0 Verified" work contributed to 11 of 28. Score shifts TB2.0→2.1: Opus 4.6 (Claude Code) 58.0→70.1 (+12.1), GPT-5.3-Codex (Codex CLI) 73.3→79.1, GPT-5.4 (Terminus 2) 55.1→54.8; per-task biggest gains polyglot-c-py +84.3, polyglot-rust-c +74.3 — [tbench.ai](https://www.tbench.ai/news/terminal-bench-2-1).
- TB 2.0 paper limitations: agents have internet access so reading oracle solutions is possible (none observed in tens of thousands of trajectories); only a canary string guards against contamination; "no private test set" — [arXiv 2601.11868](https://arxiv.org/html/2601.11868).

**GAIA**
- Of 623 newly crafted questions, 55% got two matching independent answers, 27% one, 18% none; ~68% valid as-is, rest corrected or removed — [arXiv 2311.12983](https://arxiv.org/html/2311.12983).

**Scaffold overfitting, shortcuts, holdouts**
- "AI Agents That Matter" (Jul 2024; TMLR 2025): many agent benchmarks lack adequate holdout sets (seven with none and no plans), letting agents overfit; repeated calls raise accuracy at much higher cost; recommends cost–accuracy Pareto reporting — [arXiv 2407.01502](https://arxiv.org/abs/2407.01502), [project page](https://agents.cs.princeton.edu/).
- HAL (Oct 2025): across 21,730 rollouts, "higher reasoning effort reducing accuracy in the majority of runs"; agents searched HuggingFace for the benchmark answer key; agents misused credit cards in flight-booking tasks; found via LLM-aided log inspection; 2.5B tokens of logs released — [arXiv 2510.11977](https://arxiv.org/abs/2510.11977).
- "Efficient Benchmarking of AI Agents" (Mar 2026): "scaffold-driven distribution shift" degrades absolute score prediction but rank order stays stable (8 benchmarks, 33 scaffolds, 70+ model configs) — [arXiv 2603.23749](https://arxiv.org/abs/2603.23749).
- METR GPT-5 study (cited by EvilGenie): reward hacking in 18 of 789 samples (2.3%) on RE-Bench and HCAST — [arXiv 2511.21654](https://arxiv.org/pdf/2511.21654).

**pass@k vs pass^k**
- tau-bench defines pass^k = E_task[C(c,k)/C(n,k)] (n trials, c successes) = "the chance that all k i.i.d. task trials are successful, averaged across tasks," for customer-service settings that need reliability; pass@k = 1 − E_task[C(n−c,k)/C(n,k)]. GPT-4o pass^1 ≈ 61.2% retail / 35.2% airline; retail pass^8 < 25% — [arXiv 2406.12045](https://arxiv.org/html/2406.12045).
- tau2-bench: pass^k falls faster for telecom than airline as k grows; dual-control lowers pass^1 by 18 points (gpt-4.1) and 25 points (o4-mini) vs No-User mode — [arXiv 2506.07982v1](https://arxiv.org/html/2506.07982v1).
- Anthropic: pass@k "rises with k ... use when one success matters"; pass^k "falls with k ... use when consistency matters"; 75% per-trial success gives ~42% pass^3 — [Anthropic, Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

**Saturation**
- Anthropic: "Eval saturation occurs when an agent passes all of the solvable tasks, leaving no room for improvement"; near saturation, large capability gains show as small score gains — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). Pebblous reports Verified top score moving 74.9%→80.9% over six months before retirement (secondary, unsourced to OpenAI) — [Pebblous](https://blog.pebblous.ai/blog/swe-bench-verified-retired/en/).
- TB3 explicitly targets <= 30% solve rate at release to avoid early saturation — [tbench.ai](https://tbench.ai/news/tb3-contribution-call).

### Inferences
- Discovery mechanisms that worked: (1) selecting tasks a strong model fails *inconsistently* across many runs and having several humans read them (OpenAI, 64 runs x 138 tasks); (2) trivial/empty/adversarial agents (ABC, Terminal-Bench exploit agent); (3) CI-style re-validation on every release (Terminal-Bench 2.1, OSWorld fix log); (4) LLM-aided log inspection at scale (HAL). A 20-task in-house set can afford all four.
- The recurring root cause for coding benchmarks is repurposing artefacts made for another purpose (PR tests) as graders. Tasks written *for* evaluation with explicit requirements (SWE-Bench Pro style) and multiple gold answers (OSWorld-Verified style) fail less.
- Fix evaluators, not wording, where possible, so scores stay comparable (OSWorld-Verified); version the benchmark and declare non-comparability when wording changes (tau2 2.0.0).

### Gaps
- The 38.3% (underspecified) / 61.1% (unfair tests) breakdown in OpenAI's 2024 Verified post could not be confirmed by fetch; only the 68.3% aggregate and 93/1,699/3x figures were verified via mirrors.
- OpenAI's Feb 2026 and Jul 2026 posts could not be fetched directly; all numbers are via Epoch, The Decoder, Pebblous, DEV Community, Ground Truth. The 70% "noise ceiling" is unconfirmed.
- No count of tau-bench tasks changed between tau-bench and tau2-bench; the "75+ fixes" figure is only in third-party tau3 pages.
- A reported May 2026 audit claiming SWE-Bench Pro graders mis-graded "roughly a third of trials" could not be traced to a primary source.

## Key question 3: How are task sets sized, and what is known about how many tasks or trials are needed to tell two configs apart and about per-task variance?

### Takeaway
Published variance work says: question-sampling variance dominates and cannot be reduced by rerunning, so ~1,000 tasks are needed to detect a 3-point difference unpaired; but paired comparison on the same tasks, repeated trials per task (K≈4–6 captures most of the trial-variance reduction), and restricting to mid-difficulty tasks (30–70% pass rate) cut the requirement by half or more. On SWE-bench Verified, run-to-run SD of a fixed config is 0.7–1.8 points even at temperature 0, so ~9 runs/arm detect a 2-point and ~36 runs a 1-point difference; a 20–50 task set is defensible only for large effects.

### Cited Findings

**Variance decomposition and sizing formulas**
- Miller, "Adding Error Bars to Evals" (Nov 2024): Var(mean) = (Var(x) + E[sigma^2]) / n, where Var(x) is question-difficulty variance across the super-population (not reducible by rerunning) and E[sigma^2] is per-question trial variance (reducible by resampling). Resampling K times gives sigma^2/K; in the binary uniform-difficulty example K=2 cuts variance by 1/3, K=4 by 1/2, K=6 by 5/9, ceiling 2/3. Five recommendations: CLT standard errors; clustered SEs when questions are grouped (up to ~3x inflation in examples); variance reduction via resampling and next-token probabilities (do not lower temperature); paired differences when comparing two models; power analysis. Example: delta = 3 points, 80% power, alpha 0.05 → ~969 questions, "so new evals should have at least 1,000." With n = 198 and inter-model correlation 0.5, raising K from 1 to 10 shrinks the minimum detectable effect from 13.2% to 7.5% — [arXiv 2411.00640](https://arxiv.org/html/2411.00640v1).
- Bowyer et al., ICML 2025 spotlight: CLT-based error bars "usually dramatically underestimate uncertainty" below a few hundred datapoints; recommends Bayesian/frequentist small-sample methods (library sambowyer/bayes_evals) — [arXiv 2503.01747](https://arxiv.org/abs/2503.01747).
- Secondary calculators (same formulas): 4,361 questions to detect a 3-point gap at a 50% baseline (80% power); for 65% vs 60%, 1,471 per agent unpaired vs 626 shared paired at 20% discordance; ±3 points near 50% needs 1,068 tasks — [antonsoo/errorbars](https://github.com/antonsoo/errorbars), [agent-evals-explained](https://github.com/BrendanJamesLynskey/agent-evals-explained) (tool outputs, not peer-reviewed).

**Run-to-run variance on agent benchmarks**
- "On Randomness in Agentic Evals" (Bjarnason, Silva, Monperrus; arXiv 2602.07150, Feb–Mar 2026): 10 independent runs x 500 SWE-bench Verified tasks x 6 model–scaffold configs (Qwen3-32B, DeepSWE-preview, Devstral-2 on nano-agent and R2E-Gym), ~60,000 trajectories, 25.58B tokens. Single-run pass@1 within one configuration spans 2.2–6.0 points min-to-max; largest SD at temperature 0 is 1.8 points; lower temperature does not reliably reduce variance (Qwen3-32B/nano-agent SD 0.7 at T=0.6 vs 1.2 at T=0); scaffold changes both mean and spread (DeepSWE 31.4 ± 1.0 on nano-agent vs 34.4 ± 1.5 on R2E-Gym); median first differing token ~5 at T=1.0, ~56 at T=0. Power: ~9 runs per agent for a 2-point effect, ~36 for 1 point at 80% power; with SD 0.7/1.5/1.8 a 2-point effect needs 2/9/13 runs and a 1-point effect 8/36/51 — primary [arXiv 2602.07150](https://arxiv.org/abs/2602.07150) (numbers read via [DEV Community summary](https://dev.to/devinios/same-model-same-scaffold-10-runs-agent-benchmark-scores-still-move-by-up-to-6-points-gmb); the primary was not fetched).
- "Identical Runs, Different Results" (Sep 2026): 584 runs, six agent–model pairings each run 52 times on one ML-engineering task; "identical runs of one pairing varied more than the pairings differed from one another"; resolving differences would take "tens to more than a hundred runs of each"; fewer than 1 in 20 runs broke data rules and those had the highest scores; recommends evaluating agents and models as pairings over repeated attempts and reporting compliance alongside quality — [arXiv 2609.33812](https://arxiv.org/abs/2609.33812).
- Terminal-Bench 2.0: each agent–model combination run at least five times (32,155 trials total); 95% CIs of ±2.5–3.0 points on 89 tasks — [arXiv 2601.11868](https://arxiv.org/html/2601.11868). Criticism: pass/fail on 89 tasks "discards partial progress, which makes the metric noisy," and independent vs official runs "disagree by several points" — [Snorkel TB 2.0 page](https://snorkel.ai/leaderboard/terminal-bench-2-0/) (secondary).
- tau2-bench 1.0.1 re-grade shows how grader fixes alone move pass^1 by up to +9.02 points for one model and 0 for others — [RELEASE_NOTES.md](https://raw.githubusercontent.com/sierra-research/tau2-bench/main/RELEASE_NOTES.md).
- BrowseComp: with 64 samples per question, majority vote, confidence-weighted vote and best-of-N each improved Deep Research accuracy ~15–25% over a single attempt — [arXiv 2504.12516v1](https://arxiv.org/html/2504.12516v1).
- CL-Bench averages over five rollouts with varied instance orders to reduce ordering effects — [arXiv 2606.05661](https://arxiv.org/html/2606.05661).

**Choosing which tasks (discriminative subsets)**
- "Efficient Benchmarking of AI Agents" (Mar 2026): evaluate only on tasks with historical pass rates of 30–70% (IRT motivation: mid-difficulty items are most informative); cuts tasks 44–70% while keeping rank fidelity under scaffold and temporal shift; random subsets have high variance across seeds — [arXiv 2603.23749](https://arxiv.org/abs/2603.23749).
- DeltaSelect (Sep 2026): picks tasks whose one-run results track full-benchmark performance (Pearson); in DeepSWE's published trials only 22 of 113 tasks (19.5%) had a 5th-percentile correlation >= 0.50 with full-benchmark performance; intended for baseline-vs-candidate decisions within a dollar budget, not rankings; case study of 13 evaluations cost $27.86 — [arXiv 2609.19607](https://arxiv.org/abs/2609.19607).
- Anthropic: "20-50 simple tasks drawn from real failures is a great start" because early effect sizes are large; mature agents need larger evals for smaller effects; run multiple trials per task; a 0% pass rate across many trials "is most often a signal of a broken task, not an incapable agent" — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

**Harness as a variance source**
- Harness-Bench: wide variation in completion, process quality, efficiency and failure behaviour across model–harness pairings; report at pairing level — [arXiv 2605.27922](https://arxiv.org/pdf/2605.27922). Terminal-Bench 2.1: up to 29.9-point swing from harness alone with the same model — [ICML 2026](https://icml.cc/virtual/2026/82793). Epoch flagged scaffold dependence of SWE-bench Verified in Jun 2025 — [Epoch](https://epoch.ai/benchmarks/swe-bench-verified/review).

**Reporting hygiene**
- BetterBench (Nov 2024): 46 criteria applied to 24 benchmarks; "most benchmarks do not report statistical significance of their results nor allow for their results to be easily replicated" — [arXiv 2411.12990](https://arxiv.org/abs/2411.12990).
- "Lessons from the Trenches" (May 2024, lm-eval-harness): models are highly sensitive to evaluation setup; reproducibility and transparency lacking; share exact prompts/code — [arXiv 2405.14782](https://arxiv.org/abs/2405.14782).
- ABC reporting items: open-source dataset and harness (R.1–2), report statistical significance (R.10), report trivial-agent baselines (R.13) — [arXiv 2507.02825](https://arxiv.org/html/2507.02825).

### Inferences
- For a 20–30 task set with N trials per task, the dominant uncertainty is task sampling, so the set can only support claims like "config A beats B on *these* tasks" (paired, per-task) rather than population claims. Report paired per-task deltas with bootstrap or Bayesian intervals, not CLT SEs (Bowyer et al. threshold of a few hundred datapoints).
- Expected in-house per-task behaviour: a meaningful fraction of tasks will flip between trials; Miller's K≈4–6 guidance and Terminal-Bench's ≥5 runs converge on 5 trials as the practical floor. For a 2-point effect at SD ~1.5 the 9-run figure applies to whole-benchmark means on 500 tasks; on 20 tasks, only effects of tens of points will be detectable.
- Tasks with 0% or 100% pass across all configs carry no discriminative information (IRT view); the 30–70% filter and DeltaSelect's correlation screen are the two published selection heuristics.

### Gaps
- No source gives per-task flip rates (fraction of tasks that are sometimes-pass/sometimes-fail) for a fixed config; the "On Randomness" paper may contain this but was only read via a secondary summary.
- No published power analysis specifically for ~20-task agent suites; Anthropic's "20–50 tasks" is advice, not a computation.
- Clustered-SE guidance for agent tasks that share an environment or template (likely in a 20-task set) is only addressed generically by Miller.

## Key question 4: Which benchmarks or papers test memory, skills, or continual learning in agents, and how do they build tasks where memory or a skill measurably helps?

### Takeaway
The 2025–2026 memory/skill benchmarks converge on one design: pair each task with a matched control (no-memory or stateless or no-skill run of the same system), build task *sequences* with shared latent structure that cannot be recovered from pretraining, keep skill or memory content free of task-specific answers (leakage gates), and report the paired gain. Findings are sobering: naive in-context learning beats dedicated memory systems on CL-Bench, curated skills give +16.6 points on SkillsBench but self-generated skills are net negative, and 13–16 of ~85 tasks get worse with skills.

### Cited Findings

**Memory (conversational / declarative)**
- LongMemEval (Oct 2024): 500 questions embedded in scalable user–assistant chat histories; five abilities: information extraction, multi-session reasoning, temporal reasoning, knowledge updates, abstention; commercial assistants and long-context LLMs show a 30% accuracy drop in sustained interaction; S* variant ~355k tokens — [arXiv 2410.10813](https://arxiv.org/abs/2410.10813), length via [MemoryAgentBench](https://arxiv.org/html/2507.05257v3).
- MemoryAgentBench (Jul 2025; ICLR 2026): four competencies: accurate retrieval, test-time learning, long-range understanding, selective forgetting; reworks long-context datasets into multi-turn feed plus two new datasets, EventQA and FactConsolidation (feeds a fact then a contradictory update so the agent must overwrite memory) — [arXiv 2507.05257](https://arxiv.org/abs/2507.05257v2).
- MemoryArena (Feb 2026): "human-crafted agentic tasks with explicitly interdependent subtasks" across web navigation, preference-constrained planning, progressive information search, sequential formal reasoning; agents near-saturated on LoCoMo perform poorly here; argues LoCoMo/LongMemEval/MemoryAgentBench test recall without agent actions — [arXiv 2602.16313](https://arxiv.org/abs/2602.16313).
- MemoryBench (Oct 2025; ICML 2026): splits declarative (task-independent facts) vs procedural memory (how tasks are executed); simulates explicit and implicit user feedback with an LLM-as-user; finds existing memory systems "are not good at utilizing procedural knowledge to improve their performance" — [arXiv 2510.17281](https://arxiv.org/abs/2510.17281v3).
- 2026 additions found but only abstracts/reference lists seen: StreamMemBench (streaming, future-oriented assistance) [arXiv 2606.14571](https://arxiv.org/pdf/2606.14571); EvoMemBench (self-evolving memory by scope) [arXiv 2605.18421](https://arxiv.org/html/2605.18421v2); PATH-Bench (path-dependent lifelong agents) [arXiv 2608.01149](https://arxiv.org/pdf/2608.01149); "Learning on the Job" (deployment-feedback continual learning for frozen-weight agents) [arXiv 2607.22157](https://arxiv.org/pdf/2607.22157); survey [arXiv 2602.06052](https://arxiv.org/pdf/2602.06052). DolphinBench "600 tasks" with real tool calls is claimed by a vendor blog — [mem0.ai](https://mem0.ai/blog/state-of-ai-agent-memory-2026) (secondary, unverified).

**Continual learning across task instances (how to make memory measurably help)**
- CL-Bench (Jun 2026): six domains (software engineering, signal processing, disease outbreak forecasting, database querying, strategic game-playing, demand forecasting); instance counts: Codebase Adaptation 19 bugfix issues, Blind Spectrum Monitoring 90 scans, Cohort Studies 20, Database Exploration 40 questions, Exploitable Poker 120 hands. Design: each task has structure shared across instances but not stated (codebase layout, schema conventions, opponent tendencies); tasks built from scratch because standard benchmark items are independent and solvable by a strong offline model; early instances must yield feedback usable later; some tasks add concept drift (DB migration, shifting populations). Gain metric: stateful reward minus the same system run statelessly on the same instance; normalised gain divides by headroom (max reward minus stateless baseline). Grading per domain: hidden regression tests with step-efficiency weighting; mean IoU; information gain in bits (KL); fewer exploratory queries scores higher with wrong answers = 0; big blinds per hand. Validation: two authors, then 2–3 domain experts rating realism, reusable knowledge, learning improvement (~2.1 h per cycle, range 1–4.5 h). Results (normalised gain): naive ICL + Claude Sonnet 4.6 25.4% (highest), ICL + GPT-5.4 20.1%, Claude Code + Sonnet 4.6 23.9%, Mem0 + GPT-5.4 20.2%, ACE + GPT-5.4 8.6%, ICL Notepad + GPT-5.4 7.8%, ICL + Gemini 3.1 Pro 6.2%. Lessons: tasks need real headroom not recoverable from pretraining; environment must give usable feedback; experts flagged artificial puzzle structure; drift tests discarding stale knowledge; five rollouts with varied orders — [arXiv 2606.05661](https://arxiv.org/html/2606.05661).

**Skills (procedural knowledge supplied at inference)**
- SkillsBench (Feb 2026, v4): 87 tasks, 8 domains (5–16 tasks each), 100% human-authored; 400 candidate submissions from 142 contributors, 87 accepted (~22%). Skills must supply expertise for a class of problems, "never the solution to a specific instance"; instructions never name which skill to use (progressive disclosure); a leakage gate rejects skills containing task-specific filenames, paths, magic numbers or verbatim oracle commands; tasks solvable without procedural guidance or with no measurable gap between conditions are rejected. Each task: containerised environment, oracle solution passing 100%, deterministic pytest verifier (85/87; 2 Python checkers); no LLM judge; BenchFlow harness, Terminal-Bench scoring. 18 model–harness configs (OpenHands, Gemini CLI, Claude Code, Codex CLI), 3 public trials per (config, task, condition). Results: mean task-macro pass rate 33.9% → 50.5% (+16.6 pp; 25.5% normalised); config gains +4.1 to +25.7 pp, all 18 improved; domain gains +9.7 (Math & OR) to +28.8 pp (Natural Science); 13 of 87 tasks negative (largest −7.4 pp); self-generated skills scored *below* no-skills on all three configs tested (−8.1, −11.3, −11.5 pp) while curated gave +18.2 to +24.8 on the same configs; compact skills +19.0, standard +21.5, detailed +14.5, comprehensive +0.7 pp; 1 skill +18.0, 2–3 skills +19.0, 4+ skills +10.1 pp; benchmark skills drawn from the top quality quartile (>= 9/12, mean 10.1) vs ecosystem mean 6.2/12 — [arXiv 2602.12670](https://arxiv.org/html/2602.12670). (Earlier version reported +16.2 pp, 84 tasks, 16 negative — [hyper.ai summary](https://hyper.ai/en/papers/2602.12670); use v4 numbers.)
- SkillLearnBench (Apr 2026): 20 verified "skill-dependent" tasks across 15 sub-domains from a real-world skill taxonomy; evaluates skill quality, trajectory and outcome; all continual-learning methods beat no-skill baseline but gains are inconsistent; stronger backbones do not reliably produce better skills; methods help on tasks with clear reusable workflows and struggle on open-ended tasks; "self-feedback alone induces recursive drift" — [arXiv 2604.20087](https://arxiv.org/abs/2604.20087).
- Memp (Aug 2025; Findings of ACL 2026): procedural memory built from trajectories; on ALFWorld with GPT-4o best method 87.14% success / 15.01 steps vs 39.28% / 23.76 steps without memory; memory built by a stronger model transfers gains to a weaker one — [arXiv 2508.06433](https://arxiv.org/abs/2508.06433v1), numbers via [review](https://liner.com/review/memp-exploring-agent-procedural-memory) (secondary).
- Anthropic (practitioner guidance): grade "what the agent produced, not the path it took"; use state checks for outcomes and transcript checks for constraints like turn count — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

### Inferences
- The transferable recipe for "tasks where memory or a skill should help": (1) matched control runs of the identical system without the memory/skill; (2) per-task paired delta as the metric, normalised by headroom; (3) sequences of instances sharing hidden structure (CL-Bench) or later subtasks depending on earlier outputs (MemoryArena); (4) a leakage gate so the skill/memory cannot contain the answer; (5) reject tasks with no gap between conditions during validation (SkillsBench).
- Expect negative deltas on 15–20% of tasks; include them deliberately (Anthropic's "balance the set" and ABC's trivial-agent baseline both argue for tasks where the feature should *not* help).
- Efficiency metrics (steps, tokens, queries) are how CL-Bench and Memp detect memory benefit when success rates saturate; the platform should log them per trial.

### Gaps
- Task counts and grading for MemoryArena, StreamMemBench, EvoMemBench, PATH-Bench were not retrieved beyond abstracts.
- No source quantified how many trials are needed to detect a skill/memory effect of a given size; SkillsBench used 3 trials per cell, CL-Bench 5 rollouts, without power analysis.
- ReasoningBank and other 2025 procedural-memory papers were not found in search; no numbers.

## Key question 5: What role do humans play in task creation and validation (review, solvability checks, rubric writing, ground-truth annotation)?

### Takeaway
Across benchmarks, humans do five things: author tasks from real workflows, write an oracle/reference solution that must pass, independently re-solve or re-grade to confirm unambiguity (two-annotator agreement in GAIA, 3x labelling in Verified, 2–3 experts in CL-Bench), audit transcripts of suspicious successes/failures, and calibrate any LLM judge. Costs are consistently larger than expected: ~3 reviewer-hours per Terminal-Bench task, ~3,000 person-hours for 175 TheAgentCompany tasks, >1 hour per GDPval pairwise comparison, two months for ten people on OSWorld-Verified.

### Cited Findings
- SWE-bench Verified: 93 professional developers, 1,699 samples, each labelled three times; 68.3% filtered — [OpenAI, Aug 2024](https://openai.com/index/introducing-swe-bench-verified/) via [longtermwiki](https://www.longtermwiki.com/source/e1f512a932def9e2). Retirement audit: >= 6 engineers per problem on 138 problems — [Epoch](https://epoch.ai/benchmarks/swe-bench-verified/review), [Pebblous](https://blog.pebblous.ai/blog/swe-bench-verified-retired/en/).
- SWE-Bench Pro: "three-stage human-in-the-loop process"; humans write problem statement, requirements list and interface spec; annotators verify each fail2pass test for relevance and breadth — [arXiv 2509.16941v2](https://arxiv.org/html/2509.16941v2). OpenAI's Pro audit: AI investigator agents + five engineers per flagged task — [DEV Community summary](https://dev.to/thegatewayguy/openai-just-found-30-of-swe-bench-pro-is-broken-and-retracted-their-own-recommendation-3nlh).
- tau-bench: humans co-designed schemas/APIs/policies; GPT-4 generated DB-sampling code which humans polished; annotators wrote an initial user instruction, ran a gpt-4-turbo agent, and revised until the outcome was unambiguous (retail tasks checked with >40 trials); ground truth often copied and edited from agent actions — [arXiv 2406.12045](https://arxiv.org/html/2406.12045).
- GAIA: authors plus compensated Surge AI annotators wrote questions with a source of truth; answer must be short, unambiguous, time-stable, not in plain text online; two new annotators independently answered each question; validated only if both matched; 623 questions → 55% two matches, 27% one, 18% none; unfixable ones removed — [arXiv 2311.12983](https://arxiv.org/html/2311.12983).
- BrowseComp: trainers built "inverted" questions from a seed fact; each had to be unsolved by GPT-4o (with/without browsing), o1 and early Deep Research; not found by five Google searches; not solvable by another person in 10 minutes; a second trainer attempted questions and those solved >40% of the time were revised; trainers "confident no other valid answers existed" (uniqueness "likely but not guaranteed"). Human baseline: trainers solved 29.2% (367/1,255), gave up after two hours on 70.8%; 86.4% of solved answers matched the reference — [arXiv 2504.12516v1](https://arxiv.org/html/2504.12516v1).
- TheAgentCompany: tasks written by coauthors and collaborators (10 software engineers for SWE, one PM, one DS, two senior HR/admin professionals); ~20 contributors over two months, ~3,000 person-hours; each task needed screenshot proof the evaluator is valid and full score achievable; lead authors code-reviewed each contribution; a separate person checked checkpoint scoring consistency; no human-solver baseline — [arXiv 2412.14161](https://arxiv.org/html/2412.14161).
- Terminal-Bench 2.0: 93 contributors submitted 229 tasks, 89 selected by difficulty assessment and quality review by three experienced reviewers; criteria specificity (tests pass only in acceptable end states), solvability (oracle passes), integrity (no shortcuts absent in real deployment); pipeline: automated CI checks (canary string, Dockerfile, privileges), contributor checklist, LLM check tool (typos, anti-cheating, hardcoded solutions), manual team review, runs with multiple models, an OpenHands adversarial exploit agent prompted to cheat with every trajectory manually inspected (exploits found: monkey-patching tests, guessing, enumerating answers), final audit by two additional reviewers; ~3 reviewer-hours per task; LLM debug tool checks whether failures stem from insufficient instructions; GPT-5 judge agreed with 120 human-labelled traces 90% of the time — [arXiv 2601.11868](https://arxiv.org/html/2601.11868).
- OSWorld-Verified: ~300 feedback items from external labs, reviewed by XLANG authors and named students over ~2 months with ~10 people; public fix-log spreadsheet — [xlang.ai](https://xlang.ai/blog/osworld-verified).
- SkillsBench: 1,400-member contributor community, 200+ task authors onboarded via scoping interviews; 22% acceptance; maintainers personally inspect multimodal outputs — [arXiv 2602.12670](https://arxiv.org/html/2602.12670).
- CL-Bench: two author reviews then 2–3 domain experts rating realism, reusable knowledge and learning improvement, ~2.1 h per cycle — [arXiv 2606.05661](https://arxiv.org/html/2606.05661).
- GDPval: task authors >= 4 years experience (avg 14), expert graders, >1 h per pairwise comparison, 71% inter-expert consistency — [arXiv 2510.04374](https://arxiv.org/html/2510.04374v1).
- METR: QA asks a human to attempt the task "using the same resources an AI agent could use" with no special information beyond the prompt; submissions need a documented QA run plus summary/detailed explanation/eval info in a meta folder; variants that only remove requirements skip separate QA, major changes need new QA; tasks should include automated tests; keep task code private so it does not end up in training data — [taskdev.metr.org QA](https://taskdev.metr.org/quality-assurance/), [implementation](https://taskdev.metr.org/implementation/), [METR task-template](https://github.com/METR/task-template), [Task Standard post, Feb 2024](https://metr.org/blog/2024-02-29-metr-task-standard/). HCAST: 189 tasks, 563 human baselines (>1,500 hours); human testers log bugs and ambiguities in instructions or scoring logic, which are usually fixed rather than dropping the task; reviewers check successes for reward hacking and failures for causes outside the agent's control — [arXiv 2503.17354](https://arxiv.org/abs/2503.17354), [HCAST PDF](https://metr.org/hcast.pdf).
- Anthropic: unambiguity test is that "two domain experts would independently reach the same pass/fail verdict"; create a reference solution per task to prove solvability; calibrate LLM graders against human experts, then occasional human review; "Read the transcripts!"; domain experts and product teams contribute most tasks (PMs, CS, sales via PRs) while an evals team owns infrastructure — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).
- Hamel Husain (judge calibration, updated Sep 2026): binary pass/fail over 1–5 scales; one judge per failure mode discovered through error analysis; prerequisite of at least 20 Pass and 20 Fail human-labelled examples; validate against ~100 human-labelled traces measuring TPR/TNR — [latent.space wiki](https://latent.space/wiki/hamel-husain/), [write-judge-prompt skill mirror](https://tessl.io/registry/skills/github/hamelsmu/evals-skills/write-judge-prompt), [validate-evaluator mirror](https://claudeskills.info/skills/hamelsmu/evals-skills/validate-evaluator/) (third-party mirrors of hamelsmu/evals-skills).

### Inferences
- A minimal credible human loop for a 20-task set: author writes task + oracle; a second person solves blind from the prompt only (METR/GAIA/BrowseComp pattern); run the oracle in CI; run a trivial agent and a "cheat" prompt; read every transcript of the pilot; fix evaluators before wording.
- Human labels are the calibration set for any LLM judge; 20/20 pass/fail minimum (Husain) and inter-annotator agreement reporting (GDPval's 71%) are the published anchors.

### Gaps
- No source gives the per-task human cost for state-check-graded tasks specifically; TB's ~3 h/task is the closest.
- SWE-Bench Pro's three annotation stages and annotator count are not in the paper text retrieved.

## Key question 6: What task-design lessons do practitioners give for building a small in-house task set?

### Takeaway
Practitioner guidance (Anthropic, OpenAI's audits, Sierra, Scale, METR, Terminal-Bench, OSWorld maintainers, Braintrust, LangChain, Husain, Princeton HAL/ABC) agrees on: start with 20–50 tasks mined from real failures; grade end state not path; one oracle solution and one trivial-agent baseline per task; isolated clean environment per trial; multiple trials; paired comparison; partial credit for multi-part tasks; judges only for what code cannot check, calibrated on human labels; treat the benchmark as versioned software with continuous validation; and read transcripts before believing a number.

### Cited Findings

**Anthropic, "Demystifying evals for AI agents" (2026)**
- Definitions: task, trial ("Each attempt at a task is a trial"), grader, transcript, outcome ("the final state in the environment at the end of the trial" e.g. a reservation exists in the DB, not that the agent claimed it).
- Grader taxonomy: code-based (string match, unit tests, static analysis, state and tool-call checks: fast, objective, brittle), model-based (rubrics, NL assertions, pairwise, reference-based, multi-judge: flexible, non-deterministic, needs calibration), human (gold standard, expensive). Scoring can be weighted, binary (all graders pass) or hybrid.
- Task sourcing: manual pre-release checks, common user tasks, bug trackers, support queues. Balance the set: test where a behaviour should and should not occur to avoid one-sided optimisation. Partial credit for multi-component tasks. For judges: provide an "Unknown" option, structured rubrics, one judge per dimension. Make graders resistant to hacks.
- Isolation: trials start from a clean environment; leftover files or git history inflate scores; shared resource limits make failures correlated.
- Rigid tool-call-sequence checks are "overly brittle"; grade outcomes; use transcript checks only for constraints (turn count, tokens).
- Case: Claude Opus 4.5 scored 42% on CORE-Bench due to rigid numeric matching (rejecting "96.12" for "96.124991…"), ambiguous specs and irreproducible stochastic tasks; 95% after fixes. METR found tasks whose grading contradicted their instructions.
- Capability evals (low pass rate, "hill to climb") graduate into regression evals (near 100%, run continuously) — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

**OpenAI (2026 audits)**
- Tests repurposed from PRs "don't necessarily measure model capability"; future benchmarks should be "built by experienced software developers specifically to test model capabilities"; OpenAI is building its own non-public tests; "Evaluation flaws are easier to detect now than they would have been even a short time ago" (AI investigators + human review) — via [DEV Community](https://dev.to/thegatewayguy/openai-just-found-30-of-swe-bench-pro-is-broken-and-retracted-their-own-recommendation-3nlh) and [The Decoder](https://the-decoder.com/openai-wants-to-retire-the-ai-coding-benchmark-that-everyone-has-been-competing-on/).
- BrowseComp design: answers short and verifiable; questions screened against current models and a 10-minute human solve bar; a second trainer blind check — [arXiv 2504.12516v1](https://arxiv.org/html/2504.12516v1).

**Sierra (tau-bench family)**
- Use pass^k for reliability-sensitive deployments; grade DB end-state plus required outputs; iterate instructions against an agent until outcomes are unambiguous; quantify user-simulator error separately (16–47% of conversations); version releases and declare score non-comparability; ship a `--fresh-tasks` re-grade flag and tagged versions (`pre-v1.0.1`) so old scores are reproducible — [arXiv 2406.12045](https://arxiv.org/html/2406.12045), [arXiv 2506.07982v1](https://arxiv.org/html/2506.07982v1), [RELEASE_NOTES.md](https://raw.githubusercontent.com/sierra-research/tau2-bench/main/RELEASE_NOTES.md).

**Scale AI (SWE-Bench Pro)**
- Human-written requirements and interface specs alongside the issue; exclude 1–10 line trivial edits; cap per-repo contribution; run gold tests several times and drop inconsistent environments; use copyleft and private repos as a contamination deterrent — [arXiv 2509.16941v2](https://arxiv.org/html/2509.16941v2).

**Terminal-Bench team (and "Benchmarks as Software")**
- Three task standards: specificity, solvability, integrity. Pipeline includes canary strings, LLM checks for hardcoded solutions, adversarial exploit agent, two-reviewer final audit, >= 5 runs per config with 95% CIs — [arXiv 2601.11868](https://arxiv.org/html/2601.11868). Post-release: continuous validation, versioned revisions, fix external-dependency drift and resource budgets, confirm every task is solved by at least one agent — [tbench.ai TB 2.1](https://www.tbench.ai/news/terminal-bench-2-1), [ICML 2026](https://icml.cc/virtual/2026/82793). TB3 targets <= 30% solve rate at release to leave headroom — [tbench.ai](https://tbench.ai/news/tb3-contribution-call).

**OSWorld maintainers**
- Prefer minimal evaluator changes over task-wording changes to keep scores comparable; add alternative gold answers; budget far more maintenance time than expected; monitor task health continuously; build controlled environments for tasks depending on external sites; keep both decentralised and centralised evaluation; document every issue and fix in a public log — [xlang.ai](https://xlang.ai/blog/osworld-verified).

**METR**
- Blind human QA with the agent's resources; documented QA run per task; automated tests in the task; private task code to avoid training leakage; re-QA when environment or goal changes — [taskdev.metr.org](https://taskdev.metr.org/quality-assurance/), [implementation](https://taskdev.metr.org/implementation/), [task-template](https://github.com/METR/task-template). The Task Standard "helps ensure that the behavior of the task is well-specified"; porting tasks "usually requires clarifying specifications, per-task engineering work, and additional quality-assurance checks" — [METR, Feb 2024](https://metr.org/blog/2024-02-29-metr-task-standard/).

**Princeton (ABC checklist, HAL, AI Agents That Matter)**
- Task validity items: specify tool versions (T.1), clean state between runs (T.4), isolate agents from ground truth (T.5), provide an oracle solver (T.9). Outcome validity: handle semantically equivalent answers (O.a.1), negation in substring matching (O.b.1), verify unit tests (O.d.1), fuzz with inputs that affect output (O.e.3), state ground truth covering all successful outcomes (O.g.1). Reporting: open-source dataset/harness, statistical significance, trivial-agent baselines — [arXiv 2507.02825](https://arxiv.org/html/2507.02825).
- Report cost with accuracy; keep a holdout set; standardise harness to avoid implementation bugs; inspect logs with LLM assistance to find shortcuts — [arXiv 2407.01502](https://arxiv.org/abs/2407.01502), [arXiv 2510.11977](https://arxiv.org/abs/2510.11977).

**Braintrust / LangChain / Husain**
- Braintrust: group production traces into named failure patterns, filter a cluster into a labelled dataset, write an eval targeting that pattern; dataset records are input/expected/metadata; "plan starts with a dataset if none exists, then adds a scorer, and only then runs an experiment"; scores vary between runs of the same eval — [workshop](https://www.braintrust.dev/workshops/2026-09-09-evals-foundations), [cookbook on 1,781 agent traces](https://braintrust.dev/docs/cookbook/recipes/HuggingFaceAgentTraces), [agent-skills article](https://www.braintrust.dev/articles/best-agent-skills-llm-evaluation).
- LangChain/LangSmith: three agent-eval levels: final response (LLM-judge effective), trajectory (exact tool-sequence match is "simple but has flaws"; judge with reference trajectory tolerates slightly-off steps), single-step (fast, one decision, misses the whole agent); use several techniques — [LangSmith docs](https://docs.langchain.com/langsmith/evaluation-approaches).
- Husain: code checks first; judge only subjective criteria; binary verdicts; one judge per failure mode; calibrate on 20+20 then ~100 labelled traces — [latent.space wiki](https://latent.space/wiki/hamel-husain/), [skill mirrors](https://tessl.io/registry/skills/github/hamelsmu/evals-skills/write-judge-prompt).

**Memory/skill-specific design (from Q4)**
- Matched stateless/no-skill control per task; leakage gate on skill content; reject tasks with no gap between conditions; headroom-normalised gain; vary instance order across rollouts — [SkillsBench](https://arxiv.org/html/2602.12670), [CL-Bench](https://arxiv.org/html/2606.05661).

### Inferences
- A concrete checklist for the platform's 20+ task set, assembled only from the cited guidance: real-failure provenance for each task; oracle solution run in CI; blind human solve; trivial-agent and "cheat-prompt" baselines recorded per task; clean container per trial; >= 5 trials; paired per-task deltas with small-sample intervals; state/exact/unit graders first, judge only for NL sub-assertions with an Unknown option and human calibration labels; partial credit via checkpoints; task versioning with non-comparability flags; transcript review of every 0% and every surprising 100%.
- For "tasks where memory or skills should help": the published way to make the claim measurable is a within-task paired comparison (same harness ± feature) with the feature content audited for answer leakage, plus efficiency metrics (steps, tokens) as secondary signals.
