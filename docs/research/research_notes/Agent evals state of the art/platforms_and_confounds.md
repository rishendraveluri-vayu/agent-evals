# Agent evaluation platforms and the confounds that invalidate harness-versus-model comparisons (state as of 3 Nov 2026)

Scope note. Findings come from primary docs and papers fetched on 3 Nov 2026 unless marked "(secondary)". Older findings carry their date. Where a doc page could not be fetched, the item is listed under Gaps rather than asserted.

## Key question 1: Platform survey (what each platform does, how it models tasks/configs/runs/trials/traces, isolation, versioning, statistics, cost tracking, and gaps)

### Takeaway
Two families exist. Research harnesses (Inspect, Harbor/Terminal-Bench, Vivaria, HELM) model the sandbox, the trial and the per-sample limit explicitly and ship a durable log with resume logic; commercial observability platforms (LangSmith, Braintrust, Weave, Phoenix, DeepEval, promptfoo) model dataset -> task -> scorer -> experiment, treat "repetitions/trials" as a count on the experiment, and leave sandboxing and infra-failure classification to the user. None of the surveyed platforms records a content hash or lockfile that pins harness version x model snapshot x tool list x system prompt as one unit; the nearest are Inspect's `export-config` loop and Harbor's per-trial "Lock" tab.

### Cited Findings

**Inspect AI (UK AISI)**
- Data model: an `EvalLog` has `version`, `status` ("started", "success", "error"), `eval` (EvalSpec: task, model, creation time), `plan` (EvalPlan: "List of solvers and model generation config used for the eval"), `results`, `stats` (model usage), `error` (with traceback), `samples` with `events` transcript, `reductions`, `tags`, `metadata`, `log_updates`. Default `.eval` binary format since v0.3.46; `.json` alternative. — [Inspect: Eval Logs](https://inspect.aisi.org.uk/eval-logs.html)
- Provenance: `eval_retry()` "does not overwrite the previous log file" and keeps the original `task_id`; later edits append to `log_updates` with author and reason; score edits keep a `history`; `inspect log export-config` produces a run config that `inspect eval --run-config` accepts ("eval -> log -> config -> eval loop"); `ModelEvent.request_ids` and `ModelOutput.response_id` are recorded for supported providers. — [Inspect: Eval Logs](https://inspect.aisi.org.uk/eval-logs.html)
- Token accounting: `ModelUsage` fields are `input_tokens` ("Input tokens charged at full rate (excludes cached tokens)"), `output_tokens`, `total_tokens`, `input_tokens_cache_write`, `input_tokens_cache_read`, `reasoning_tokens`. `GenerateConfig.seed` is "OpenAI, Google, Mistral, Groq, HuggingFace, and vLLM only." — [Inspect reference: model](https://inspect.aisi.org.uk/reference/inspect_ai.model.html)
- Statistics: metrics `accuracy`, `mean`, `std`, `var`, `stderr` ("Standard error of the mean using Central Limit Theorem", with a `cluster` parameter: "The key from the Sample metadata corresponding to a cluster identifier for computing clustered standard errors"), `bootstrap_stderr`, `grouped`. Epoch reducers: `mean`, `median`, `mode`, `max`, `at_least`, `pass_at` ("Probability of at least 1 correct sample given k epochs"). — [Inspect reference: scorer](https://inspect.aisi.org.uk/reference/inspect_ai.scorer.html); [Inspect: Scorers](https://inspect.aisi.org.uk/scorers.html)
- Sandboxing: built-in `docker` and `local` ("Local file system (no sandbox)"); external packages `k8s`, `daytona`, `modal`, `ec2`, `proxmox`, `vagrant`, `openshell`. "Each sample gets its own sandbox instance, even if the sandbox is defined at Task level." `max_sandboxes` per provider; Docker default is twice available processors. — [Inspect: Sandboxing](https://inspect.aisi.org.uk/sandboxing.html)
- Resume: `eval_set` uses the log directory as "a durable record of which tasks are completed"; `retry_attempts` default 10; `retry_immediate` default on; reuse of completed samples requires stable sample IDs, and Inspect warns and skips reuse if it detects `dataset.shuffle()` "but not when shuffling happens another way." `eval_set()` returns `(success, logs)`. — [Inspect: Eval Sets](https://inspect.aisi.org.uk/eval-sets.html)
- Limits: `fail_on_error` accepts `True` (stop on first error, default), `False`, a fraction (e.g. `0.1`) or an integer count; `message_limit` is checked on each `generate()`; `token_limit` can be set per Task (e.g. 500K per sample) or by a solver; custom limits raise `SampleLimitExceededError`. (From search snippet of the page; the page itself returned only "Redirect" on fetch.) — [Inspect: Errors and Limits](https://inspect.aisi.org.uk/errors-and-limits.html)
- Output caching: cache key = model name and base URL, message history, epoch number, generate config (temperature, top_p), active `tools` and `tool_choice`; default expiry 1 week; `per_epoch=False` disables per-epoch scoping. Aliased model names "can resolve to new versions over time", so the docs advise explicitly versioned names such as `openai/gpt-4-turbo-2024-04-09`. Provider prompt caching can only be turned off for Anthropic (`--cache-prompt=false`); usage shown as I/CW/CR/O. — [Inspect: Caching](https://inspect.aisi.org.uk/caching.html)
- Ecosystem signal: METR archived its Task Standard on 7 Oct 2026 and says "we use Inspect to define tasks"; Anthropic's Petri (6 Oct 2025) is "built on the UK AI Security Institute's Inspect framework." — [METR/task-standard](https://github.com/METR/task-standard); [Anthropic Alignment Science: Petri](https://alignment.anthropic.com/2025/petri)

**Harbor and Terminal-Bench**
- Model: "A job is a collection of trials. A trial is an agent's attempt at completing a task." Inputs: tasks, models, agents, sandboxes, skills. Task directory = `instruction.md`, `task.toml`, `environment/` (Dockerfile), `solution/solve.sh`, `tests/test.sh`; verifier "must produce a numerical reward" at `/logs/verifier/reward.txt` or `reward.json`. — [Harbor: Run a job](https://docs.harborframework.com/jobs/run-a-job.md); [Harbor: Tasks overview](https://docs.harborframework.com/tasks/overview.md)
- Job config defaults: `n_attempts` 1, `n_concurrent_trials` 4, `timeout_multiplier` 1.0, `retry.max_retries` 0 with `include_exceptions`/`exclude_exceptions` ("Exclusions take precedence"), `agents[].override_timeout_sec`, `environment.type` "docker", `environment.delete` true, `verifier.override_timeout_sec`; `source_jobs` regrades earlier jobs. Resolved config saved to `<job>/config.json`. — [Harbor: Configs](https://docs.harborframework.com/jobs/configs.md)
- Task config: `[agent] timeout_sec` default null ("If not set, no timeout is enforced"); `[verifier] timeout_sec` 600; `[environment] build_timeout_sec` 600, `cpus`/`memory_mb`/`storage_mb`/`gpus` null, `network_mode` one of `"no-network" | "public" | "allowlist"` default `"public"` (`allow_internet` deprecated); `[[environment.mcp_servers]]`. — [Harbor: Task configuration](https://docs.harborframework.com/tasks/configuration.md)
- Sandboxes: local runtimes docker (default), podman, apple-container, singularity, sbx; ~30 remote providers including daytona, e2b, modal, runloop, gke, ec2, langsmith, vercel. "Harbor runs each trial in an isolated environment." Modal: "Compose on gVisor remains public-only." Docker/Podman "require Harbor's egress-control support" for allowlists; "A limit is a hard ceiling. A request reserves or selects capacity." — [Harbor: Pre-integrated sandboxes](https://docs.harborframework.com/sandboxes/pre-integrated-sandboxes.md)
- Viewer shows per-trial reward, cost, tokens, timing, trajectory; tabs Agent, Verifier, Artifacts, Config ("the resolved trial configuration") and Lock ("a replayable trial lock"). — [Harbor: View job results](https://docs.harborframework.com/results/view-job-results.md)
- Trajectory format ATIF-v1.8 with `agent` (name, version, `model_name`), `final_metrics` ("Optional aggregate token, cost, and step metrics"), per-step `metrics`, `tool_calls`, `observation`, `subagent_trajectories`. — [Harbor: ATIF](https://docs.harborframework.com/agents/atif.md)
- Terminal-Bench paper (arXiv 17 Jan 2026): tasks run via Daytona "between 32 and 100 containers in parallel"; each model-agent pair run at least five times, 32,155 trials; Table 2 reports resolution rate with 95% CI; reasoning effort left at provider default ("medium"); closed models via first-party APIs, open-weight via Together.AI. Limitations: internet access means agents "could find and read the oracle solutions" (not observed), canary string but no private test set, "Machine resources and container runtime enforcement can also vary." — [Terminal-Bench paper](https://arxiv.org/html/2601.11868)
- Current tbench.ai docs describe Terminal-Bench 4.0 run via `harbor run -d terminal-bench/terminal-bench@4.0.0 -e modal -a claude-code -m ... -k 5`; uploads "private by default." — [tbench.ai docs](https://www.tbench.ai/docs)
- Other Harbor docs pages exist for error classification, regrade ("Rerunning an updated verifier on recorded outputs without rerunning the agent"), reward-hacking hardening, separate verifier sandboxes, skills injection, and observability plugins. — [Harbor docs index](https://docs.harborframework.com/llms.txt)

**METR Vivaria and Task Standard**
- "METR's tool for running evaluations and conducting agent elicitation research"; results in PostgreSQL; the Task Standard and pyhooks "follow Semantic Versioning" while "the Vivaria server's HTTP API, the Vivaria UI, and the viv CLI don't have versions." — [Vivaria](https://vivaria.metr.org/)
- Architecture: server builds an image from task family + agent code, creates a Docker container, runs the agent; agents call the API via pyhooks ("Calls models and saves trace events"), the API forwards model calls to Middleman, which calls providers; scoring runs `TaskFamily#score` inside the container. — [Vivaria: Architecture](https://vivaria.metr.org/architecture/)
- Glossary: a run = task environment + agent started via `viv run`; "agent branch" = one agent process in a task environment, multiple branches can share a container and "aren't supposed to interact with each other, although they can theoretically" (used only for elicitation research); for evals "we run each agent inside its own agent container." Trace entries record generations, actions, results, errors. — [Vivaria: Glossary](https://vivaria.metr.org/glossary/)
- `viv run` usage limits: `max_tokens` default 300,000; `max_actions` 1,000; `max_total_seconds` 604,800 (7 days); `max_cost` 100; `checkpoint_tokens/actions/total_seconds/cost` pause for human input; `k8s` flag; `batch_concurrency_limit`; `dangerously_ignore_global_limits`. — [viv CLI reference](https://vivaria.metr.org/reference/cli/)
- Task Standard: `TaskFamily` class with `get_instructions`, `install`, `get_tasks`, `start`, `score`; agent "cannot access files and processes created/owned by root"; tasks declare internet level, and "If full_internet permission isn't requested, the driver restricts network access." Repo archived 7 Oct 2026; "METR is no longer maintaining the Task Standard. Instead, we use Inspect to define tasks." — [METR/task-standard](https://github.com/METR/task-standard)

### Inferences
- The platforms that take "trial" seriously as a first-class record with its own sandbox, limits and failure class are the research harnesses (Inspect, Harbor, Vivaria). The commercial tools expose `trials`/`repetitions` as a multiplier but do not isolate repeats from each other beyond a cache namespace.
- Harbor's per-trial "Lock" tab and Inspect's `export-config` are the only things resembling a config lockfile; neither hashes the agent's system prompt or tool list as emitted by the harness, so a change in those can still go unnoticed unless the platform records the actual request payload (Inspect logs raw model API requests for the first few calls per model plus all errors by default, and all calls with `--log-model-api`).
- Platform consolidation is underway: METR dropped its Task Standard for Inspect, HELM is in maintenance, OpenAI's hosted Evals is shutting down and points users to promptfoo, and Terminal-Bench moved onto Harbor.

### Gaps
- Inspect's errors-and-limits page returned only "Redirect" twice; `retry_on_error`, `working_limit` and what happens to scoring when a limit fires are therefore unverified here (only `fail_on_error`, `message_limit`, `token_limit` were confirmed via a search snippet).
- Harbor's on-disk `result.json` schema (fields such as `reward_valid`, `failure_cause`, `exception_info`) was seen only through the Python `TrialResult` example on the error-classification page; the full layout page was not found.
- HELM request caching (SQLite/MongoDB) and its per-run output files were not confirmed from the fetched pages.
- Braintrust's error handling and per-row token/cost fields were not on the fetched pages.
- No independent 2026 user-complaint survey of Inspect/Harbor/Vivaria was found; the "what users complain is missing" evidence is limited to vendor-adjacent comparison blogs for the commercial tools.

## Key question 2: Harness confounds (do scaffold and prompt changes move scores as much as model changes, and how to keep a single-axis comparison honest)

### Takeaway
Multiple independent measurements in 2025-2026 put scaffold-only variance on SWE-bench-style tasks at 9 to 34 points for a fixed model, which is as large as or larger than typical model-to-model gaps; Terminal-Bench's own 32k-trial study still concludes model choice usually dominates, so the honest framing is "scaffold variance is of the same order as model variance and can reverse rankings." Enabling a skill or memory necessarily changes the system prompt (skill metadata is injected at startup), so a single-axis comparison must record and diff the realized prompt and tool list, not just the config flag.

### Cited Findings
- Epoch AI: "our SWE-bench Verified scaffold was significantly upgraded in February 2026"; changelog 2026-02-12 "We performed a major upgrade of scaffolding, environments, and token limits. This led to model performance improving significantly"; 484 of 500 samples used because 16 "do not reliably run in our infrastructure"; scaffold is "a simple loop" with `bash`, Inspect's `text_editor` and `apply_patch`. — [Epoch AI: SWE-bench Verified](https://epoch.ai/benchmarks/swe-bench-verified)
- (secondary, reporting Epoch) scaffold switch alone moved GPT-5 by up to 11 points and Kimi K2 Thinking by up to 15 points; chart range ~55-72%. — [The Decoder](https://the-decoder.com/?p=30762)
- "Stop Comparing LLM Agents Without Disclosing the Harness" (arXiv 7 May 2026) collates: Epoch (11 and 15 points); HAL SWE-bench Verified Mini where Claude Sonnet 4.5 drops 68% -> 34%, GPT-5 Medium 46% -> 12%, o4-mini nearly 48 points across scaffolds; Grok 4 on SWE-bench Verified 58.6% under SWE-agent vs 72-75% under xAI's scaffold; SWE-bench Pro where adding a WarpGrep search subagent flips MiniMax 2.5 and Claude Opus 4.6; a controlled factorial where "6 of 9 model-pair/harness-pair comparisons reverse rank"; HV/MV ratio 8.72x (run 1) vs 6.76x (run 2). It is a position paper and does not measure API-provider variance. — [arXiv 2605.23950](https://arxiv.org/html/2605.23950v1)
- Terminal-Bench paper (Table 2, 95% CI): GPT-5.2 Codex CLI 62.9% +-3.0 vs Terminus 2 54.0% +-2.9; Claude Opus 4.5 Terminus 2 57.8% vs Claude Code 52.1% vs OpenHands 51.9%; GPT-5 Codex CLI 49.6% vs Terminus 2 35.2% vs Mini-SWE-Agent 33.9%; Gemini 2.5 Pro Terminus 2 32.6% vs OpenHands 15.7%. Authors conclude "model selection is usually more important than agent scaffold." — [Terminal-Bench paper](https://arxiv.org/html/2601.11868)
- HAL: "Model-scaffold pairings matter. Claude models did better with BrowserUse, and OpenAI models did better with SeeAct"; task-specific scaffolds beat the generalist on 9/12 CORE-Bench Hard and 11/12 SWE-bench Verified Mini runs while the generalist was cheaper in 20/24; recommendation "Evaluate models with the same scaffold. Only 2 benchmarks had the same scaffold for 4 or more listed models"; TAU-bench Few Shot agent's few-shot examples "included benchmark data, which invalidated its results." — [HAL paper](https://arxiv.org/html/2510.11977)
- HAL reasoning-effort confound: "Across 36 model-agent-benchmark combinations, 21 showed equal or lower accuracy with higher reasoning effort"; Anthropic "high" used LiteLLM's default 4,096-token budget while "OpenAI does not disclose its reasoning token budgets." — [HAL paper](https://arxiv.org/html/2510.11977)
- Agent Skills change the system prompt by construction: "Claude loads this metadata at startup and includes it in the system prompt"; Level 1 metadata costs "~100 tokens per Skill"; SKILL.md body (<5k tokens) is loaded only when triggered; the API path requires the code execution tool, whose container the skills run in. — [Anthropic: Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)
- Anthropic prompt-cache invalidation hierarchy `tools -> system -> messages` with "Changes at each level invalidate that level and all subsequent levels" (tool definitions invalidate all three) shows that a tool-list change also changes the request shape and cost profile. — [Anthropic: Prompt caching](https://platform.claude.com/docs/en/docs/build-with-claude/prompt-caching)
- Disclosure standard proposed (ETCSOVG, 7 layers): Execution (sandboxing, filesystem/network, timeouts, max steps), Tool (tool list, schema style, retryable error classes, model-visible vs hidden middleware), Context (context cap, summarization, retrieval, persistent memory, cache policy), Scheduling (loop, stopping rule, retry policy), Observability, Verification, Governance. Protocol: minimum 2x2 model x harness grid on a fixed task set; hold constant "task order, execution environment, evaluation script, API parameters, and stopping rules"; report HV per model, MV per harness, HV/MV ratio, ranking-reversal count, partial eta-squared with omega-squared or bootstrap interval. — [arXiv 2605.23950](https://arxiv.org/html/2605.23950v1)
- Statistical method for paired comparisons: use paired differences, not two-sample tests, because question-score correlations between frontier models were "roughly 0.3 to 0.7"; clustered SEs on popular evals "over three times as large as naive standard errors"; resample per question (Inspect `epochs`). (Nov 2024) — [Anthropic: Adding Error Bars to Evals](https://www.anthropic.com/research/statistical-approach-to-model-evals)
- SWE-bench leaderboard records scaffold only via the submission name; a 2026 analysis notes the leaderboard "does not record comparisons in a machine-readable form"; submissions require `trajs/` reasoning traces (mandatory since Jul 2024) and the "Verified" check means "the SWE-bench team received access to the model and was able to reproduce the patch generations." — [swebench.com/submit](https://swebench.com/submit.html); [SWE-bench/experiments](https://github.com/swe-bench/experiments)
- ABC (Jul 2025, 25 authors): "SWE-bench Verified uses insufficient test cases" and "TAU-bench counts empty responses as successful"; issues misstate performance "up to 100% in relative terms"; ABC "reduces the performance overestimation by 33%" on CVE-Bench. — [arXiv 2507.02825](https://arxiv.org/abs/2507.02825)
- (secondary) blogs report 10-20 point swings from harness choice and ~1-3 points sampling noise for a fixed scaffold; one cites Claude Opus 4.5 at 45.9% under SEAL's standardized scaffold vs 55.4% under Claude Code on SWE-bench Pro. — [nextgenoperator](https://nextgenoperator.beehiiv.com/p/scaffold-parity); [Daniel Vaughan, Apr 2026](https://codex.danielvaughan.com/2026/04/09/harness-performance-terminal-bench/)

### Inferences
- The two best-controlled large studies disagree on the headline (Terminal-Bench: model usually dominates; harness-disclosure paper: harness variance exceeds model variance), but both report scaffold effects of roughly 9-16 points at fixed model with overlapping CIs across scaffolds. For a platform claiming harness x model comparisons, the defensible position is to measure HV and MV on the user's own task set rather than assume either dominates.
- Because skill metadata and tool definitions are injected into the system prompt and tool list, "enable memory" or "enable skill X" is never a single-axis change at the request level. An honest comparison needs (a) a recorded realized-prompt hash and tool-list hash per trial, (b) a diff shown to the user when a one-flag change alters them, and (c) ideally a control arm where the same extra prompt text is present but the capability is inert.
- Reasoning-effort defaults differ by provider and proxy (LiteLLM's 4,096 Anthropic budget vs undisclosed OpenAI budgets), so "same effort setting" across models is itself a confound to record.

### Gaps
- No primary source quantifies the pure effect of adding a memory store or a skill (holding everything else fixed) on an agent benchmark; the evidence is about whole-scaffold swaps.
- API-provider variance under an identical scaffold is asserted in blogs and mentioned by HAL ("aggregators can serve different quantizations under the same endpoint name") but no controlled measurement was found.
- Epoch's primary page does not publish per-scaffold numbers; the 11/15-point figures are second-hand via The Decoder and the arXiv position paper.

## Key question 3: Reproducibility (pinning harness versions, model snapshots, provider updates, prompt caching, temperature, seeds, content hashes/lockfiles)

### Takeaway
Seeds are best-effort on OpenAI and absent on Anthropic; aliases silently re-point; providers swap weights; prompt caching does not change outputs but changes cost and latency. No platform surveyed ships a complete lockfile, so the platform under design should pin the dated model snapshot, log the response's resolved model and fingerprint/request id, pin the harness SHA, and hash the realized system prompt, tool list and generate config per trial.

### Cited Findings
- OpenAI seed: "our system will make a best effort to sample deterministically"; "There is a small chance that responses differ even when request parameters and system_fingerprint match"; `system_fingerprint` is "an identifier for the current combination of model weights, infrastructure, and other configuration options" and changes when OpenAI updates serving infrastructure "which may happen a few times a year." Cookbook is archived and was written for `gpt-4-1106-preview` / `gpt-3.5-turbo-1106` (late 2023). — [OpenAI cookbook: reproducible outputs](https://developers.openai.com/cookbook/examples/reproducible_outputs_with_the_seed_parameter)
- Inspect's `GenerateConfig.seed` is "OpenAI, Google, Mistral, Groq, HuggingFace, and vLLM only" (no Anthropic). — [Inspect reference: model](https://inspect.aisi.org.uk/reference/inspect_ai.model.html)
- (secondary) third-party SDK adapter states "Anthropic does NOT support seeding. Providing a seed will raise SeedingError"; several secondary sources quote Anthropic docs that temperature 0 "will not be fully deterministic." — [maseval docs](https://maseval.readthedocs.io/en/stable/interface/inference/anthropic/)
- (secondary) a 2026 post recommends bucketing eval runs by `system_fingerprint` and refusing to compare across buckets; cites a late-2025 experiment of 1,000 identical temperature-0 queries to a hosted vLLM Qwen3-235B yielding 80 unique completions. — [tianpan.co, Jun 2026](https://tianpan.co/blog/2026-06-02-the-deterministic-seed-your-eval-suite-set-that-your-provider-quietly-ignored)
- Model aliases: OpenAI's deprecations page lists "Plain-text aliases" pairs such as "gpt-5 | gpt-5-2025-08-07"; retirements are notified by email and exposed via an optional `shutdown_date` on `GET /v1/models`. — [OpenAI deprecations](https://developers.openai.com/api/docs/deprecations)
- OpenAI community feature request asks for dated snapshots of `gpt-5-main`/`gpt-5-chat-latest` because researchers "need a stable, dated target to make results comparable over time." — [OpenAI community](https://community.openai.com/t/feature-request-dated-snapshots-for-gpt-5-gpt-5-main-or-pinning-for-gpt-5-chat-latest/1338807)
- Inspect caching docs: aliased model names "can resolve to new versions over time", so use explicitly versioned names to invalidate cache. — [Inspect: Caching](https://inspect.aisi.org.uk/caching.html)
- HAL: "Providers sometimes swap model weights silently, and aggregators can serve different quantizations under the same endpoint name"; "An OpenAI API change also broke scaffolds"; "o3's price dropped 80% after release" (so dollar-cost comparisons also drift). — [HAL paper](https://arxiv.org/html/2510.11977)
- Prompt caching and outputs: "Prompt caching has no effect on output token generation. The response you receive is identical to what you would get if prompt caching were not used." Pricing: 5-minute writes 1.25x base input, 1-hour writes 2x, reads 0.1x (0.025x on Claude Fable 5.1/Mythos 5.1, 0.05x on Opus 5.5/Sonnet 5.5); default lifetime 5 minutes refreshed on use; cache hits require "100 percent identical prompt segments." — [Anthropic: Prompt caching](https://platform.claude.com/docs/en/docs/build-with-claude/prompt-caching)
- LiteLLM prompt caching: `cache_creation_input_tokens` (Anthropic "charges for this"), `prompt_tokens_details.cached_tokens`; caching "silently skipped" below provider minimums (512-4,096 tokens for Anthropic) "with no error"; OpenAI 12-hour writes bill 2.5x input; Gemini 2.5+ caches implicitly for free but `cache_control` switches to paid explicit caching. — [LiteLLM: Prompt caching](https://docs.litellm.ai/docs/completion/prompt_caching)
- Inspect records `ModelEvent.request_ids` and `ModelOutput.response_id` per call, logs raw API requests for the first few calls per model plus all errors by default (`--log-model-api` for all), and `export-config` reproduces a run config from a log. — [Inspect: Eval Logs](https://inspect.aisi.org.uk/eval-logs.html)
- Weave versions objects automatically with immutable history and `Name:hash` refs. — [Weave: Objects](https://docs.coreweave.com/weave/guides/tracking/objects)
- Harbor saves the resolved `config.json` per job and shows a "Lock: a replayable trial lock" per trial. — [Harbor: Configs](https://docs.harborframework.com/jobs/configs.md); [Harbor: View job results](https://docs.harborframework.com/results/view-job-results.md)
- promptfoo's cache key includes provider config and request digest, but "Cache key formats are implementation details and may change between versions." — [promptfoo: Caching](https://www.promptfoo.dev/docs/configuration/caching/)
- Terminal-Bench: "Internet access and changing external resources add reproducibility risk. Machine resources and container runtime enforcement can also vary." — [Terminal-Bench paper](https://arxiv.org/html/2601.11868)
- Vivaria: Task Standard and pyhooks are semver'd; the server, UI and CLI "don't have versions." — [Vivaria](https://vivaria.metr.org/)

### Inferences
- Since neither seeds nor temperature 0 deliver determinism and Anthropic exposes no seed, repeated trials should be treated as independent samples and compared with paired/clustered statistics rather than expected to replay. Caching the model output (Inspect-style, keyed by epoch) is a replay mechanism, not a reproducibility mechanism, and must stay off for trials.
- A workable lockfile for this project = harness git SHA + dated model id + resolved generate config (temperature, top_p, max_tokens, reasoning effort/budget) + hash of realized system prompt + hash of tool JSON schemas + skill/memory bundle hashes + proxy (LiteLLM) version and model_cost map version. Log the response-side `model`, `system_fingerprint`/request id per call to detect provider drift after the fact.
- Prompt caching should be recorded (cache write/read tokens) but can be left on for cost, since it does not alter outputs; however latency comparisons across configs with different cache-hit rates are confounded.

### Gaps
- Anthropic's exact Messages API wording on temperature and determinism could not be fetched (page too large); only secondary quotes were found.
- No primary source documents whether Gemini or other providers' seeds are deterministic in practice; Inspect lists Google as seed-capable but makes no determinism claim.
- No surveyed platform documents a content-hash lockfile covering prompt and tool list; this appears to be a genuine gap rather than something missed in the fetch.

## Key question 4: Isolation and contamination (state leaking between trials via filesystem, memory stores, caches, shared sandboxes, harness home directory; isolation levels and trade-offs)

### Takeaway
Research harnesses isolate at the container-per-trial level (Inspect, Harbor, Vivaria) and treat network egress as a first-class policy; microVM providers (Daytona, E2B, Modal, Docker Sandboxes) are offered as plug-ins where kernel-level isolation matters. The documented leak paths are: code outside the sandbox (custom tools, scorers), shared containers across agent branches, internet access to oracle solutions, and provider-side response caches; none of the docs explicitly address a harness's own home directory or memory store persisting across trials, so that must be designed in.

### Cited Findings
- Inspect: "each sample gets its own sandbox instance, even if the sandbox is defined at Task level"; `network_mode: none` "applies only to processes inside the container. Code in custom tools, agents, or scorers can still reach the internet outside the sandbox"; a custom Compose config "replaces the generated configuration rather than extending it", so `network_mode: none` must be re-set; writable host mounts blocked by default; `local` sandbox = "Local file system (no sandbox)". — [Inspect: Sandboxing](https://inspect.aisi.org.uk/sandboxing.html)
- Harbor: "Harbor runs each trial in an isolated environment"; `network_mode` default `"public"` with `"no-network"` and `"allowlist"` options; `environment.delete` default true; local runtimes "can also expose host-mounted logs, which remote sandboxes generally don't"; Modal "Compose on gVisor remains public-only"; limits vs requests differ by provider (Docker/Podman/Modal hard limits, Daytona/E2B requests). — [Harbor: Pre-integrated sandboxes](https://docs.harborframework.com/sandboxes/pre-integrated-sandboxes.md); [Harbor: Task configuration](https://docs.harborframework.com/tasks/configuration.md)
- Harbor also offers "Verifying tasks in a sandbox separate from the agent's" and "Hardening infrastructure against reward hacking in tasks." — [Harbor docs index](https://docs.harborframework.com/llms.txt)
- Vivaria: for evals "we run each agent inside its own agent container"; agent branches sharing a container "aren't supposed to interact with each other, although they can theoretically." — [Vivaria: Glossary](https://vivaria.metr.org/glossary/)
- METR Task Standard: agent runs unprivileged and "cannot access files and processes created/owned by root"; network restricted unless `full_internet` requested. — [METR/task-standard](https://github.com/METR/task-standard)
- Terminal-Bench ran 32-100 Daytona containers in parallel; limitation: agents with internet "could find and read the oracle solutions"; canary string but no private set. — [Terminal-Bench paper](https://arxiv.org/html/2601.11868)
- HAL: agents "searched for the benchmark on HuggingFace instead of solving the task"; "Environmental barriers such as crashed browsers or missing files appeared in roughly 40% of failed tasks on AssistantBench, CORE-Bench, and SciCode." — [HAL paper](https://arxiv.org/html/2510.11977)
- Response caches as a contamination path: LiteLLM exact-match caches "key on a hash of the whole request, so any change to the conversation is a miss" and serve the second identical request from cache with an `x-litellm-cache-key` header; Redis is "the right default for anything past a single worker." — [LiteLLM: Caching](https://docs.litellm.ai/docs/proxy/caching). Inspect's cache is per-epoch by default so repeats stay distinct; `per_epoch=False` would collapse them. — [Inspect: Caching](https://inspect.aisi.org.uk/caching.html). promptfoo caches by default with 14-day TTL and separate namespaces per repeat index. — [promptfoo: Caching](https://www.promptfoo.dev/docs/configuration/caching/). LangSmith `LANGSMITH_TEST_CACHE` reuses identical API calls across experiments. — [LangSmith: Experiment configuration](https://docs.langchain.com/langsmith/experiment-configuration.md)
- Skills on the Claude API "run in a sandboxed container with no network access and no runtime package installation"; in Claude Code "Skills have the same network access as any other program on the user's computer." — [Anthropic: Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)
- (secondary) 2026 sandboxing guides: runc containers share the host kernel; gVisor's user-space kernel implements roughly 70-80% of syscalls; Firecracker/Kata give a dedicated guest kernel via KVM at 100 ms-1 s startup and higher memory overhead; Docker shipped "Docker Sandboxes" (Apr 2026) using microVM isolation; reported Docker startup numbers conflict (10-50 ms vs ~500 ms). — [manveerc, 2026](https://manveerc.substack.com/p/ai-agent-sandboxing-guide); [dev.to, 2026](https://dev.to/aiagentengineering/how-to-sandbox-ai-agents-in-2026-firecracker-gvisor-runtimes-isolation-strategies-14pk)

### Inferences
- For a harness x model platform where the harness (e.g. Hermes) owns a home directory, memory store and caches, a fresh container per trial with the harness's `$HOME` created inside the container is the only level that matches what Inspect/Harbor/Vivaria do; a process-level isolation (shared host, per-trial temp dir) would leave the harness's own config and memory DB as a leak path that none of the surveyed research harnesses accept for evals.
- Any proxy-level response cache must be off for trials; it is a replay, not a sample. Record the proxy's cache setting in the trial record as evidence.
- Network policy is a config axis, not an environment detail: Harbor's default is public, Inspect's default compose is no-network, so the platform must pin and record it.

### Gaps
- No platform doc fetched addresses a harness's own home directory or a persistent memory store leaking between trials; this is inferred from the general per-trial container model.
- No independent head-to-head benchmark of container vs gVisor vs Firecracker for agent evals was found; the numbers above are vendor/blog figures.

## Key question 5: Cost, latency and token accounting (per-trial attribution through a proxy such as LiteLLM, and pitfalls)

### Takeaway
LiteLLM gives a per-response `x-litellm-response-cost` header plus a spend-log row keyed by hashed API key, `end_user`, `request_tags` and `spend_logs_metadata`, which is enough to tag each trial and separate judge from agent spend if the platform sets those fields on every call. Known pitfalls: cached tokens priced differently per provider and silently skipped below minimums; fallbacks recorded in metadata but retry billing not documented; aggregator rows capped at 10k; zero-cost rows when pricing is missing; prompt caching changes cost/latency but not outputs.

### Cited Findings
- LiteLLM returns cost "in the response headers with calculated cost" (`x-litellm-response-cost`); `LiteLLM_SpendLogs` rows carry hashed `api_key`, `user`, `team_id`, `end_user`, `request_tags`, `model_group`, `api_base`, `spend`, `prompt_tokens`, `completion_tokens`, `total_tokens`, `metadata.attempted_fallbacks`, `metadata.original_model_group`; tags via key/team metadata, request `metadata.tags`, `x-litellm-tags` header or config; `spend_logs_metadata` via request metadata or `x-litellm-spend-logs-metadata` header; User-Agent added as a tag by default. — [LiteLLM: Cost tracking](https://docs.litellm.ai/docs/proxy/cost_tracking)
- Pitfalls documented by LiteLLM: `/spend/logs` legacy truncates to 10,000 rows (`x-litellm-spend-logs-truncated: true`), `/spend/logs/v2` caps `total` at 10,000; a request pricing to $0 on a non-free model is logged with `spend = 0` plus a warning and a Prometheus counter; "Daily activity request counts record each upstream attempt separately" but the page does not say whether retried attempts are billed; end users can omit the `user` field to avoid tracking, so set `user_id` on keys. — [LiteLLM: Cost tracking](https://docs.litellm.ai/docs/proxy/cost_tracking)
- Cached-token pricing in LiteLLM: `cache_creation_input_token_cost`, `cache_creation_input_token_cost_above_12hr` (OpenAI 12-hour writes 2.5x), `cache_read_input_token_cost`; "Cost cache-hit prompt tokens can differ from cache-miss prompt tokens"; caching "silently skipped" below provider minimums; Bedrock Mantle uses a different usage shape. — [LiteLLM: Prompt caching](https://docs.litellm.ai/docs/completion/prompt_caching)
- Anthropic usage: `total_input_tokens = cache_read_input_tokens + cache_creation_input_tokens + input_tokens`, where `input_tokens` is only tokens "after the last cache breakpoint"; writes 1.25x/2x, reads 0.1x (or 0.025x/0.05x on newer models). — [Anthropic: Prompt caching](https://platform.claude.com/docs/en/docs/build-with-claude/prompt-caching)
- Inspect separates `input_tokens` (full-rate), `input_tokens_cache_write`, `input_tokens_cache_read`, `reasoning_tokens` in `ModelUsage`. — [Inspect reference: model](https://inspect.aisi.org.uk/reference/inspect_ai.model.html)
- Weave auto-costs only for OpenAI/Anthropic/Cohere/Mistral and only when usage is in the response; custom `add_cost` otherwise; no cached-token pricing documented. — [Weave: Costs](https://docs.coreweave.com/weave/guides/tracking/costs)
- LangSmith experiment view shows "cost, token counts, latency and status" and per-metadata-group averages. — [LangSmith: Analyze an experiment](https://docs.langchain.com/langsmith/analyze-an-experiment.md)
- Harbor records per-trial cost, tokens and timing in the viewer and in ATIF `final_metrics`/per-step `metrics`. — [Harbor: View job results](https://docs.harborframework.com/results/view-job-results.md); [Harbor: ATIF](https://docs.harborframework.com/agents/atif.md)
- Vivaria enforces `max_tokens`, `max_actions`, `max_total_seconds`, `max_cost` per run, with cost currency "depends on the Vivaria installation." — [viv CLI reference](https://vivaria.metr.org/reference/cli/)
- HAL: harness "automatically tracks token usage and cost" via LiteLLM + Weave; "Dollar-cost and token-count Pareto curves tell different stories" (Claude Opus 4.1 on token frontier 3/8 but cost frontier 1); average cost per evaluation $13 (ScienceAgentBench) to >$450 (Online Mind2Web); Browser-Use + Claude Sonnet 4 cost $1,577 vs SeeAct + GPT-5 Medium $171 for ~2 points; "latency measurements may be inflated by rate-limit errors from massively parallel runs." — [HAL paper](https://arxiv.org/html/2510.11977)
- "AI Agents That Matter" (Jul 2024): "a narrow focus on accuracy without attention to other metrics" yields "unnecessarily complex and costly" agents; proposes "jointly optimizing the two metrics." — [arXiv 2407.01502](https://arxiv.org/abs/2407.01502)
- (secondary) a LiteLLM-based service documents that response-cache hits show cost 0 and are logged as separate spend rows with a `_cache_hit<timestamp>` suffix on the original id. — [Zeabur AI Hub docs](https://zeabur.com/docs/en-US/ai-hub/usage-and-cost). A LiteLLM issue (v1.49.3) reported `cache_hit` always 0 despite cached tokens in the API response. — [BerriAI/litellm#6229](https://github.com/BerriAI/litellm/issues/6229)

### Inferences
- To attribute cost per trial and keep judge cost separate: issue distinct virtual keys or at minimum distinct `metadata.tags` (e.g. `trial:<id>`, `role:agent|judge`) on every call, and store the per-call `x-litellm-response-cost` plus usage object in the trial record rather than relying on `/spend/logs` aggregates, which are capped and summarized.
- Retries are a double-count risk at two layers: the harness's own retries and LiteLLM's retries/fallbacks. Since LiteLLM's docs record fallbacks in metadata but do not state retry billing, the platform should count what the provider's usage object says per attempt and record attempt counts explicitly.
- Latency comparisons across configs are confounded by cache hit rate, rate-limit backoff and parallelism (HAL's note); report latency alongside cache-read fraction and retry count.

### Gaps
- LiteLLM's official docs do not state how `response_cost` is set on a response-cache hit, whether retried upstream attempts are each billed in spend logs, or how streaming affects cost rows.
- No platform doc fetched describes separating judge/grader token usage from agent usage in its aggregates (Inspect's scorer page defers to a "Model Grading" page not fetched).

## Key question 6: Partial failures (infrastructure vs agent failures; resume without duplicating or losing trials)

### Takeaway
Harbor is the only surveyed platform with a published, exhaustive failure taxonomy that decides per class whether a reward is valid, whether to retry and whether to grade; Inspect handles this with `fail_on_error` thresholds, per-sample `error`/limit fields and an `eval_set` resume keyed on stable sample IDs and a durable log directory. Commercial tools mostly expose an error flag per row and leave classification and resumption to the user.

### Cited Findings
- Harbor error classification: "A trial with no error always has a valid reward." Classes: `agent_exhausted_budget` (`AgentTimeoutError`, `ContextWindowExceededError`, `OutputTokenExceededError`...) reward valid, not retried, graded; `agent_refused_task` (`AgentSafetyRefusalError`, `ContentPolicyViolationError`) reward valid, not retried, graded; `sandbox_failed` (`EnvironmentStartTimeoutError`, `SandboxBuildFailedError`, `AgentSetupTimeoutError`, `HealthcheckError`, `SandboxLikelyOutOfMemoryError`...) reward invalid, retried, not graded; `model_provider_failed` retryable (`ApiRateLimitError`, `ApiOverloadedError`, `ServiceUnavailableError`, `Timeout`...) reward invalid, retried, graded; non-retryable request errors (`BadRequestError`, `BudgetExceededError`) not retried, graded; auth/access (`AuthenticationError`, `ModelNotFoundError`) neither retried nor graded; `verifier_failed` (`VerifierTimeoutError`, `RewardFileNotFoundError`, `VerifierOutputParseError`) invalid, not retried, graded; `unclassified` (`NonZeroAgentExitCodeError`) invalid, retried, graded; `cancelled`. `TrialResult` exposes `exception_info.exception_type`, `failure_cause`, `reward_valid`. Overrides via `retry.include_exceptions` / `retry.exclude_exceptions`. — [Harbor: Error classification](https://docs.harborframework.com/jobs/error-classification.md)
- Harbor retry config: `max_retries` default 0, `wait_multiplier` 1.0, `min_wait_sec` 1.0, `max_wait_sec` 60.0; "Exclusions take precedence over inclusions." Hub "pauses on cascading failures (such as usage limits), and backs off on rate limits." — [Harbor: Configs](https://docs.harborframework.com/jobs/configs.md); [Harbor: Run a job](https://docs.harborframework.com/jobs/run-a-job.md)
- Harbor regrade: "Rerunning an updated verifier on recorded outputs without rerunning the agent" via `source_jobs`. — [Harbor docs index](https://docs.harborframework.com/llms.txt); [Harbor: Configs](https://docs.harborframework.com/jobs/configs.md)
- Inspect `fail_on_error`: `True` default stops on first sample error; `False` never stops; fraction or integer thresholds; custom limits via `SampleLimitExceededError`. — [Inspect: Errors and Limits](https://inspect.aisi.org.uk/errors-and-limits.html) (search snippet; page fetch returned "Redirect")
- Inspect resume: log directory is "a durable record of which tasks are completed"; re-running schedules "any work not yet completed"; completed samples re-used only with stable IDs, with a warning on `dataset.shuffle()` but not on other shuffles; `max_samples` affects recoverability ("Smaller values write completed samples more often"); failed logs cleaned up after success unless `--no-retry-cleanup`; `eval_retry()` "does not overwrite the previous log file" and keeps the original `task_id`; EvalLog `status` is "started" | "success" | "error" with `error` traceback. — [Inspect: Eval Sets](https://inspect.aisi.org.uk/eval-sets.html); [Inspect: Eval Logs](https://inspect.aisi.org.uk/eval-logs.html)
- Inspect sandbox `exec()` "truncates output silently" on overflow: "Don't rely on an exception to detect exec() overflow." — [Inspect: Sandboxing](https://inspect.aisi.org.uk/sandboxing.html)
- Terminal-Bench classifies trajectory failures as Execution, Coherence, Verification; command error rate 9.2% (Grok 4) to 26.7% (GPT-OSS-120B), most common cause "Executables not installed or not in PATH" (24.1% of failures); a timeout-rate heatmap (Fig. 12) is reported. — [Terminal-Bench paper](https://arxiv.org/html/2601.11868)
- HAL: "Scaffolds can fail silently, which can understate performance. The authors modified scaffolds to prevent failures"; tool-calling errors "nearly universal" on SciCode and CORE-Bench; ~40% of failed tasks on three benchmarks had environmental barriers. — [HAL paper](https://arxiv.org/html/2510.11977)
- Vivaria trace entries record "an error" among event types; `checkpoint_*` options pause a run for human input; glossary has no run-state list. — [Vivaria: Glossary](https://vivaria.metr.org/glossary/); [viv CLI reference](https://vivaria.metr.org/reference/cli/)
- DeepEval `ErrorConfig` (`ignoreErrors`, `skipOnMissingParams`); Arize AX `exit_on_error=False` then inspect the DataFrame; LangSmith shows a status column; promptfoo retries 429 with backoff and stores no error responses in cache. — [DeepEval](https://deepeval.com/docs/evaluation-introduction); [Arize AX](https://phoenix.arize.com/docs/ax/develop/datasets-and-experiments/run-experiment); [LangSmith: Analyze an experiment](https://docs.langchain.com/langsmith/analyze-an-experiment.md); [promptfoo: Caching](https://www.promptfoo.dev/docs/configuration/caching/)
- Statistical handling: Anthropic's error-bars post recommends treating questions as draws from a universe and reporting SEM/CI; paired differences for comparisons. (Nov 2024) — [Anthropic: Adding Error Bars to Evals](https://www.anthropic.com/research/statistical-approach-to-model-evals)

### Inferences
- Harbor's table is a ready template for this project's "infra failure vs agent failure" rule: budget exhaustion and refusals are agent outcomes (score them, usually 0); sandbox/provider/auth/harness errors are infra (reward invalid, retry a bounded number of times, never silently drop; report counts). Verifier failures are a third class that must be surfaced, not folded into either.
- Idempotent resume needs a stable trial identity (config hash + task id + repeat index) written before the trial starts, as Inspect's stable-sample-ID requirement and Harbor's per-trial directory imply; otherwise a crash between "model call finished" and "result written" duplicates or loses a trial. Inspect's note about `max_samples` is a reminder that write frequency, not just identity, decides how much survives a crash.
- Because providers' rate-limit errors inflate latency (HAL) and are retried (Harbor), the trial record should carry attempt count and the class of the last error so latency and cost analyses can exclude or stratify infra-retried trials.

### Gaps
- Inspect's `retry_on_error`, `working_limit`, and whether a limit-terminated sample is scored could not be verified because the errors-and-limits page did not render through the fetch tool.
- Harbor's docs say whether a reward is "valid" but "the page doesn't say explicitly how invalid rewards are handled" in aggregate metrics (excluded vs counted as 0).
- Vivaria's run states and resume semantics were not found on the fetched pages (architecture, glossary, CLI).
- No documentation was found for how Braintrust, Weave or Phoenix resume an interrupted experiment without re-running completed rows.
