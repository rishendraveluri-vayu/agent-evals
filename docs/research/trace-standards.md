# Trace formats for carrying four harnesses' trajectories into one store (state as of 3 Nov 2026)

Scope: whether OpenTelemetry GenAI semantic conventions or OpenInference can carry traces from Hermes Agent, LangGraph, an agents SDK (Google ADK or OpenAI Agents SDK) and a plain tool-calling loop into a Postgres store behind a NestJS API with a Vue UI, with no observability vendor. Every finding carries its source. Findings dated before 2026 are marked. "Verified" means read from the primary document; "secondary" means a blog or vendor doc.

Research method note: the opentelemetry.io GenAI pages are now redirect stubs ("GenAI semantic conventions have moved to the OpenTelemetry GenAI semantic conventions repository", [opentelemetry.io](https://opentelemetry.io/docs/specs/semconv/gen-ai/)), so the primary source for the spec is the GitHub repo `open-telemetry/semantic-conventions-genai`, read from `main` on 3 Nov 2026.

---

## Key question 1: OpenTelemetry GenAI semantic conventions, status and model as of November 2026

### Takeaway
Every `gen_ai.*` span, attribute, event and metric is still at stability level **Development** (the only Stable attributes on a GenAI span are inherited `error.type`, `server.address`, `server.port`); the conventions moved to a dedicated repository on 12 Jun 2026 which has **no tagged release and a "TODO" schema URL**, and there were three Breaking changes in Aug 2025 alone. The model itself is now rich: inference, agent, workflow, tool, memory and skill spans exist, with message content captured as JSON on opt-in span attributes.

**Message content capture**
- Content is opt-in: "the environment variable MUST be named `OTEL_INSTRUMENTATION_GENAI_CAPTURE_CONTENT`", with values `NO_CONTENT` ("Do not capture content on spans or events. (Default)"), `SPAN_ONLY`, `EVENT_ONLY`, `SPAN_AND_EVENT`; parsed case-insensitively, unknown values fall back to `NO_CONTENT` — verified, [gen-ai-spans.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md). Note: the dash0 explainer gives the older name `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` "only as an example" ([dash0](https://www.dash0.com/knowledge/opentelemetry-genai-semantic-conventions-explained)); the ADK source still imports that older name ([adk tracing.py](https://github.com/google/adk-python/blob/main/src/google/adk/telemetry/tracing.py)). The spec text I read mandates `..._CAPTURE_CONTENT`.
- Message JSON: `gen_ai.input.messages` / `gen_ai.output.messages` are arrays of objects with `role` and `parts`; part types shown are `text` (`content`), `tool_call` (`id`, `name`, `arguments`), `tool_call_response` (`id`, `response`). "Instrumentations MUST follow these schemas": `/model/gen-ai/gen-ai-input-messages.json`, `gen-ai-output-messages.json`, `gen-ai-system-instructions.json`, `gen-ai-tool-definitions.json` — [client-inference.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/client-inference.md)
- Large content can be externalised: `gen_ai.input.messages_ref`, `gen_ai.output.messages_ref`, `gen_ai.system_instructions_ref`, `gen_ai.tool.definitions_ref` are "An absolute URI identifying" the content "in external storage"; presence of a `_ref` does not confirm the content was stored — same source
- Event: `gen_ai.client.inference.operation.details` (Development, Recommended) "describes a completion request's chat history and parameters", severity DEBUG; it is the event-side home for the same messages — same source. `gen-ai-events.md` itself now defines only `gen_ai.evaluation.result` (attributes `gen_ai.evaluation.name` Required, `gen_ai.evaluation.score.value`, `gen_ai.evaluation.score.label`, `gen_ai.evaluation.explanation`, `gen_ai.response.id`) — [gen-ai-events.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-events.md)

### Inferences
- The vocabulary (operation names, token attributes, message parts) has settled enough that a mapping to it is cheap, but no downstream consumer can rely on exact names for more than a few months without a compatibility layer: three Breaking renames landed in one 2025 release, span naming broke again in Apr 2026, and the repo move means every SDK constants package (`opentelemetry-semantic-conventions`) is now one step behind the spec.
- `gen_ai.evaluation.result` is directly useful to an evals platform (judge score, label, explanation keyed to `gen_ai.response.id`), but as an *event*, which most self-hosted stores handle worse than spans (see Q5).
- The `_ref` attributes are an explicit acknowledgment that full message payloads are too big for span attributes in many backends; a Postgres JSONB store does not have that problem, which weakens one argument for externalising.

### Gaps
- I could not obtain the per-attribute requirement table for the memory spans in `gen-ai-agent-spans.md` beyond what `gen-ai-spans.md` carries (see Q4); the agent-spans document is 141 KB and the summariser dropped the Memory section from both halves.
- No SIG meeting notes were retrievable; the "when will it stabilise" question has no primary-source answer. The secondary sources agree only that it is not stable and no date is published.
- I could not find a dated primary source for when `gen_ai.prompt`/`gen_ai.completion` or `gen_ai.usage.prompt_tokens`/`completion_tokens` were removed; they were already gone by v1.36.0 (the CHANGELOG window I read).

## Key question 2: OpenInference (Arize)

### Takeaway
OpenInference is a flat, dot-indexed attribute vocabulary on top of OTel spans, with a required `openinference.span.kind` (LLM, TOOL, AGENT, CHAIN, RETRIEVER, EMBEDDING, RERANKER, GUARDRAIL, EVALUATOR, PROMPT, DECISION). Arize calls it "Stable" with versioned breaking changes, it has the widest auto-instrumentation catalogue (including Google ADK and the OpenAI Agents SDK), and both Arize AX and Phoenix now normalise incoming `gen_ai.*` spans into it at ingest. It has no memory or skill concept.

### Cited Findings
- `openinference.span.kind` is required on all OpenInference spans; values: LLM, EMBEDDING, CHAIN, RETRIEVER, RERANKER, TOOL, AGENT, GUARDRAIL, EVALUATOR, PROMPT, DECISION — verified, [spec/semantic_conventions.md](https://github.com/Arize-ai/openinference/blob/main/spec/semantic_conventions.md)
- Generic I/O: `input.value`, `input.mime_type`, `output.value`, `output.mime_type`. Messages are flattened with indices: `llm.input_messages.{i}.message.role`, `llm.input_messages.{i}.message.content`, `llm.output_messages.{i}.message.tool_calls.{j}.tool_call.id`, `...tool_call.function.name`, `...tool_call.function.arguments` — same source
- Model and params: `llm.model_name`, `llm.provider`, `llm.system`, `llm.invocation_parameters` (JSON string), optional `llm.request.model_name` / `llm.response.model_name` — same source
- Tokens and cost: `llm.token_count.prompt`, `llm.token_count.completion`, `llm.token_count.total`, `llm.token_count.prompt_details.*`, `llm.token_count.completion_details.*`; `llm.cost.prompt`, `llm.cost.completion`, `llm.cost.total`, `llm.cost.prompt_details.*` (input, cache_read, cache_write, cache_input, audio), `llm.cost.completion_details.*` (output, reasoning, audio) — same source
- Tools: `llm.tools.{i}.tool.name` / `.tool.description` / `.tool.json_schema` (tools offered to the model); on TOOL spans `tool.name`, `tool.description`, `tool.parameters` (JSON string); `tool_call.id`, `tool_call.function.name`, `tool_call.function.arguments` — same source
- Retrieval, session, metadata: `retrieval.documents` (objects with `document.id`, `document.score`, `document.content`), `session.id`, `user.id`, `metadata` (JSON string), `tag.tags`, `agent.name`, `graph.node.id`, `graph.node.name`, `graph.node.parent_id` — same source
- The spec page states no stability level itself, only that reserved attributes "MUST be supported by all OpenInference Tracing SDKs" — same source. Arize's AX docs describe OpenInference as "Stable" with versioned breaking changes, and GenAI as "still in development; not on a stable release" — [Arize AX semantic conventions](https://arize.com/docs/ax/concepts/otel-openinference/semantic-conventions.md)
- README: OpenInference is "a set of conventions and plugins that is complementary to OpenTelemetry"; licence Apache-2.0; Python instrumentations include `openai`, `langchain`, `llama-index`, `dspy`, `bedrock`, `anthropic`, `google-genai`, `google-adk`, `openai-agents`, `pydantic-ai`, `crewai`, `autogen-agentchat`, `smolagents`, `claude-agent-sdk`, `strands-agents`, `mcp`, `litellm`, plus span processors `openlit` and `openllmetry` — verified, [openinference README](https://github.com/Arize-ai/openinference). `openinference-instrumentation-openai-agents` is on PyPI (release history shows 2.2.1) — [PyPI](https://pypi.org/project/openinference-instrumentation-openai-agents/)
- Relationship to OTel GenAI, ingest-side: Arize AX normalises any span carrying a `gen_ai.`-prefixed attribute into OpenInference; raw `gen_ai.*` preserved; existing OpenInference attributes win; unknown `gen_ai.operation.name` leaves span kind unset; "the two conventions are expected to converge as the GenAI spec stabilizes" — [Arize AX semantic conventions](https://arize.com/docs/ax/concepts/otel-openinference/semantic-conventions.md)
- Mapping table (Arize): `chat`/`text_completion`/`generate_content` → LLM; `embeddings` → EMBEDDING; `execute_tool` → TOOL; `retrieval` → RETRIEVER; `invoke_agent`/`create_agent` → AGENT; `invoke_workflow` → CHAIN; others unclassified. Attributes: `gen_ai.input.messages` → `llm.input_messages.*`; `gen_ai.output.messages` → `llm.output_messages.*`; `gen_ai.usage.input_tokens` → `llm.token_count.prompt`; `gen_ai.usage.output_tokens` → `llm.token_count.completion`; `gen_ai.request.model` → `llm.model_name`; `gen_ai.provider.name` (fallback `gen_ai.system`) → `llm.provider` and `llm.system`; `gen_ai.tool.name` → `tool.name`; `gen_ai.tool.call.arguments` → `tool.parameters` and `input.value`; `gen_ai.tool.call.result` → `output.value`; `gen_ai.conversation.id` → `session.id`. No mapping for `gen_ai.agent.name`, and memory operations are unmapped — [Arize AX span kinds](https://arize.com/docs/ax/concepts/otel-openinference/span-kinds.md)
- Phoenix (open source) does the same conversion from arize-phoenix 15.10.0 onward (release note dated 15 May 2026) — [Phoenix release note](https://arize.com/docs/phoenix/release-notes/05-2026/05-15-2026-otel-semconv-conversion)
- Independent comparison (26 Jun 2026): OpenInference has "first-class retrieval and re-ranking spans"; OTel GenAI "differentiates less between operation types" and is "still catching up on the expressiveness that LLM and agent workloads demand", but is "well-governed and on a path to becoming the broad ecosystem default". Recommends OTel GenAI for stack-wide standardisation and OpenInference for production agents today. Vendor-adjacent source (Arthur) — [arthur.ai](https://www.arthur.ai/column/openinference-vs-opentelemetry-genai-conventions-agent-tracing)
- The OpenInference LangChain instrumentor emits no `gen_ai.*` attributes at all; "the only OpenTelemetry semconv constants used are for exception attributes" — verified from source, [_tracer.py](https://github.com/Arize-ai/openinference/blob/main/python/instrumentation/openinference-instrumentation-langchain/src/openinference/instrumentation/langchain/_tracer.py)

### Inferences
- OpenInference's flattened `llm.input_messages.{i}.message.*` form is friendlier to a plain SQL store than a 100 KB JSON string in one attribute, but it also means a single LLM call can produce hundreds of attribute rows; a JSONB column holding the whole message list is the natural Postgres shape for either convention.
- Because Arize maps `gen_ai.*` → OpenInference losslessly for the common fields, a platform that stores either can round-trip to the other with a small table; the hard cases are exactly the agent-level concepts (memory, skills, handoffs) that OpenInference does not model.
- The "dual emission" claim found in one search summary ("recent OpenInference instrumentations emit both") was not confirmed by the OpenInference README or by the LangChain instrumentor source; treat it as unverified.

### Gaps
- No primary statement of OpenInference's own versioning policy for the spec was found (the "Stable" label comes from Arize product docs, not the spec repo).
- No neutral benchmark comparing the two conventions exists; all comparisons found are vendor-authored.

## Key question 3: Native instrumentation per framework

### Takeaway
All four candidate harnesses expose a complete LLM-call and tool-call tree through a native hook that can be redirected to our own code without an external vendor: LangGraph via LangChain's `BaseCallbackHandler`/`BaseTracer` (`run_id`/`parent_run_id` tree, `langgraph_node`/`langgraph_step` metadata), Google ADK via OpenTelemetry spans named to the GenAI conventions (`invoke_agent`, `execute_tool`, `generate_content`), the OpenAI Agents SDK via its own `TracingProcessor` (typed span data incl. `handoff`, `function`, `generation`), and Hermes via plugin hooks (`pre_llm_call`, `post_tool_call`, etc.) that two existing plugins already turn into OTel/Langfuse spans. None of the four traces memory reads/writes natively, and only ADK (and the Hermes community plugin) trace skills.

### Cited Findings

**LangChain / LangGraph**
- `BaseCallbackHandler` methods and parameters (verified from source): `on_llm_start(serialized, prompts, *, run_id, parent_run_id, tags, metadata)`, `on_chat_model_start(serialized, messages, *, run_id, parent_run_id, tags, metadata)`, `on_llm_new_token(token, *, chunk, run_id, parent_run_id, tags)`, `on_llm_end(response, *, run_id, parent_run_id, tags)`, `on_llm_error(error, ...)`, `on_chain_start(serialized, inputs, *, run_id, parent_run_id, tags, metadata)`, `on_chain_end(outputs, *, run_id, parent_run_id)`, `on_chain_error`, `on_tool_start(serialized, input_str, *, run_id, parent_run_id, tags, metadata, inputs)`, `on_tool_end(output, *, run_id, parent_run_id)`, `on_tool_error`, `on_text`, `on_retry(retry_state, ...)`, `on_agent_action(action, ...)`, `on_agent_finish(finish, ...)`, `on_retriever_start(serialized, query, ...)`, `on_retriever_end(documents, ...)`, `on_retriever_error`, `on_custom_event(name, data, *, run_id, tags, metadata)`. `on_chat_model_start` falls back to `on_llm_start` when it raises `NotImplementedError`. `ignore_llm`, `ignore_retry`, `ignore_chain`, `ignore_agent`, `ignore_retriever`, `ignore_chat_model`, `ignore_custom_event` default False — [callbacks/base.py](https://github.com/langchain-ai/langchain/blob/master/libs/core/langchain_core/callbacks/base.py)
- `BaseTracer` (a `BaseCallbackHandler`) builds `Run` objects and calls the abstract `_persist_run(self, run: Run)` only when a root run ends (`if not run.parent_run_id:`); hooks `_on_run_create(run)` and `_on_run_update(run)` fire per run; `Run` comes from `langchain_core.tracers.schemas` — verified, [tracers/base.py](https://github.com/langchain-ai/langchain/blob/master/libs/core/langchain_core/tracers/base.py)
- LangGraph attaches per-task metadata when it schedules a node: `"langgraph_step"`, `"langgraph_node"`, `"langgraph_triggers"`, `"langgraph_path"`, `"langgraph_checkpoint_ns"`, merged with the parent config via `merge_configs(...)`/`patch_config(...)`; callbacks for the task come from `manager.get_child(f"graph:step:{step}")`; node `tags` are also set — verified from source, [pregel/_algo.py](https://github.com/langchain-ai/langgraph/blob/main/libs/langgraph/langgraph/pregel/_algo.py). The LangGraph streaming docs show the same key surfacing to consumers: `metadata["langgraph_node"] == "some_node_name"` — [LangGraph streaming](https://docs.langchain.com/oss/python/langgraph/streaming). These keys are listed in `EXCLUDED_METADATA_KEYS` of the checkpoint base, i.e. runtime metadata kept out of persisted checkpoints — [reference](https://reference.langchain.com/python/langgraph.checkpoint/base/EXCLUDED_METADATA_KEYS)
- Custom events from inside a node: `get_stream_writer()` and `stream_mode="custom"`; `on_custom_event(name, data, ...)` exists on the callback interface — [LangGraph streaming](https://docs.langchain.com/oss/python/langgraph/streaming), [callbacks/base.py](https://github.com/langchain-ai/langchain/blob/master/libs/core/langchain_core/callbacks/base.py)
- Persistence (memory) APIs: checkpointers `InMemorySaver`, `SqliteSaver`, `PostgresSaver`/`AsyncPostgresSaver`; store `InMemoryStore` passed via `builder.compile(store=...)`; each subgraph "manages its own checkpoint namespace"; the page "says nothing about whether checkpointer or store operations are traced or appear in LangSmith or callbacks" — [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence). ## Key question 4: Do the standards represent memory, skills, and the rendered system prompt?

### Takeaway
OTel GenAI now does model all three on paper: memory spans (`create_memory`, `search_memory`, `upsert_memory`, … with `gen_ai.memory.store.id`, `gen_ai.memory.record.id`, opt-in `gen_ai.memory.query.text`/`gen_ai.memory.records`), skill spans as `execute_tool` refinements (`gen_ai.skill.name`, `gen_ai.skill.description`, `gen_ai.skill.source.uri`, `gen_ai.skill.resource.name`) and the rendered system prompt as opt-in `gen_ai.system_instructions`. All of it is Development-status, and no framework or backend I checked emits or understands the memory and skill attributes except Google ADK's skill tracing. OpenInference has none of the three; its nearest tools are `PROMPT` spans and `metadata`.

### Cited Findings
- Memory spans (verified): span name SHOULD be `{gen_ai.operation.name}`; kind SHOULD be `CLIENT`, MAY be `INTERNAL`; operations `create_memory_store`, `search_memory`, `create_memory`, `update_memory`, `upsert_memory`, `delete_memory`, `delete_memory_store`. Attributes: `gen_ai.operation.name` Required; `error.type` Conditionally Required (Stable); `gen_ai.memory.record.id` Conditionally Required "when the operation applies to a specific record"; `gen_ai.memory.store.id` Conditionally Required if applicable; `gen_ai.provider.name` Conditionally Required "if handled by a named external provider or service"; `gen_ai.memory.record.count` Recommended; `server.address`/`server.port`; **Opt-In** `gen_ai.memory.query.text` and `gen_ai.memory.records`. All Development — [gen-ai-spans.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md). (Note: the dash0 explainer's attribute names differ slightly from the spec text I read; the spec names above are the ones to use.)
- Skill spans (verified): three refinements of the execute-tool span, all INTERNAL, Development, Recommended: load skill (`gen_ai.execute_tool.load_skill.internal`, name `execute_tool {gen_ai.tool.name} {gen_ai.skill.name}`), read skill resource (`...read_skill_resource.internal`, name adds `{gen_ai.skill.resource.name}`), command execution (`...command.internal`, may use `process.executable.name`, `process.exit.code`, `process.executable.path`). Attributes: Required `gen_ai.operation.name`, `gen_ai.tool.name`; Conditionally Required `gen_ai.skill.name`, `gen_ai.skill.resource.name`, `gen_ai.tool.call.id`, `gen_ai.agent.name`, `gen_ai.conversation.id`, `error.type`; Recommended `gen_ai.skill.description`, `gen_ai.skill.source.uri`, `gen_ai.tool.description`, `gen_ai.tool.type`; Opt-In `gen_ai.tool.call.arguments`, `gen_ai.tool.call.result`. "`gen_ai.skill.description` and `gen_ai.skill.source.uri` may contain sensitive information" — [gen-ai-agent-spans.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)
- Rendered system prompt: `gen_ai.system_instructions` is Opt-In on inference spans, on `create_agent` and on `invoke_agent`; with `gen_ai.system_instructions_ref` for external storage; its JSON schema is `/model/gen-ai/gen-ai-system-instructions.json` — [client-inference.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/client-inference.md), [gen-ai-agent-spans.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)
- Memory and skills were not in the main-repo CHANGELOG for v1.36.0–v1.42.0 ("Not found ... memory operations") — [CHANGELOG](https://github.com/open-telemetry/semantic-conventions/blob/main/CHANGELOG.md); they appear only in the dedicated repo's `main`, which has no release — [repo](https://github.com/open-telemetry/semantic-conventions-genai)
- OpenInference: span kinds are LLM, EMBEDDING, CHAIN, RETRIEVER, RERANKER, TOOL, AGENT, GUARDRAIL, EVALUATOR, PROMPT, DECISION; no memory or skill attribute exists; system prompt is just an `llm.input_messages.{i}.message.role = "system"` entry; free-form `metadata` is a JSON string — [spec/semantic_conventions.md](https://github.com/Arize-ai/openinference/blob/main/spec/semantic_conventions.md). Arize's GenAI→OpenInference mapping leaves memory operations unclassified ("Any other value → Unclassified (span kind left unset)") — [Arize span kinds](https://arize.com/docs/ax/concepts/otel-openinference/span-kinds.md)
- Framework emitters: ADK sets `gen_ai.skill.*` and traces skill load/resource/script spans but not memory — [adk tracing.py](https://github.com/google/adk-python/blob/main/src/google/adk/telemetry/tracing.py); the Hermes community plugin emits `skill.{name}` CHAIN spans (its own naming) and no memory spans — [hermes-otel](https://github.com/briancaffey/hermes-otel); OpenAI Agents SDK sessions and LangGraph store/checkpointer have no documented tracing (Q3)
- Backends: Langfuse reads `gen_ai.tool.call.arguments`/`result`, `gen_ai.usage.*`, `gen_ai.request.model` but its documented attribute list has no `gen_ai.memory.*` or `gen_ai.skill.*`, and no `gen_ai.input.messages` — [Langfuse OTel docs](https://langfuse.com/docs/opentelemetry/get-started)

### Inferences
- "Standard covers memory and skills" is true of the *spec text* and false of the *ecosystem*: as of Nov 2026 nothing else emits or renders them. Adopting the spec's names for memory and skills therefore buys naming hygiene and interview recognisability, not interoperability.
- Custom attributes still needed under either standard, because the spec does not define them: memory **operation payload shape** beyond opt-in `gen_ai.memory.records` (e.g. which keys were read vs written, namespace/thread scoping, hit/miss); the **diff of state** for LangGraph checkpoints; **which skill text was injected into the prompt** (the spec records the skill's name/uri, not the rendered contribution); **trial/experiment identity** (trial id, condition, seed, harness name/version), which neither standard has and which an evals platform needs on every span; **cost**, which OTel GenAI does not define (OpenInference has `llm.cost.*`).
- Using the spec's `gen_ai.memory.*` and `gen_ai.skill.*` names as *our* names, inside our own schema, is low-risk: they are the only candidate names likely to persist, and a rename would be a one-line adapter change rather than a spec break.

### Gaps
- Exact requirement table for memory attributes in `gen-ai-agent-spans.md` (vs `gen-ai-spans.md`) was not read; the two documents may differ in detail.
- No source found for how the spec intends LangGraph-style **state checkpoints** (not key-value memory) to be modelled; `invoke_workflow` plus custom attributes is my reading, not the spec's.

## Key question 5: Collection without a vendor

### Takeaway
No collector is needed. Python can export spans to Postgres three ways with the components already in the stack: an in-process `SpanExporter` subclass that writes rows directly; an OTLP/HTTP **JSON** POST to a NestJS route (`/v1/traces`, `Content-Type: application/json`, hex ids, stringified 64-bit ints) that the API persists; or a framework-native processor (LangChain `BaseTracer`, OpenAI `TracingProcessor`, Hermes hook) that emits our own JSON tree over HTTP. Of the ready-made stores, Phoenix runs on plain Postgres (`PHOENIX_SQL_DATABASE_URL`), Langfuse needs Postgres + ClickHouse + Redis + S3, Logfire self-hosted is enterprise-only, MLflow runs on Postgres but is tuned for offline use.

### Cited Findings
- OTel Python `SpanExporter`: `export(spans: Sequence[ReadableSpan]) -> SpanExportResult` (`SUCCESS=0`, `FAILURE=1`), `shutdown()`, `force_flush(timeout_millis=30000)`; `SimpleSpanProcessor` runs `on_end` synchronously on the calling thread; `BatchSpanProcessor` batches with `OTEL_BSP_SCHEDULE_DELAY`, `OTEL_BSP_MAX_QUEUE_SIZE`, `OTEL_BSP_MAX_EXPORT_BATCH_SIZE`, `OTEL_BSP_EXPORT_TIMEOUT`; `ConsoleSpanExporter` as a reference implementation — [OTel Python SDK](https://opentelemetry-python.readthedocs.io/en/latest/sdk/trace.export.html)
- OTLP is Stable for traces; OTLP/HTTP carries Protobuf in binary or **JSON** encoding via HTTP POST; default path `/v1/traces`, ports 4317 (gRPC) / 4318 (HTTP); JSON rules: `traceId`/`spanId` as hex strings, enums as integers, lowerCamelCase keys, 64-bit ints (incl. timestamps) as decimal strings, receivers must ignore unknown fields; `Content-Type: application/json` or `application/x-protobuf`; success = HTTP 200 with `ExportTraceServiceResponse` (`partial_success` unset), partial = 200 with `rejected_spans`/`error_message` (client must not retry), retryable codes 429/502/503/504, 400 = bad data, no retry — [OTLP spec](https://opentelemetry.io/docs/specs/otlp/)
- A NestJS receiver therefore needs: a POST route at `/v1/traces` accepting JSON, response `{}` with 200, and 429/503 on backpressure. I found no off-the-shelf Node "OTLP receiver" library; search results only showed Express handlers decoding protobuf with `@opentelemetry/otlp-transformer`'s `ExportTraceServiceRequest`, and the JSON case needs no decoder beyond `express.json()` — search summary, unverified beyond the OTLP spec above
- OpenAI Agents SDK: `TracingExporter.export(items: list[Trace | Span[Any]])` is the equivalent in-process hook; the docs recommend `set_trace_processors()` with an application-owned exporter wrapped in `BatchTraceProcessor` for redaction before export — [tracing docs](https://openai.github.io/openai-agents-python/tracing/), [processor_interface](https://openai.github.io/openai-agents-python/ref/tracing/processor_interface/)
- LangChain: `BaseTracer._persist_run(run)` fires once per root run with the whole `Run` tree — [tracers/base.py](https://github.com/langchain-ai/langchain/blob/master/libs/core/langchain_core/tracers/base.py)

**Langfuse (v4)**
- Required components: Langfuse Web, Langfuse Worker, PostgreSQL (transactional), ClickHouse (observability data), Redis/Valkey (cache and queue), S3/Blob storage (raw events, media) — [Langfuse self-hosting](https://langfuse.com/self-hosting); traces/observations/scores were moved from Postgres to ClickHouse in v3 because "Row-based storage in PostgreSQL becomes increasingly inefficient at billions of rows" — [v2→v3 guide](https://langfuse.com/self-hosting/upgrade-guides/upgrade-v2-to-v3)
- Core is MIT with "no usage limits"; `/ee` features (SCIM, audit logging, data retention policies, org creators, instance management API, UI customisation) need a licence key — [Langfuse open source](https://langfuse.com/docs/open-source), [self-hosting](https://langfuse.com/self-hosting)
- OTLP ingest at `/api/public/otel` (traces at `/api/public/otel/v1/traces`), OTLP/HTTP with JSON or protobuf, **gRPC not supported**, HTTP Basic auth `base64(public_key:secret_key)`, header `x-langfuse-ingestion-version=4` recommended (else up to 10 min delay). Maps `gen_ai.*`, OpenInference (`input.value`, `output.value`, `llm.model_name`, `llm.token_count.*`), MLflow (`mlflow.spanInputs/Outputs`), and its own `langfuse.observation.type` (`span`, `generation`, `event`, `embedding`, `agent`, `tool`, `chain`, `retriever`, `guardrail`, `evaluator`), `langfuse.observation.input/output`, `langfuse.session.id`, `langfuse.user.id`, `langfuse.trace.name`; filtering fields must be on every span (use Baggage); keys containing `__proto__`/`constructor`/`prototype` silently dropped — [Langfuse OTel docs](https://langfuse.com/docs/opentelemetry/get-started)

**Arize Phoenix**
- Default is "a file-based SQLite database in a temporary folder"; Postgres via `PHOENIX_SQL_DATABASE_URL` (`postgresql://user:password@host/dbname`) or `PHOENIX_POSTGRES_HOST/PORT/USER/PASSWORD/DB`; optional `PHOENIX_SQL_DATABASE_SCHEMA`; `PHOENIX_WORKING_DIR` default `~/.phoenix/` — [Phoenix persistence](https://arize.com/docs/phoenix/deployment/persistence). Docker image `arizephoenix/phoenix`, Helm chart `arizephoenix/phoenix-helm`, "free to self-host with no feature limitations", auth via OAuth2/LDAP/local — [Phoenix self-hosting](https://arize.com/docs/phoenix/self-hosting). Licence: Elastic License 2.0 per third-party deployment templates (unverified against the Phoenix licence page; the self-hosting page links to it without naming it)
- Phoenix converts incoming `gen_ai.*` to OpenInference at ingest from 15.10.0 (15 May 2026) — [release note](https://arize.com/docs/phoenix/release-notes/05-2026/05-15-2026-otel-semconv-conversion)
- Ports 6006 (UI + OTLP/HTTP) and 4317 (gRPC), path `/v1/traces` — from third-party Railway templates (search summary), not verified against Phoenix docs

**Pydantic Logfire**
- SDKs are open source and export to any OTel backend; "The Logfire platform (the UI and backend) is closed source. You can self-host it by purchasing an enterprise license"; Helm chart requires Kubernetes 1.32+ and PostgreSQL 16 plus object storage, with private container images — [Logfire FAQ](https://pydantic.dev/docs/logfire/get-started/faq/), [self-hosted overview](https://logfire.pydantic.dev/docs/reference/self-hosted/overview), [helm chart](https://github.com/pydantic/logfire-helm-chart)

**MLflow (for completeness)**
- Self-hosted tracking server with a PostgreSQL `--backend-store-uri`; "optimized for offline use and is generally not suited to very high traffic"; setting `OTEL_EXPORTER_OTLP_ENDPOINT` on the client diverts traces away from MLflow — [MLflow tracking server](https://mlflow.org/docs/latest/self-hosting/architecture/tracking-server/), [MLflow production](https://mlflow.org/docs/3.0.1/tracing/production). A `/v1/traces` OTLP endpoint on the server was described only by a third-party template (unverified)

### Inferences
- Phoenix is the only turnkey store that fits "Postgres only": one container plus our existing database. But it stores OpenInference, has its own UI and auth, and would sit beside, not inside, the NestJS API, so the Vue UI would either embed Phoenix or read Phoenix's tables, which are not a public contract.
- Langfuse's four-service footprint (ClickHouse, Redis, S3) is the opposite of the brief's "Postgres by a NestJS API"; its value would be the UI and the ability to ingest all four harnesses via OTLP/JSON with mixed conventions.
- Writing our own: a Python `SpanExporter` (or `TracingProcessor`/`BaseTracer`) that POSTs OTLP/JSON to NestJS is roughly 50–100 lines per harness; the NestJS side is one controller and two tables (trace, span with JSONB attributes). The hard part is not transport but *what to put in the attributes*, which is Q4.
- Events: OTLP JSON carries span events inline, so `gen_ai.client.inference.operation.details` and `gen_ai.evaluation.result` would simply land in a `span.events` JSONB column; Langfuse's docs do not say whether it keeps span events, so a judge-score-as-event design is safer with our own store.

### Gaps
- No primary source for a Node OTLP/JSON receiver library; building one by hand against the spec is the verified route.
- Phoenix's internal span table schema and licence name were not read from primary docs.
- Per-trace write throughput of Postgres for span rows at this project's scale was not researched; Langfuse's "billions of rows" justification is far beyond an evals platform's volume, which is an inference not a measurement.

## Key question 6: Trade-offs: adopt OTel GenAI or OpenInference, or own JSON schema with adapters

### Takeaway
The evidence separates two decisions that are often conflated: the **transport/envelope** (OTLP span tree versus our own JSON tree) and the **vocabulary** (which attribute names). Adopting OTLP as envelope is cheap, stable (OTLP traces are Stable) and recognisable; adopting `gen_ai.*` as the *only* vocabulary is risky because it is Development with a documented history of breaking renames and because no emitter yet produces the memory/skill attributes; OpenInference is more stable and better instrumented but structurally cannot express memory and skills. An own schema is the smallest surface to explain and control, at the cost of writing four adapters and getting no interop for free.

### Cited Findings
- Adoption effort evidence: OpenInference has instrumentors for LangChain (works with LangGraph), Google ADK and the OpenAI Agents SDK, and the Hermes community plugin emits OpenInference — [openinference README](https://github.com/Arize-ai/openinference), [Phoenix LangGraph](https://arize.com/docs/phoenix/integrations/python/langgraph/langgraph-tracing), [hermes-otel](https://github.com/briancaffey/hermes-otel). ADK emits `gen_ai.*` natively and the Hermes plugins also emit `gen_ai.*` — [adk.dev traces](https://adk.dev/observability/traces/), [hermes-otel](https://github.com/briancaffey/hermes-otel). LangSmith's OTel export emits old-generation `gen_ai.prompt`/`gen_ai.system` names — [LangSmith OTel docs](https://docs.langchain.com/langsmith/trace-with-opentelemetry)
- Schema stability evidence: OTel GenAI Development everywhere, Breaking renames in v1.37.0 (Aug 2025) and v1.41.0 (Apr 2026), no release of the new repo — Q1 sources. OpenInference described by Arize as Stable with versioned breaking changes — [Arize semantic conventions](https://arize.com/docs/ax/concepts/otel-openinference/semantic-conventions.md). OTLP itself is Stable — [OTLP spec](https://opentelemetry.io/docs/specs/otlp/)
- Information-loss evidence per existing instrumentor: OpenInference LangChain tracer keeps only the first input-message set, drops `langgraph_node`/`langgraph_step`, sets no `user.id`/tags — [_tracer.py](https://github.com/Arize-ai/openinference/blob/main/python/instrumentation/openinference-instrumentation-langchain/src/openinference/instrumentation/langchain/_tracer.py); OpenAI SDK `TaskSpanData`/`TurnSpanData` drop `metadata` on export — [span_data](https://openai.github.io/openai-agents-python/ref/tracing/span_data/); OpenAI SDK sessions and LangGraph store are not traced — Q3
- Convergence evidence: Arize and Phoenix both normalise `gen_ai.*` → OpenInference and expect convergence "as the GenAI spec stabilizes" — [Arize](https://arize.com/docs/ax/concepts/otel-openinference/semantic-conventions.md), [Phoenix release note](https://arize.com/docs/phoenix/release-notes/05-2026/05-15-2026-otel-semconv-conversion); Langfuse maps both plus its own — [Langfuse OTel](https://langfuse.com/docs/opentelemetry/get-started)
- Recognisability evidence: OTel GenAI is "on a path to becoming the broad ecosystem default" (Arthur, Jun 2026) — [arthur.ai](https://www.arthur.ai/column/openinference-vs-opentelemetry-genai-conventions-agent-tracing); the GenAI span names `invoke_agent`/`execute_tool`/`chat` are what ADK, the Hermes traceverse plugin and the spec all use — Q3 sources
- Coverage of memory/skills: spec yes (Development), OpenInference no, emitters almost none — Q4 sources

### Inferences (trade-off matrix)
- **Option 1: Adopt OTel GenAI end-to-end (OTLP envelope + `gen_ai.*` vocabulary).** Effort: low for ADK and Hermes (native `gen_ai.*`), medium for LangGraph (write a `BaseTracer` that emits `gen_ai.*`, because neither OTel path emits current names), medium for OpenAI SDK (a `TracingProcessor` → OTel spans; or OpenInference instrumentor then map). Stability: lowest; expect a names migration within 12 months and pin a schema version per trial. Debuggability: good tooling (any OTLP viewer), but attribute JSON strings for messages. Interviewer recognition: highest. Memory/skills: covered by spec names but we author every emitter ourselves.
- **Option 2: Adopt OpenInference (OTLP envelope + `openinference.span.kind` + `llm.*`).** Effort: lowest for LangGraph/ADK/OpenAI SDK via existing instrumentors, and Phoenix gives a UI on Postgres for free. Stability: better than GenAI. Debuggability: Phoenix is purpose-built. Recognition: good (Arize ecosystem), less "standard". Memory/skills: not modelled; would need `metadata` JSON or custom `gen_ai.memory.*`/`gen_ai.skill.*` attributes alongside, which Phoenix would ignore. Also inherits each instrumentor's information loss (first input-message set only, no graph node ids).
- **Option 3: Own small JSON trace schema, with adapters, OTLP-compatible envelope.** Effort: four adapters (LangChain `BaseTracer`, OpenAI `TracingProcessor`, ADK `SpanExporter`, Hermes plugin), each ~100 lines, plus a NestJS `/v1/traces` controller. Stability: fully under our control; can mirror `gen_ai.*` names as a *projection* so a future export to any OTLP backend is a mapping table. Debuggability: the Vue UI shows exactly the fields we define (messages, memory diffs, skills, trial id). Recognition: lower unless the design states explicitly which spec concepts it mirrors. Memory/skills: defined by us, with the spec's names reused where they exist.
- A hybrid is natural: use OTLP/JSON as the wire format and Postgres `span(attributes JSONB, events JSONB)` as the store (Option 3's control), name attributes after `gen_ai.*` where the spec has a name and `evals.*` (or similar) where it does not (Option 1's recognisability), and keep the Phoenix/Langfuse ingest paths as an optional sink because both accept `gen_ai.*` anyway.

### Gaps
- No effort measurement exists; "~100 lines per adapter" is an estimate from the interface sizes read, not from an implementation.
- I found no practitioner write-up specifically about evaluating memory/skill tracing across frameworks; the comparisons found focus on LLM calls and RAG.

## Key question 7: Options for the architect (evidence-weighted, not a decision)

### Takeaway
Three concrete options follow from the evidence. The evidence favours **Option C (own minimal schema on an OTLP-compatible envelope, attribute names borrowed from `gen_ai.*`)** for this platform's requirements (memory, skills, trial identity, Postgres-only, single Vue UI), with **Option B (OpenInference + Phoenix)** as the fastest-to-demo alternative and **Option A (pure OTel GenAI)** the most recognisable but the most exposed to spec churn. Rishi decides.

### Cited Findings (option definitions rest on the sources already cited; repeated here where load-bearing)
- Option A, pure OTel GenAI: ADK already emits it ([adk.dev traces](https://adk.dev/observability/traces/)); Hermes plugins emit it ([hermes-otel](https://github.com/briancaffey/hermes-otel)); spec has memory/skill spans ([gen-ai-spans.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md), [gen-ai-agent-spans.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)); all Development, no release, Breaking changes Aug 2025/Apr 2026/Jun 2026 ([CHANGELOG](https://github.com/open-telemetry/semantic-conventions/blob/main/CHANGELOG.md), [tags](https://github.com/open-telemetry/semantic-conventions/tags))
- Option B, OpenInference + Phoenix on Postgres: instrumentors for all three frameworks ([openinference README](https://github.com/Arize-ai/openinference)); Phoenix on `PHOENIX_SQL_DATABASE_URL` ([persistence](https://arize.com/docs/phoenix/deployment/persistence)); Phoenix also ingests `gen_ai.*` ([release note](https://arize.com/docs/phoenix/release-notes/05-2026/05-15-2026-otel-semconv-conversion)); no memory/skill concepts ([spec](https://github.com/Arize-ai/openinference/blob/main/spec/semantic_conventions.md)); LangChain instrumentor information loss ([_tracer.py](https://github.com/Arize-ai/openinference/blob/main/python/instrumentation/openinference-instrumentation-langchain/src/openinference/instrumentation/langchain/_tracer.py))
- Option C, own schema: hooks exist in every harness ([callbacks/base.py](https://github.com/langchain-ai/langchain/blob/master/libs/core/langchain_core/callbacks/base.py), [processor_interface](https://openai.github.io/openai-agents-python/ref/tracing/processor_interface/), [OTel SpanExporter](https://opentelemetry-python.readthedocs.io/en/latest/sdk/trace.export.html), [Hermes hooks](https://hermes-agent.nousresearch.com/docs/plugins/hermes_otel)); OTLP/JSON is a Stable, documented envelope a NestJS route can accept ([OTLP spec](https://opentelemetry.io/docs/specs/otlp/))

### Inferences
- **Option A: OTel GenAI as the schema.** Cost: author `gen_ai.*` emitters for LangGraph (BaseTracer) and OpenAI SDK (TracingProcessor); reuse ADK's and Hermes' native output but normalise `gen_ai.system` → `gen_ai.provider.name` and legacy `call_llm` spans; pin the spec commit SHA of `semantic-conventions-genai` in `docs/design.md` because there is no release to pin; budget a rename migration. Benefit: the trace a reviewer sees looks like the industry's trace. Risk: memory/skill attributes exist only in our emitters; any renames land on us.
- **Option B: OpenInference + self-hosted Phoenix on our Postgres.** Cost: one container; accept instrumentor gaps (first input-message set only, no LangGraph node ids, no sessions/memory); add memory/skills as custom attributes Phoenix will display only as raw JSON; the Vue UI either embeds Phoenix or we accept two UIs. Benefit: working trace viewer in an afternoon; least custom code. Risk: the platform's distinctive requirements (memory, skills, trial metadata) are second-class in the viewer, and Phoenix's tables are not a stable contract for our API.
- **Option C: own minimal schema, OTLP-compatible envelope, `gen_ai.*` names where they exist.** Shape suggested by the evidence: tables `trace(trial_id, harness, started_at, ...)`, `span(id, trace_id, parent_id, name, kind, start, end, status, attributes JSONB, events JSONB)`; span kinds taken from `gen_ai.operation.name` values (`invoke_agent`, `chat`, `execute_tool`, `search_memory`, `upsert_memory`, `execute_tool load_skill`) plus `evals.*` attributes for trial id, condition, seed, cost; messages stored as the spec's `{role, parts[]}` JSON (so `gen_ai.input.messages` is a direct copy); adapters: LangChain `BaseTracer`, OpenAI `TracingProcessor`, ADK `SpanExporter`, Hermes plugin on `pre/post_llm_call` and `pre/post_tool_call`, each also wrapping the harness's memory object. Cost: four adapters and one controller; we own the schema doc. Benefit: every field the UI needs is first-class; export to Phoenix/Langfuse remains possible because both already read `gen_ai.*`. Risk: no free tooling; must be explained as "OTel-shaped, not OTel-certified".
- What the evidence favours: C, because the two things the brief requires that standards do not deliver in practice (memory reads/writes and skill invocations, plus trial identity) are exactly where adopting a standard yields no reuse, while the things standards do deliver (LLM call shape, token names, tool call shape) are cheap to copy by name. B is the right choice if demo speed outranks fidelity; A if interview recognisability outranks stability and the team is willing to track an unreleased spec.
- Regardless of option: set `OTEL_INSTRUMENTATION_GENAI_CAPTURE_CONTENT=SPAN_ONLY` semantics (content on spans) as the platform default, since an evals platform exists to inspect content; record this as a deliberate deviation from the spec's `NO_CONTENT` default in `docs/design.md`.

### Gaps
- Not researched: Postgres JSONB sizing for very long traces (Hermes sessions with many turns) and whether a `_ref`-style blob offload would be needed; not researched: the OTel JS SDK's ability to re-emit stored spans if the team later wants to forward to a vendor.
- The brief leaves ADK vs OpenAI Agents SDK open; both are covered above but the recommendation does not depend on the choice.
