# Known limits

Where this platform's conclusions should not be trusted. Add a line the moment one turns up. Remove a line only if it's actually fixed and tested.

## Topics the brief names

- **Task-set size:** with 21 tasks, results may not generalise to other work. The headline compares the 10 held-out tasks only (D53), where the comparison finds a real +15 point improvement only about half the time (Statistics, below). In the real run 5 of the 10 tied (4 at 10 of 10 in both arms, 1 at 0 of 10), so only 5 tasks carried the test and p could not go below 0.0625 (`docs/experiment.md`, Results).
- **Judge bias:** measured on Rishi's tuning labels only (33 discovery trials, one rater; `docs/experiment.md`, "The judge against Rishi's tuning labels"). The specific criteria agreed with him (clears-card-first 12 of 12, keeps-medicines and health-cover 3 of 3 each, where kappa is undefined because his labels were all one value); the overall verdict is lenient (kappa 0.30, interval 0.00 to 0.78; specificity 0.20, 4 false passes). Not yet checked on held-out labels or for a false-pass gap between arms, so no judge criterion counts in the headline: every judge check there is optional and was not run. Judge retest: see `docs/experiment.md`.
- **Contamination:**
  - **Between trials: none by design, and tested.** Each trial gets a fresh Hermes home and trial folder at a fixed path, wiped and checked empty between trials with leftover processes killed, on a read-only root with no host mounts (`docs/design.md` section 4). The netcheck (`docker compose --profile smoke run --rm netcheck`, `workers/base/netcheck.py`) checks a worker reaches the API, LiteLLM and the fake model but not the internet, on a read-only root with `/trial` writable. The image leak tests (`workers/adapterlib/tests/test_images.py`) run two trials in one container, the first writing markers everywhere it can and leaving processes behind, and check the second sees none of it and cannot reach the first one's stored files. LiteLLM's response cache is off (`cache: false`, enforced by `scripts/check_litellm_config.py`), so no answer is replayed. What the tests do not cover: SysV IPC and POSIX message queues are not cleared, and the leak test looks at known paths (both below).
  - **Tasks seen before the comparison.** 4 of the 10 held-out tasks (convo-consolidation, loan-to-clear-card, sip-education-goal, otp-scam) had v1 outputs read on 4 Nov, before v2 was written and before the split existed (`docs/experiment.md`, Setup), so v2 may carry what was seen there. Of the 5 tasks where the arms differed, 2 were among them (convo-consolidation 2 → 5, loan-to-clear-card 8 → 9); the 3 never run before v2 also favoured v2 (convo-phone-loan 2 → 5, convo-job-loss 3 → 4, college-cost-stepup 9 → 10).
  - **Model training data.** The tasks, client files and personas are new, synthetic and not public. The model may still know standard EMI formulas and Indian product facts (FDs, PPF, SIPs, RBI rules) from training. Unmeasured. Both arms use the same model, so in the prompt experiment this moves both pass rates alike; in a model-vs-model comparison it would not cancel.
  - **The simulated client (D22).** Its replies are cached by exact conversation state, scoped by task, simulator model, prompt and settings but not by agent config, so both arms meet the same client: same persona, hidden facts, model and prompt, and the same reply whenever two conversations are identical so far. This is allowed: it fixes the environment and never touches the agent's calls. It makes a recorded conversation repeatable, not the client deterministic. The simulator runs Haiku 5.5 at its default temperature (D27), and in the headline's 60 conversation trials all 60 first agent replies differed, so no two trials shared a state after the opening message and every client reply was a fresh sample. The client's own variation is part of each trial's noise in both arms: on convo-phone-loan it did not answer v1's direct question about the extra it could pay (`t_0mw38a1yo2bb2711bbfafd20c`), and it volunteered its ₹3,000 to v2 without being asked for an amount (`t_0mw38a1yod9dd291f21e1b63c`).
- **Harness-specific quirks:** see below.

## Hermes-specific, from notes so far

- The system prompt contains the date, the model name and a home path, so prompts aren't byte-identical across days or models. Comparing models can't be a pure single-axis change.
- Memory on vs off also changes tools and prompt. Enabling memory and skills together added about 2k tokens per call, estimated as chars / 4.
- The Hermes repo changes daily, so results apply only to the pinned SHA.
- The prompt also carries the kernel release, user home, working directory, scratch path, an environment-probe line and a git snapshot. Byte-identical prompts across concurrent trials need fixed paths per trial, which in practice means a container. The calendar date cannot be fixed, so arms should be interleaved in time.
- Prompt-cache markers are sent only when the proxy hostname contains `litellm` and the model name contains `claude`. Cost and latency comparisons across model families are therefore affected by caching for Claude only. Markers change cost and latency, not the reply: Anthropic's prompt-caching documentation says caching "has no effect on output token generation" and the response is identical to an uncached one (platform.claude.com/docs/en/build-with-claude/prompt-caching, read 4 Nov 2026). The trial page's settings table says so on the markers row.
- The extra summary call Hermes makes at `max_iterations` is missing from its own token and cost totals. Cost must come from the LiteLLM log, or Hermes trials that hit the step cap are undercounted.
- Compression, if left on, rewrites the transcript. The final message list is then not the full trajectory.
- With the MCP route, Hermes shows the model prefixed tool names and wraps tool results in an "untrusted" block with no switch to turn it off. A cross-harness comparison includes that difference.
- The agent's shell can read its LLM key from the environment, files or `/proc` in every isolation option. Per-trial budgeted virtual keys limit the damage; they do not prevent the read.
- Hermes has no switch to stop the agent editing its own `config.yaml`, `SOUL.md` or project context files. Only a before-and-after hash per trial detects it.
- The findings in this list were first found by reading the code (3 Nov). The sections below and `docs/hermes-notes.md` record what running Hermes has confirmed since.

## From the 3 Nov research

- **Judge validation per config is underpowered.** 15 to 25 labels per config supports descriptive numbers with intervals, not a pass or fail gate. No published practice validates judges per config.
- **Judges are weakest on emotional framing**, which is exactly what the finance advice tasks test. No study tests this on advice rubrics, so it must be checked in our own labels.
- **With about 20 tasks, task count limits power more than trials do.** Effects smaller than roughly 6 to 25 points will not be detectable whatever N is. That range is a calculation from Miller's formula under assumed variances, not a measured figure.
- **LiteLLM spend logs** price missing models at zero, skip cached-token pricing below provider minimums, and do not document how retries are billed (on 4 Nov a retried call was charged once; see "LiteLLM retries" below).

## Hermes, from the SP1 probes (3 Nov)

- Hermes sends local-server probes (Ollama detection, `/models`) to the proxy host that no setting fully stops. They are excluded from model-call counts by path; a change in Hermes's probe paths would inflate counts until noticed.
- Hermes's own hooks miss its hidden unmask-probe retry and its max-iterations summary calls, so any Hermes-side trace under-reports model calls. The proxy's records are authoritative (R10.9); the two are kept side by side.
- Whether `reasoning_effort` would be translated into extended thinking on a real Claude or Gemini route behind LiteLLM was not tested; the adapter keeps it off the wire.

## Hermes, from the adapter's gate tests (3 Nov)

- Hermes repairs malformed tool-call JSON and runs the repaired call, or runs the tool with `{}` when it cannot repair it, without telling the model. The other harnesses send the error back. A model that often emits broken JSON will look better on Hermes for this reason alone; the `malformed_tool_calls` count on each trial shows where it happened.
- Hermes start-up (import and MCP discovery) takes several seconds of the trial's `timeout_s`, which the other harnesses do not spend. Wall-clock comparisons across harnesses include it.

## Trial isolation (D3)

- Consecutive trials in one harness container are separated by a process sweep, a folder wipe and a read-only root filesystem, not by a fresh container. A harness that writes somewhere we did not anticipate could carry state from one trial to the next. The SP3 leak test checks the known paths only. Worker containers mount nothing from the host (trial files are uploaded to the API, which alone writes `runs/`), so the only writable places are the trial folder and `/dev/shm`, both wiped between trials; the image test checks that trial 2 sees no `/runs` and none of trial 1's files.

## Cost tracking

- LiteLLM v1.99.4's bundled price map has no entry for Haiku 5.5 or Gemini 3.8 Flash (checked 3 Nov inside the pinned image). Spend on a model the map does not know counts as $0, so a per-trial `max_budget` would never trip. Every model in `services/litellm/config.yaml` must therefore state its prices in `model_info`, and `scripts/check_litellm_config.py` fails CI otherwise. Those prices are copied by hand from the provider pages, so they can go stale.

## LiteLLM records (checked 3 Nov, v1.99.4)

- A wildcard route priced only in `model_info` logged every call at $0, because LiteLLM prices the resolved model name (`openai/<script>`). The fake route now also sets prices in `litellm_params`. A real model added later under a wildcard would hit the same gap, so real models are listed one by one.
- Spend-log rows are written in batches, every second with `proxy_batch_write_at: 1`, and lagged by more than 1.5 s for a fast trial on 3 Nov. The runner now waits until LiteLLM holds at least as many calls as the harness reported, then 1.5 s of no change, at most 30 s. If the log never catches up, `proxy_usage.complete` is false and the trial's counts and cost are not trusted. A harness that under-reports its own calls could still let the wait end early; the floor is the harness's count, not the true one.
- LiteLLM cuts long strings out of the bodies it stores in the spend log (about 2,000 characters by default, with a note naming `MAX_STRING_LENGTH_PROMPT_IN_DB`). It cut the task prompt out of Hermes's system prompt on 3 Nov. Compose now sets the limit to 2,000,000 characters, and the merge flags any body that still carries the note (`evals.request.truncated`), which fails the proxy gate.
- The proxy merge puts a model call under the agent turn whose time window holds its start. The clocks are the adapter's and LiteLLM's container clocks; skew between them larger than the gap between turns would misplace a call.

## LiteLLM retries (D16, checked 4 Nov on v1.99.4 against the fake)

- **Failed attempts have no spend-log row of their own.** A call LiteLLM retried is one row: 429, 429, 200 gave one `success` row with `metadata.attempted_retries: 2`; an always-503 call gave one `failure` row with `attempted_retries: 3`, while the fake saw 4 requests. So per-attempt detail (each attempt's time, status and error text) is not stored anywhere we read; only the count is, and only the last error. `proxy_usage.attempts` is the sum of 1 + `attempted_retries` per row. A row without the field (a call refused before routing, such as a budget stop) counts 0 attempts, which matched the fake's capture. If a later LiteLLM stops writing `attempted_retries`, `attempts` would fall to 0 and `retried_calls` to 0 without any error.
- **Retried calls are charged once.** The served attempt carries the cost; failed attempts are logged at $0 (fake prices, 4 Nov). Whether a real provider bills a failed attempt is the provider's business; 429s and 5xx normally are not billed.
- **A 403 may be retried on real routes.** Through the fake's OpenAI-compatible route LiteLLM mapped a 403 to `BadRequestError`, so `BadRequestErrorRetries: 0` applied and it got 1 attempt (tested). Its code maps some Gemini 403s to `PermissionDeniedError` instead, and its router retries those when the model has a healthy deployment; `retry_policy` has no key for 403 (read in `router.py` and `exception_mapping_utils.py`, not run). Such a 403 would get up to 4 attempts and about 10 s of waiting before the trial ends as `infra:config_error`. It costs no tokens; only the attempt count is off.
- **Waits add to latency.** Backoff is about 1, 1 and 2 s (Retry-After replaces it when the provider sends one), and LiteLLM waits once more after the last failed attempt before giving up: an always-503 call took about 10 s and an always-429 one (Retry-After: 1) about 6 s. A trial whose call was retried is slower for reasons outside the agent; `proxy_usage.retried_calls` and `evals.proxy.attempts` on the `chat` span show which.
- **The per-call timeout (180 s) times 4 attempts is longer than a trial.** With the default `timeout_s` of 300 s, a provider that hangs on every attempt still ends the trial at its own deadline as `timeout`, labelled `agent` (see the 4 Nov Gemini entry below). Only a hung attempt followed by a quick one is recovered, and only if it fits in the time left. The 408 that LiteLLM returns after its timeout retries is labelled `infra:provider_error`, but it arrives only when `timeout_s` exceeds about 12 minutes. Tested with a 5 s timeout: 4 attempts, one `failure` row with status 408, about 31 s in all.
- `retry_policy` keys LiteLLM ignores: `InternalServerErrorRetries` is accepted but never read in v1.99.4, so 5xx errors follow `num_retries`. A future change to one of them in the config would do nothing; the config check bounds `num_retries` as well.

## Pre-run checks: rendered prompt and conflict check (D33, D38)

- **The rendered prompt comes from a probe on `fake/finance-emi`, so model-gated text is missing.** Hermes adds `TOOL_USE_ENFORCEMENT_GUIDANCE` when the model name contains `gpt`, `codex`, `gemini`, `gemma`, `grok`, `glm`, `qwen`, `deepseek` or `muse`, plus `GOOGLE_MODEL_OPERATIONAL_GUIDANCE` for `gemini` and `gemma` (`agent/prompt_builder.py:362`, `agent/system_prompt.py:580` at the pin). A Hermes config on Gemini 3.8 Flash really gets that text; its rendered prompt and its conflict check do not see it. Claude model names are not on the list, so Haiku and Sonnet configs are unaffected. Every rendered prompt carries this caveat. A fix is in the Parking lot (probe on `fake/<real model name>`).
- **The rendered prompt's sha moves with the host.** Hermes writes the kernel release and paths into its runtime block; only the date and model are normalised. In the worker image the paths are fixed (`/trial/...`), but a different host kernel gives a new sha, so a config rendered on one machine and checked on another is checked again (and paid again).
- **The conflict check is one model's judgment, not validated.** There is no labelled set for it. It can miss a conflict or report one that is not there, and its quotes are not yet checked against the texts (Parking lot). Read it as a prompt for a human look, not a gate.
- **`max_tokens` 2000 with thinking at the default.** Sonnet 5.5 thinks adaptively by default and thinking counts towards `max_tokens`, so a long think can cut the JSON reply short. That reply is refused (502 `checker_output_invalid`) and its cost still recorded; nothing is repaired or guessed. How often this happens is unknown until the first real check.
- **Cost from the spend log, with a 10 s wait.** If LiteLLM's row has not landed after 10 s, the API takes the `x-litellm-response-cost` header (`cost_source: response_header`); with neither, the cost is null and the check's worst-case reservation stays counted against the allowance. Unsettled `pending` rows (an API crash mid-call) also stay counted at their reservation.

## Invariance diff

- It normalises only the trial folder path and Hermes's "Conversation started:" date line. Other per-run text in Hermes's prompt (kernel release, host, user name) is constant on one machine, so trials compared across machines will show it as unexpected differences. Real runs happen in one container image, which keeps them constant.
- It compares the first request only. A difference that appears later in a trial (for example a tool result wrapped differently) is not caught here; the trace shows it.
- "First" is the first spend-log row after sorting by LiteLLM's `startTime`, then request id. On 4 Nov LangGraph's proxy invariance test failed once in four runs (against a throwaway LiteLLM and the fake), with the diff showing `messages[2]` and `messages[3]`, as if a later request had been taken as the first; the other three runs passed. The cause was not found. Read the diff's paths before trusting an unexpected difference.

## Platform checks (`checks.json`, 4 Nov)

Number provenance began as a text check for highlighting. Since D54 the `provenance` grader built on it is required at 0 unsupported figures on 18 of the 21 tasks (9 of the 10 held-out), so where it is wrong it decides an outcome. Where it is wrong:

- **Unsupported but harmless.** A figure the agent picked as an example ("such as ₹3,000 or ₹5,000 a month", "about ₹2,000 on the card") has no number behind it and is counted as unsupported, the same as arithmetic done in prose. On the 4 Nov run 3 of the 34 unsupported amounts were examples of this kind (read by hand, not counted by code); the rest were arithmetic.
- **Supported by coincidence.** A number anywhere in what the agent had read counts, whatever it meant, so a figure the agent worked out itself is "supported" if it happens to equal or round to an unrelated number. A figure shown with little precision matches widely: "₹5 lakh" matches any source from 4.5 to 5.49 lakh. Trailing zeros count as rounding only within 1% and with two significant digits left (on 4 Nov this stopped "roughly ₹31,000", the agent's own sum, from matching an unrelated 31,330.07), which narrows this but does not close it.
- **Missed amounts.** Money written without a marker in Western grouping or as words ("441,050", "twenty thousand rupees") is not extracted, nor is the second end of a range written "between ₹2,000 and 3,000". Numbers glued to letters ("t001"), dates and URLs (since D58) are not sources.
- **Sources it does not see.** Tool results are read from the `execute_tool` spans, where strings are cut at 16,000 characters (`MAX_STRING_ATTR` in `trace.py`): numbers past the cut in a long amortisation page or transaction list are lost, and an amount quoting them shows as unsupported. Text the model wrote before a tool call is not in the transcript, so its amounts are not checked. Simulated-client hidden facts count only once the client has said them.
- **Laundering a figure through an arithmetic tool: fixed by D56** (5 Nov). With the arithmetic tools (D54) a number the agent made up, or worked out itself, counted as supported once it had passed through a tool that returns it: `round(23120)`, `add([x, 0])`, `multiply([x, 1])`. Now an arithmetic tool's result counts only when every number it was given is itself supported, traced through the calls in start order (contract section 12, A40), and `checks.json` says which input was not. What it still does not catch, or gets wrong:
  - **An input equal to a supported number by chance.** Inputs are matched by the amounts' rule, so a figure the agent invented or worked out itself is accepted when it happens to equal, or round to, a number it had read: `9000` is "supported" by an unrelated 8,960 (trailing zeros within 1%), and a small number such as 0, 1 or 12 is supported by any tool result that happens to hold it (a count, a number of months, a rate). The same holds for an amount in a reply ("Supported by coincidence" above).
  - **The other tools' inputs are not traced** (D56 covers the seven arithmetic tools only). A finance tool's result counts whatever it was given: `calculate_emi` on a made-up principal gives figures that count as supported, and `inflation_adjusted_value(23120, 0, 1)` returns 23,120.00 (run on 5 Nov), so a made-up figure can still pass through it.
  - **A constant with no source made a correct result unsupported: fixed by D58 for the unit facts** (5 Nov). `multiply([8997.26, 12])` for a year of EMIs, or `divide(x, 100)`, counted only if 12 or 100 was in a tool result, the client file or a message by then (A40). Now 7, 12, 28 to 31, 52, 100, 365, 366, 1,00,000 and 1,00,00,000 need no source as arithmetic inputs (A43). **The list is fixed**: any other constant (4 weeks, 24 months, 1,000, a rate the agent picked) still needs a source, so `multiply([x, 24])` for two years is unsupported unless 24 appears somewhere, and the correct answer is to multiply by 12 twice or take the tenure from a tool.
  - **A figure made only of unit facts counted: fixed by D61** (5 Nov). `multiply([100, 12])` gave a supported 1,200 though nothing the agent read held it. Since D61 every arithmetic call needs a sourced amount (a sourced input of 100 or more), so it does not count. A sourced 100 or more that is not really money (a tenure of 240 months from a tool) can still be that amount.
  - **Start order stands for "had read it".** Two calls from one model response (parallel tool calls, off by default) are traced as if the one that started first had been read before the other was sent.
  - **Arguments the trace does not hold.** A call whose arguments are missing or cut at 16,000 characters (`MAX_STRING_ATTR`) is not a source, so its result is unsupported even when correct.
  - **A regrade does not re-run the checks.** `checks.json` is written once, by the runner, at the end of the trial; the grader reads it. A trial whose checks.json predates D56 keeps the old rule in that file, so on a regrade (framework 0.4.0) the `provenance` grade is an `error` when an amount there rests on an arithmetic result and nothing else fails it. The arithmetic tools exist since 5 Nov (server 0.3.0), and none of the 189 trial traces under `runs/` on 5 Nov calls one, so none of those is touched; a trial run on `finance/v2` between D54 and D56 would be (the API's stored trials were not checked). Likewise a checks.json from before D58 (runner 0.2.0) keeps D56's stricter rule: there `multiply([emi, 12])` is unsupported unless 12 was in a source, and a regrade (framework 0.5.0) still fails it, because the grader cannot re-trace. None of the 189 traces under `runs/` calls an arithmetic tool or `reference_rates` (checked 5 Nov), so none is affected; the grader does not try to spot such a file. And a checks.json from before D61 (runner 0.4.0) counts arithmetic written in prose as unsupported: a regrade (framework 0.6.0) keeps that, and the provenance grade says the file predates D61. Every trial recorded before D61 is in that position: re-running the checks on its folder (`python -m evals_adapter.checks <trial-dir>`) gives D61's view.
- **Verify, don't trace (D61, 5 Nov).** A figure no source holds is verified when the checker recomputes it as a one-step derivation of numbers a reader can see (A44): a sum or difference of a figure the answer wrote and another written figure or sourced amount; a sourced amount times or divided by 12 or a count the answer writes before "months", "EMIs" and the like; a percentage of one at a rate the answer states or a source holds; a run of 3 to 8 figures written next to it. Where it is wrong:
  - **Verified by coincidence.** A round figure the agent chose can equal some sum or share of the numbers in the answer. On the 4 Nov transcripts 15 of the 34 formerly unsupported amounts are now derived in prose; read by hand, 11 are the reply's real arithmetic and 4 are coincidences (LangGraph's "such as ₹3,000 or ₹5,000 a month" as 8,000 − 5,000 and 60,000 ÷ 12, its ₹30,000 as 8,000 + 22,000, and the Agents SDK's ₹31,000 as 40,650 − 9,650). Moving every amount on those transcripts 7% to 13% off its value, 4.5% of the 920 wrong figures still "derive" (mostly lakh figures, whose precision is ₹1,000): the search over every pair of source numbers, at the sources' 1% trailing-zeros tolerance, gave 27.7%, which is why the pools are narrow and a derivation must match at the precision written.
  - **Correct but unverified.** Two-step arithmetic (42% of ₹84,250, over 12 months), a total of figures the answer does not show, and a rounded estimate ("about ₹40,200" for 40,211.63: within 1% but not at the precision written) stay unsupported. So do choices ("about ₹2,000 on the card"), as they should. On 4 Nov 19 of the 34 stay unsupported.
  - **A stated rate is a free factor.** A percentage the answer writes ("at 7.4%") may be the rate of a derivation or of `percent_of`, so a made-up rate the answer discloses no longer fails (D58 refused it); one it does not state still does, and `reference_rates` is still the way to give a rate a source.
  - **A rate written as a fraction is not a source (found in the headline run, 5 Nov).** A rate passed to an arithmetic tool as a fraction (0.42, 0.0833333333 for 1/12, 0.035, 0.24) is neither a sourced number, a unit fact, a whole number from 1 to 60 nor a percentage the answer writes (A44), so the result is unsupported even when it is right, and the cause rules call it made-up arguments. `multiply([84250, 0.42, 0.0833333333])` = ₹2,948.75, a card's correct monthly interest at 42%, failed `t_0mw38a1ypd590d04a27189624`. In `e_0mw38a1ym89666c6ccc6bfd13` 5 v1 and 2 v2 failures contain such a figure, and it is the only reason for 1 v1 and 2 v2 failures (`t_0mw38a1yo5e18427f65f5a378`, `t_0mw38a1yoc843064ed31bbba7`), all on convo-consolidation; it costs v2 one more pass than v1, so it does not explain v2's +9 points (`docs/experiment.md`, Trajectories). Not fixed under the freeze (D65).
  - **Tools and prose use different factors.** An arithmetic tool's input may be any whole number from 1 to 60 without a source (the call is explicit in the trace); a derivation in prose may use only 12 and the counts the answer writes, to keep the search from verifying by chance. So `multiply([emi, 18])` counts, and "₹1,61,951 over 18 months" derives only if the answer says "18 months".
  - **`derived_in_prose` is a count of verified figures, not of all prose arithmetic.** A figure computed in prose that is wrong, or two steps away, is counted as unsupported, not as derived; and one a tool computed but whose call does not count (its inputs had no source) is derived in prose when the checker can recompute it.
- **Required tools** count a call that ran, even with wrong arguments; `only_errors` lists required tools whose every call failed. Calls in the trace come from the adapter's tool callbacks, so a call a harness ran without reporting it (none known) would be missed.

## Simulated client (D22)

- The reply cache is filled per trial and stored by the API when the trial is reported (from its uploaded `out/sim_replies.jsonl`). Two trials running at the same time that reach the same new conversation state both call the simulator, and can get different replies; the first stored wins for later trials. At temperature 0 the replies should match, but that is not guaranteed. On Haiku 5.5 the simulator sends no temperature (D27), so it runs at the model's default and two such calls will usually differ: only the cache makes it repeatable, and only for states already stored.
- The API trusts the replies a trial reports in `out/sim_replies.jsonl`. That file is written inside the trial folder, which the adapter process and anything it runs can also write (a harness with a shell or file tool turned on), so an agent could add a forged reply under a future conversation state's key and it would be served to later trials of the same task and simulator. Forging needs the key, a hash of the exact future transcript, so an accident is very unlikely, but nothing checks it. A check against the simulator key's LiteLLM spend log, which holds the real responses, would close it; not built.
- The simulator's own calls go through a separate key, so they are not in the agent's spans or counts. Their cost is recorded per trial (`sim_cost_usd`) and counted in the experiment's spend, but the comparison's cost difference is the agent's alone.
- Since `client-sim.v4` (4 Nov) a client can end the conversation unhappy when its patience runs out (three advisor replies in a row with nothing on its main concern, only questions). That ending writes the same end marker, so `conversation.ended_by: client` no longer means the client was satisfied: the library cannot tell the two apart, and a grader or the judge must read the client's last message. Whether Haiku 5.5 counts the replies as the prompt asks is unknown until real v4 transcripts are read; v4 has run only against the fake simulator, which ignores the prompt.

## Fake model server (tests and CI only)

- It does not model `max_tokens`: a reply is cut off (`finish_reason: length`) only where a script asks for it with the `length` fault (`finance-length`, `finance-length-always`), never because a cap was too small. It does not model `tool_choice`, `n`, auth, or whether a tool call matches the request's `tools` either. Tests that pass against it say nothing about those behaviours; real dev runs (R9) cover them.
- It speaks only the OpenAI Chat Completions format. A harness that needs the Anthropic Messages format (for example the Claude Agent SDK) reaches it only through LiteLLM's translation, which is untested.
- **Its costs are made up (5 Nov).** Fake models are priced in `services/litellm/config.yaml` only so budgets and spend can be tested; a cost on a fake-model trial is not what any real model would cost. The comparison says so above its cost tiles, and approving a real judge for fake-model trials warns and asks twice, since it spends real money grading scripted replies.

## Finance tools (`services/finance-mcp`)

- Loans that cannot be scheduled in whole paise are rejected rather than approximated: an EMI that rounds to ₹0, an EMI below the first month's interest, a loan that would clear early, or a final payment above twice the EMI. Tasks must avoid such inputs.
- **Part-prepayment charges are not modelled.** `prepayment_impact` and `debt_payoff_plan` assume a lender takes any part-prepayment free, including small monthly extras. Many Indian lenders charge 2 to 5% on part-prepaying a fixed-rate personal loan or refuse it in the first months, so tasks that prepay a personal loan (`draft-prepay-personal-loan`, `draft-convo-phone-loan`, and the payoff plans once the card is cleared) overstate what is possible; a good answer says to check the lender's terms.
- Tool schemas leave the server identical for every client, but harnesses rewrite them before the model sees them (LangGraph strips titles and inlines references; ADK wraps descriptions). The schemas are kept flat to minimise this, and the tool test compares what actually reaches the model.
- The MCP SDK orders `inputSchema` keys differently under protocol 2026-07-28 than under 2025-11-25. Content is identical; every known harness negotiates 2025-11-25.
- **The toolset's schema changed on 4 Nov: `sip_future_value` gained an optional `lump_sum`** (Rishi's review note 18), with a longer tool description. Every trial's tools array, and so its first request, prompt tokens and cost, differs from trials run before it, and an agent can now get a lump sum's future value from the tool where before it had to work it out. **Results before and after are not comparable on SIP tasks**, and not byte-comparable on any task (the invariance diff shows the tool change). A call without a lump sum returns exactly what it returned before. The server's version is now 0.2.0.
- **Toolset hashes before 4 Nov covered the tool names only.** Since 4 Nov `finance/all`'s sha256 covers the full published manifest: each allowed tool's name, description and input schema, and the finance server's version, as canonical JSON (`builtInToolsets` in `apps/api/src/catalogue/catalogue-files.ts`, read from `services/finance-mcp`'s manifest snapshot and `__version__`; `FINANCE_MCP_DIR` in compose), and the manifest is stored with the toolset row (migration 009). So the lump-sum change is a new toolset, and configs created after it get new hashes. **Configs created before the fix keep their old toolset hash**, which names the tools but not their schemas, and their toolset row has no manifest (NULL): which SIP schema such a config's trials saw is known only from the trial dates against the manifest snapshot's git history, and two such configs can share a hash while their trials saw different schemas. The fix also covers only what the server publishes; a harness's own rewrite of the tools (ADK's description wrapper) is in its capabilities, not in this hash.

- **The toolset changed again on 5 Nov: `finance/v2` adds seven arithmetic tools** (`add`, `subtract`, `multiply`, `divide`, `percent_of`, `percent_change`, `round`; D54; server 0.3.0). It is a new toolset version, so configs made before keep `finance/all` and its hash. Every trial's tools array has 18 tools instead of 11, so each call carries more prompt tokens and costs more, and an agent that now takes every sum from a tool makes more tool calls and uses more steps: a `max_steps` chosen for 11 tools may now be reached, and cost estimates from earlier trials run low. **Results on `finance/all` and `finance/v2` are not comparable**; both arms of an experiment use the same toolset (D54 gives both the new one).
- **And again: `finance/v3` adds `reference_rates`** (D58; server 0.4.0). No experiment ran on v2, so nothing recorded moves, but a v2 trial and a v3 trial are not comparable either: the tools array has 19 tools (one more description in every call's prompt), and an agent may now call `reference_rates` and quote its values where before it gave a rate with no source or none at all. Since v3 the checks also accept unit facts as arithmetic inputs (D58), so the same answer can count fewer unsupported amounts on a v3-era runner than on a D56 one.
- **`reference_rates` is a snapshot, not live rates (D58, 5 Nov).** Its values were read on 5 Nov 2026 from the pages it names, each with the date it applies to (`as_of`): SBI's one-year FD rate took effect on 15 Dec 2025 and its savings rate on 15 Jun 2025, PPF is the Oct to Dec 2026 quarter's, CPI inflation is September 2026's (provisional, on the new 2024 base; October's is due in mid-November), the repo rate is the 7 Oct 2026 decision, and the equity return runs to 30 Oct 2026. Nothing refreshes them: a trial quotes the file's value even after the real rate has changed, and the provenance check counts that quote as supported. That is by design (every trial on a server version sees the same values, so runs compare), but a reader of a later answer should check the dates. The six values were **approved by Rishi, 5 Nov** (server 0.4.1); a changed value is a new server version and a new toolset hash.
  - **The equity figure is a past index return, not a fund return.** `equity_long_run` is the Nifty50 Total Return Index's compound annual growth since it began (12.15%), before fund costs and tax, and it ends in a weak stretch (the one-year return was -9.45% and the five-year 6.70%), so a plan built on it states an assumption, as the tool says. **There is no debt rate**: `debt_fund` (the Nifty Composite Debt Index, 7.41%) was removed at Rishi's review, being an index return rather than what a debt-fund investor earns after costs, so an agent that quotes a debt-fund return has no source for it.
  - **PPF comes from a secondary source.** The Department of Economic Affairs and NSI pages could not be fetched on 5 Nov (certificate errors), so the value is Indian Bank's copy of the 30 Sep 2026 office memorandum, which press reports agree with.
  - **The FD and savings rates are one bank's.** SBI's card for the general public; senior citizens get 0.5 points more on the FD, and other banks differ. An agent that says "FD rates are about 6.25%" is supported by this one bank's rate.
- **Arithmetic results have 2 decimals** (`round` aside), so a small ratio loses digits (`divide(9, 1200)` is `0.01`). The calculators never needed one; percentages go through `percent_of` and `percent_change`.
- **Worker images carry their own copy of the finance server**, built in, while the API reads the tool manifest from the source folder. After this change, rebuild the worker images (`docker compose up -d --build`, or `workers/build_images.sh`) before running a `finance/v2` or `finance/v3` config. On an image built before it, the own loop, LangGraph, ADK and the Agents SDK fail at start-up because a listed tool is missing, but **Hermes silently drops the missing tools**: its `tools.include` is a whitelist over the tools the server lists (`tools/mcp_tool_registration.py`, `_make_tool_filter`, read in the source, not run), so the trial would run with 11 tools under a config that says 18 (or 18 under one that says 19). The pre-run rendered prompt ("N tools sent with it") and `scripts/verify_hermes.py` (tools against the config's toolset version) both show it; ask for the rendered prompt only after rebuilding, because a config's rendered prompt is stored once and never re-made.
- **`finance-no-calculators/v3` is for validation only (D70, 5 Nov).** It is `finance/v3` with the eight calculators left out, made for the positive control, a run whose effect is known in advance. A result on it says whether the platform detects a broken tool service, not how good an agent is, and it compares only with the `finance/v3` arm of its own experiment. (1) **The calculators are hidden, not gone.** The trial's finance server still serves them; only each harness's tool filter keeps them from the model (the own loop's and LangGraph's name filter, ADK's `tool_filter`, the Agents SDK's static filter, Hermes's `tools.include`). The gate tests (`test_tools_without_calculators`, all five harnesses, fake model) show that exactly the 11 reach the model's first request. What a harness does when the model calls a removed tool by name anyway is not tested; Hermes's `mcp__finance__calculate_emi` could be guessed from the other names. Such a call shows in the trace as an `execute_tool` span, and `scripts/verify_hermes.py` checks the tools sent against the config's toolset id and version. (2) **Tasks are unchanged (D65 freeze).** They still list the calculators in `required_tools` and their graders still ask for them, so a trial on this toolset is expected to fail those checks; prompt v1 still says to use the finance tools for EMIs, SIP and FD returns. (3) **Its version follows `finance`'s:** a new server version is a new version of both, with a new pinned hash for each.

## Deterministic graders (SP4, 4 Nov)

- **Exports from before 5 Nov count a regraded trial's grades twice.** Since 5 Nov the export (CSV and JSON) has each trial's `arm` and `outcome`, its current grading exactly as `GET /experiments/:id/compare` and the run grid count it, and `grades_passed`, `grades_total`, `grades_json` (and JSON `grades`) cover only that grading's grades; every older version stays in the database, in the JSON export's `grade_history` and in the bundle. A CSV saved before then lists every stored grade row of a trial, all versions (the shipped example's showed 6 of 10 for five graders after its regrade), so do not count passes from an old CSV's grade columns: read `GET /trials/:id` or export again. `grades_passed` counts optional graders as well as required ones; the outcome is the column to count.
- **Amounts are read with regular expressions.** `number` finds ₹/Rs/INR amounts, lakh and crore, and grouped digits; it does not read amounts in words ("twenty thousand"), ranges ("₹4,200 to ₹4,500" gives two numbers, either may match), or negative signs. With `match: any`, dates and list numbers count as numbers, so an expected value that also appears by chance (a "28" elsewhere) passes. A tolerance is per task: agents round (the own loop's "about ₹33,500" for ₹33,491.54).
- **`provenance` at 0 decides most draft-task outcomes (5 Nov).** On the 24 Hermes trials from 4 Nov with a `checks.json`, the required `every-amount-from-a-tool` grader (`max_unsupported: 0`) failed 18, almost always on a correct sum or difference written in prose (₹23,120 = ₹14,120 + ₹9,000). A task's pass rate then mostly measures whether the agent added two numbers in prose. D54 keeps it required at 0 and adds arithmetic tools to the finance toolset, so every figure can come from a tool; until a trial runs with those tools, a provenance fail on a correct sum is a missing tool as much as an agent failure.
- **What the headline's pass rate measures (counted 5 Nov, after the results).** On the headline run, 31 of v1's 36 failures and 24 of v2's 27 failed only the provenance grader. With that grader set aside, v1 passes 95 of 100 trials and v2 97 of 100. So the +9 points measure v2's compliance with "every rupee figure comes from a tool", which is the rule v2's prompt adds and the gain the hypothesis named. They say little about whether the advice is otherwise better: the checks on the numbers themselves are near the ceiling in both arms, and the judge criteria that would speak to clarity and care do not count until they are trusted (D8). Provenance at 0 is also strict: trajectory 3 in `docs/experiment.md` fails a correct saving that was rounded in prose.
- **Two regex false fails, fixed in version 2 (D53).** `draft-payoff-order`'s `\b28\s*months?\b` failed a Hermes answer that said "cleared in month 28, which is when you're debt-free"; `draft-loan-to-clear-card`'s `names-a-risk` failed an answer that said "The card can fill up again" (and passed any answer containing "risk"). Version 2 checks month counts with a `number` (`match: "any"`), which still misses "two years and four months", and asks the judge whether a risk is named, so that task has no required deterministic check on the risk until the judge's criterion passes the trust bar (D8).
- **Recorded trials keep their task version (D53).** Version 2 changed every task's core (no draft flag, a real split; for `draft-convo-payoff` and `draft-convo-where-to-start` also the simulated client), so an API regrade of a 4 Nov trial uses that trial's version 1 graders: the D53 fixes and severities reach only trials run on version 2. `evals-grade` on a trial folder uses whatever `task.json` it is given. `draft-convo-where-to-start` version 2 is a different scenario (her mother's medical costs, not a payoff budget), so its 4 Nov trials say nothing about it, and `draft-convo-payoff`'s budget now means "in total": compare neither across the versions.
- **Fixed 5 Nov: the label queue goes by each task's split in `tasks/` today (D52).** It used to read a trial's split from the task version the trial ran on, so the 4 Nov trials of the four tasks moved to held-out (`draft-loan-to-clear-card`, `draft-convo-consolidation`, `draft-sip-education-goal`, `draft-otp-scam`) would have been offered for tuning. A task no longer in `tasks/` counts as held-out if any version of it ever was. No labels had been written before the fix.
- **otp-scam's two critical checks are bounded unit tests (D63).** `says-do-not-share` needs a negation (do not, don't, never, no one should, nobody should) with one of share, give, tell, disclose, hand over, read out, pass on, send or reveal, and "OTP", "one-time password" or "code" within 160 characters in the same paragraph. It misses a refusal in other words ("keep it to yourself", "that code is for you alone"), and "don't share it" counts when "OTP" is near even if "it" means something else. `never-asks-for-otp` fails a request aimed at the client ("send me the OTP", "please share your code", "what is the OTP") in any reply or tool argument. It skips a request after a negation that governs it or after a reporting verb (says, asks, claims) in the same sentence, or inside double quotes, so an agent that wrote "the bank asks: tell me the OTP" as its own request would pass. Both pass all five recorded 4 Nov answers; the tests in `graders/tests/test_task_graders.py` hold the edge cases.
- **The D68 criteria have no tuning labels.** `explains-plainly`, `clarifies-ambiguous-amount` and `asks-deciding-fact` were written after Rishi's tuning labels, so nothing tuned them: the first measure of how far to trust them is their agreement with his held-out labels, where they must pass the trust bar (D8) before they count. A wording fault found there cannot be fixed without tuning on held-out labels, so it is reported, not fixed. `explains-plainly` has its own wording on draft-otp-scam, draft-distress-helpline and draft-mba-loan-missing-info but one criterion id, so its agreement pools three slightly different questions with the standard one.
- **The comparison cannot see v2's "clarify an ambiguous amount" fix (D68).** `clarifies-ambiguous-amount` exists only on two discovery tasks, because no held-out task's content has an amount that reads two ways; the headline compares on held-out tasks only, so that half of D67's clarify fix is unmeasured there. `asks-deciding-fact` is on three held-out conversations.
- **The card-first crux is unchecked in the pass rate (D63).** On car-loan-afford, convo-car, payoff-order, convo-payoff and prepay-personal-loan the card regex is an optional floor (minor): it passed all 25 recorded trials, because "credit card" appears whenever the debts are listed, so it never told a recommendation from a mention. Whether the card is recommended first is a judge criterion (major), which counts only once it passes the trust bar (D8). Until then those tasks pass without the R6 judgment being checked.
- **`regex_absent` on a word cannot tell a warning from a breach.** On 4 Nov `\bOTP\b` failed LangGraph's conversation because it told the client never to share an OTP. Rules about what the agent asks for belong in a `unit_test` or the judge.
- **`from_tool` needs the tool result in the trace.** Span attributes over 16,000 characters are cut (`evals_adapter.trace`), and a cut JSON result cannot be read, so the grade is an `error` (not a fail) naming the truncation. The finance tools' results are far below that; a long `list_transactions` could reach it.
- **The unit_test sandbox is a Python audit hook, not an OS sandbox.** It refuses sockets and child processes from Python code, and the subprocess gets a timeout, an empty folder and an empty environment, but native code (ctypes) could get round it. Task graders are our own code in git, so this guards against mistakes, not attacks; in compose the grader container is also limited to the internal trials network and a read-only root.
- **Grade evidence is verbatim for the built-in types only.** A `unit_test` may return any quote; its evidence is checked for shape, not checked against the text.
- **`provenance` and `required_tools` need a `checks.json`**, which the runner writes after every trial since 4 Nov (contract v2 section 12). The 4 Nov real trials predate it, so both are `not_applicable` on them; re-running the checks on an old trial folder (`python -m evals_adapter.checks`) needs the whole trial folder (`spec.json`, `state/`, `out/`); the uploaded `out/` files alone give no client-file numbers and no `required_tools`. Their verdicts inherit the check's own limits (see Platform checks above).

## The judge's plumbing (SP4, 4 Nov night)

- **Run on a real model since 5 Nov.** Gemini 3.8 Flash judged the 33 discovery trials twice ($0.259 and $0.249): every reply parsed, and 98 of 99 verdicts repeated (`docs/experiment.md`). It has not judged the headline runs, and no criterion has met the trust bar on held-out labels yet.
- **A quote is checked as a substring, whitespace aside.** A quote the judge stitched from two places with "..." is reported as not found even when both parts are real; a short quote such as "yes" can be found by chance. The verdict is not changed either way (choice 10 in `docs/proposals/grader-format.md`).
- **All criteria are judged in one call,** so one criterion's verdict can influence another's. Per-criterion calls would cost about one call per criterion (choice 13).
- **The fake judge (`fake/judge`) always answers "yes" on `overall`** and never reads the trial. It tests the path, not judgment.
## LLM judge approval (SP4, R8)

- **The judge's key is stored in Postgres as plain text**, because every grading claim for the experiment hands it out again. Anyone who can read the database can use it until it is revoked; the damage is capped by its budget (at most $20) and its one model. A revoked row keeps the dead key's text.
- **A grading job with a judge grader carries the key** (since 4 Nov night, only those; a job without one gets `judge: null`). It reaches the grader worker's memory, not its unit tests: a `unit_test` runs in a subprocess with an empty environment.
- **A revoked approval's spend relies on LiteLLM keeping a deleted key's spend-log rows** (assumption A19, not checked on v1.99.4). The figure read at revoke is the floor and the fallback, so at worst `GET /spend` under-counts calls whose rows landed after the revoke.
- **`GET /spend` reads LiteLLM's spend log once per approval ever made**, on every request, in parallel. With LiteLLM down each read waits for its timeout (15 s) and the judge line is null while any approval is active.
- **The judge's key check knows set, not valid (5 Nov, QA round 3).** `POST /experiments/:id/judge` refuses a model whose provider key compose's flag says is not set (`provider_key_missing`, naming the variable), but a key that is set and wrong, expired or without access to the model is approved, and every judge grade then errors. Outside compose there is no flag and nothing is refused.
- **The header's visible spend split shows trials and platform calls only.** `total_usd`, and so the header's bar and its spoken summary, include judge spend; a Judge figure in the visible split is a UI follow-up.

- Labelling is blind only when it is done from the Label page. While held-out outputs remain to label, the Judge page keeps the judge's reasons closed, and a trial page hides the judge's quotes, rationale and highlights for any task with an output still in the queue and never says where your label disputes the judge. Trial pages still show the judge's Pass or Fail on every check, and the hiding matches tasks by the queue item's `task_id`, which is not in the API contract: if the API leaves it out, trial pages show the judge's reasons for every task.

- **No screen says how far to trust a judge-graded check (5 Nov).** `GET /judge/agreement` returns null in this version, so the Judge page says the agreement is not shown, and the comparison and trial pages give a judge's Pass or Fail with no measured trust beside it. The agreement is worked out from the command line (`stats/`, `evals-agreement`). Until a screen shows it, read a judge-graded result as unvalidated.
- **The trial page's number check marks amounts by their text (5 Nov).** The runner's `checks.json` (contract v2) lists each amount with its reply's turn, not its position, so an amount written the same way in two replies is underlined in both when either is unsupported. The list beside the grades gives each amount once, with its source. Trials from before the runner wrote `checks.json` (the 4 Nov runs, and the shipped draft example) have no number check at all, and the page says so.

## Hermes memory (D39, 4 Nov)

- **Memory is never written within one trial.** In 20 memory-on trials on Haiku 5.5, Hermes did not call its `memory` tool once. Each trial is a fresh session, so a memory-on vs memory-off comparison on these tasks measures the extra tool schema and prompt text, and a seeded config measures the seeded facts. It does not measure whether Hermes saves the right things for later. Testing that needs a task that runs two sessions on one home, which we have not built.

## Run screen and engine (fresh-clone QA fixes, 4 Nov night)

- **The time estimate uses each trial's claim-to-report time.** It leaves out time a trial waits in the queue and the start of a worker that has just come up, and it averages over every earlier trial of the cell, including ones run while other experiments shared the workers. With no history it assumes 10 s a trial on a fake model (measured on the own loop only) and 60 s on a real one (A27).
- **The run grid, Compare and the futility check read each trial's grading outcome.** `GET /experiments/:id/trials` carries each trial's `grading` (its latest finished grading job's outcome, required graders only), and since 5 Nov Compare counts the same outcome, with trials whose outcome is `incomplete` (a required grader errored, was not applicable or is the unapproved judge) counted apart as `incomplete`, never as a pass or a fail. Whether SP6's primary metric is this pass rate or a mean score is still open (`docs/proposals/stats.md`, decision 2).
- **The futility check fires only while the run is running.** Grading lags the trials, so a fast run (fake models, many workers) can finish before its first `after` trials per arm are graded, and then the check never fires. That can only miss a pause, never add one. Since 5 Nov (A41) a run on fake models only has the check off unless it is turned on by hand, so such a run never pauses for it: most fake trials fail by design, and a pause there protected no spend.
- **The analysis plan commit is the person's word.** Since 5 Nov the API takes only a commit hash's shape (7 to 40 hex characters) and the Run screen says the commit is recorded as given. The platform cannot see git history, so nothing checks that the commit exists, that it is older than the run, or that `docs/experiment.md` at that commit holds a plan. A result's claim to a pre-registered plan rests on checking the commit by hand.
- **"Key set" means set, not valid.** `GET /models`' `key_set` comes from compose's `${ANTHROPIC_API_KEY:+1}` flag, read when the API starts: a key that is set but wrong, expired or without access to the model shows as set, and is still found only when a call fails (the arm pauses with a config error, or the conflict check fails). After editing `.env`, `docker compose up -d` recreates the API and LiteLLM with the new values; until then the flag and the key LiteLLM holds are the old ones. Outside compose the flag is absent and `key_set` is `null`: the UI then says nothing and a run finds out, as before.
- **Header spend leaves fake models out; an experiment's own spend does not.** Since 5 Nov `GET /spend`'s `trials_usd` (the header's "Trials") counts only calls to real models, and `fake_trials_usd` holds the made-up prices apart. Each experiment's `spend_usd` (the run page's "Spend so far", the experiments list) still counts every call at LiteLLM's price, fake ones included, since that is what its LiteLLM budget is charged; the run page labels a fake-only run's figure as made up. The LLM judge's spend is counted whatever its model, so a judge approved on a `fake/*` model adds made-up prices to `judge_usd`.
- **Fake-model trials are never labelling items.** Since 5 Nov the labelling queue leaves out trials whose agent ran on a `fake/*` model (a script, not an agent's output). A trial with a real agent and a fake simulated client is still an item: the agent's turns are real, but the client's are scripted, so judge those labels with that in mind.
- **A config counts as the example's until one of your own experiments uses it.** `example_only` is worked out from which experiments use a config: one the shipped example uses (or the parent of one) and none of your own does. A config you saved yourself with exactly the content of an example's (the same hash) before loading the example is one row, so it counts as the example's until an experiment of yours uses it; pickers then leave it out of their defaults, and it can still be named in the address or forked.
- **A config error's own trial is not re-run when its arm resumes** (D26, above). The run page now says so in the arm's "How to fix it": after the key or route is fixed, the arm's waiting trials run, and the slot that failed stays an infra failure. A run whose arm has no waiting trials left needs to be set up again.

## Host folders the API writes (clean-machine test, 5 Nov)

- **The API takes ownership of `runs/`, `labels/` and `configs/prompts/` when you are not uid 1000.** Its start-up step gives each of those folders (not their contents) to uid 1000, keeps your group and makes it group-writable (`docs/design.md`, section 4), so on such a host `ls -l` shows uid 1000, or whoever has that uid there, as their owner. Everything the API writes inside belongs to your group, so you delete it without sudo; you can no longer `chmod` the folders themselves without sudo. Tested 5 Nov with folders owned by uid 1001 (a throwaway stack, an example load, a fake run and a saved prompt, then a plain `rm` as uid 1001); not tested on rootless Docker, Docker Desktop or SELinux hosts.
- **A file of yours already in those folders is written only through its group.** The server joins each folder's group, so it can append to a group-writable file of your clone (664, as on a host with umask 002), such as a labels file you committed; a 644 one (umask 022) it cannot append to, and saving a label in that set fails with a permission error that the health check does not catch (it checks the folders, not each file). `chmod g+w labels/*.jsonl` fixes it.
- **A folder Docker made is root's group.** If `runs/` (or another of the three) was missing when the stack started, Docker creates it as root; the start-up step gives it to uid 1000 and group 1000, so on a host where you are not uid 1000 what the API writes there is not yours to delete: `docker compose exec api rm -rf /runs/<folder>` works whatever the owner.

## Names and what differs (fresh-clone QA round 3, 5 Nov)

- **A config's name is fixed when it is saved.** Since 5 Nov an unnamed config is named from what it holds (A36), but configs saved before keep their old auto-names ("Prompt v1 on Own loop, Fake model finance-emi"), so two of them one setting apart can still share a name. The Run screen then shows each arm's own value beside the name ("(max steps 10)") and the run's default name says what differs, but the arm pickers list configs by name and short hash only, so same-named configs are told apart there by hash. A name is a label; the hash is what a result points to.
- **An auto-name lists settings away from the platform's default, not the harness's.** A Hermes config with compression off is not named "compression off", though Hermes's own default is on (the platform turns it off unless the config turns it on). Past 120 characters the settings a config shares with its relative are left out of its name, so a long name may not mention every setting it sets; the config page lists them all.
- **"What differs" reads the two saved configs.** A toolset, prompt or capabilities file that kept its name but changed is told apart by a short hash ("tools all (e8a3303) vs all (e4c1f08)"), without saying what in it changed; the change itself is in git.

## Statistics (SP6, 5 Nov)

Measured on simulated data (`apps/api/src/stats/simulate.ts`: task pass rates spread uniformly
from 10% to 75%, arm B adding a fixed effect; 1,000 runs per row, 2,000 bootstrap resamples), with
the method as built (D10 revised: a task bootstrap, the sign-flip test, D42's verdict, D50's floor):

| Tasks K, trials N | A/A: false better or worse | Interval covers the truth (A/A, +15) | +15 called better (power) | Interval width |
| --- | --- | --- | --- | --- |
| 4, 10 | 0% (cannot, D50) | 84.0%, 83.1% | 0% | 31 points |
| 6, 10 | 0.9% | 87.7%, 86.7% | 10.5% | 28 |
| 8, 10 | 2.7% | 88.5%, 90.7% | 30.4% | 25 |
| 10, 10 | 2.9% | 90.5%, 91.8% | 49.9% | 23 |
| 12, 10 | 3.3% | 92.0%, 90.8% | 54.7% | 21 |
| 20, 10 | 3.4% (4.7% on other seeds) | 93.0%, 94.2% (91.6%, 93.7%) | 85.4% | 17 |

- **Little power at the headline's size.** The headline compares the 10 held-out tasks only
  (D53). **At K = 10 to 12 and N = 10, a real +15 point improvement is called "better" only about 50
  to 55% of the time**, 30% at K = 8. A "no detectable difference" there is weak evidence that
  nothing changed; read the "not ruled out" figure.
- **The interval covers a little under 95% with few tasks.** The percentile interval of a task
  bootstrap is too narrow with this few tasks: 91.6% and 93.7% at K = 20, N = 10 on one set of
  seeds, 88 to 92% at K = 8 to 12. "Better" and "worse" also need the exact sign-flip p < 0.05, which
  keeps false calls under 5% at every size measured; "practically equivalent" has no such check, so
  it leans on the interval alone (a real +15 was called equivalent in 1.1% of runs at K = 8, 0.6% at
  K = 10 to 12).
- **Below 6 tasks there is no verdict** but "no detectable difference" (D50): the sign-flip test
  cannot reach p < 0.05 (its smallest p is 2/2^K), and the bootstrap of so few tasks under-covers
  (84% at K = 4) or, with one task, has no width at all.
- **When every task gives the same difference, the interval has no width.** The task bootstrap sees
  only the spread between tasks' observed differences. If every task ties (for example both arms
  fail everything, a floor effect), the interval is 0 to 0. Since 5 Nov (D55) a zero-width interval
  never gives "practically equivalent": the verdict is "no detectable difference", saying every task
  gave the same difference so the interval cannot show how large a difference could hide. Better or
  worse can still follow from it when the paired test agrees (every task moved the same way).
- **Few trials per task.** A task's own flag comes from that task's trials only (Fisher's exact
  test, Benjamini-Hochberg across tasks): at N = 5 a task can be flagged only on a near-total flip
  (5 of 5 against 0 of 5 has p = 0.008). The per-task intervals are 40 to 100 points wide at N = 5.
- **Unequal decided counts.** Each task weighs the same in the headline whatever its number of
  decided trials, so a task with 1 decided trial (the rest incomplete) counts as much as one with
  10. Trials with no outcome are left out, not counted as fails: if being undecided depends on the
  answer (for example the judge erroring more on long answers), the pass rates are biased. A task
  where an arm has no decided trial is left out of the headline altogether and listed; until the
  judge is approved for an experiment, its judge-graded tasks are all left out.
- **The simulation is a model.** Real tasks include ones every trial passes or fails (rates of 0%
  or 100%), effects that differ by task, and outcomes that are not independent within a task; the
  coverage and power above are for the simulated spread of 10% to 75%, not measured on our tasks.
  The pilot's spread should replace them before N and K are chosen.
- **A/A calibration.** Each one is a full paid run (D44). The comparison shows the latest finished
  calibration of either arm's config, whatever its task set, N or platform commit; it is a check
  on the setup, not matched to the A/B it sits under. No calibration has been run on a real model
  yet, so the setup's own noise is unmeasured.
- **The critical guardrail is only as good as the severities.** No task in `tasks/` has a severity
  yet, so every comparison says "no check is marked critical". Only required checks marked critical
  count, and only tasks that have one enter its comparison. A severity is part of the grader spec,
  so adding one gives the grader a new version: a regrade picks it up and also re-runs the grader,
  including the judge (paid, approved separately).
- **Latency leaves out trials with a retried model call** (retry backoff would make an arm look slower;
  D16). If one arm hit rate limits far more often, its time is measured on fewer trials, which may
  differ from the rest (for example trials run at busy times); `left_out_retried` gives the counts
  per arm. Trials recorded before 4 Nov carry no retry count and are kept (`retries_unknown`).
  `wall_s` is the whole trial, so it includes the simulated client's turns, whose reply cache makes
  a repeated conversation faster than a new one.
- **Cost is the agent's LiteLLM cost only.** The simulated client's cost is left out of the
  comparison (it is the environment, the same for both arms), though it is in the experiment's
  spend. Trials from before D31 carry prompt caching in their cost (Cost comparisons, above).

## Failure causes and behaviour (D64, 5 Nov)

The causes are rules over what each trial recorded (`docs/design.md`, "Failure causes and behaviour
per arm"; A45). They point at where to look, and a trial's page is still the evidence. What they
cannot tell apart:

- **A substitute from a step on the way.** Any tool the task does not want counts as "another
  tool called in its place", so an agent that read the client's profile and then stopped before
  the calculator is *wrong tool*, not *gave up early*. The rules know no tool families (data
  readers, calculators, arithmetic); adding them would tie the platform to the finance toolset.
- **Which failure came first.** Precedence picks one primary cause; the trace's order is not
  read. A tool error that did not matter (on a tool the answer never needed) can be the primary
  cause of a trial whose real fault is a wrong figure, which is then contributing. Both show.
- **Made-up arguments are only what a check can see.** They come from a `tool_called` check with
  `args` (the arguments its task names), or from the runner's provenance tracing of arithmetic
  calls. A finance tool called with an invented input that no check names is not flagged; its
  answer may still fail as a wrong answer or an unsupported figure.
- **Malformed tool calls and other agent errors are `other`**, with the harness's words quoted.
  ADK's fourth malformed call in a row and LangGraph's malformed-only reply end `agent_error`;
  Hermes repairs malformed arguments silently and runs a call it cannot repair with `{}`, which
  shows only as a tool error (the reason says so). So "hallucinated tool arguments" in the
  brief's sense is split across *made-up arguments*, *tool error* and *other*, by harness.
- **Recovery from tool errors is not comparable across harnesses.** Each shows the model a
  different error, or none (`docs/harness-guide.md`, 8.1); *tool error* counts errors never followed by a
  successful call of the same tool, which measures the harness as much as the model.
- **A wrong answer can be the check's fault.** *Wrong answer* means a required number, regex or
  unit-test check failed with the right tools called; a too-strict regex (D63's OTP case) reads
  the same as a real error. A unit test can check behaviour too (`no-repeated-calls`), and is
  still counted here.
- **Judge vs label needs a label.** It only appears on trials Rishi labelled, against the judge's
  verdict on the same criterion; a deterministic check that disagrees with his overall judgement
  is not detected. Every judge check in the current task set is optional, so it never decides an
  outcome and is never the primary cause there. The comparison page hides it while held-out items
  remain to label, as it hides the other disagreements.
- **A judge failure with no label is `other`**, since the judge is not a deterministic check
  (*wrong answer* is), and an optional check never fails a trial on its own.
- **Steps are LiteLLM's count of the agent's calls.** Hermes's summary call at the step limit is
  in it (Hermes's own count leaves it out), so a Hermes step-limit trial shows one or two calls
  more than its limit. A trial with no LiteLLM record is left out of steps, not counted as zero.
- **Tool calls are counted from the execute_tool spans.** LangGraph, ADK and the Agents SDK run a
  reply's calls concurrently, so "after it" in *tool error* is by span start, not the model's
  order; ADK's synthetic `adk_handle_model_error` call is counted as a tool call.
