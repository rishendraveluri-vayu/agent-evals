# Assumptions

The brief says to document every assumption. One line each: the assumption, why, and what changes if it's wrong.

| # | Assumption | Why | If wrong |
| --- | --- | --- | --- |
| A1 | One local user: no auth or multi-tenancy | Local one-command run, scope cut | Add auth at the API layer |
| A2 | One machine: no multi-node workers | Local one-command run, scope cut | Workers need remote claim support |
| A3 | Configs and tasks live as files in git, plus a simple form | Versioning comes free, scope cut | Add editors |
| A4 | Polling is enough for run progress | The brief doesn't require live updates | Add SSE or WebSocket |
| A5 | Finance tool conventions: reducing-balance EMI with monthly rate = annual/12; the last EMI absorbs rounding so loans close at exactly ₹0.00; SIP contributions at the start of each month; FDs compound quarterly by default; money rounded half-up to paise | The usual Indian bank and calculator conventions; graders need one exact answer | Expected values in task graders change |
| A6 | Snowball debt payoff orders by starting balance, fixed at the start, ties in input order | The brief and the tool spec left it open | Payoff order in snowball tasks changes |
| A7 | The host's `runs/` folder is writable by uid 1000, the `node` user the API container runs as (as `labels/` already must be) | The API alone stores uploaded trial files there; workers mount nothing | Uploads fail with a 500 and trials go unreported until the folder's owner or mode is fixed |
| A8 | D27's simulator temperature change applies to models that refuse temperature (the API's `MODEL_REJECTS` table, today Haiku 5.5): there the simulator sends none; any other simulator model keeps D22's temperature 0 | D27 amends D22 for Haiku 5.5, the simulator model it names; it does not say other models change | `simTemperature` in `apps/api/src/worker/spec-builder.ts` returns null for every model |
| A9 | The client summary (D27) holds the client file's profile as recorded and its debts with their totals, not its transactions | D27 says "profile and debts"; transactions are long and the agent reads them through a separate tool | The simulator can still contradict a transaction figure the agent quotes; add a transactions section to `clientSummary` |
| A10 | A simulator reply holding only the end marker is a normal client ending once the client has already sent a message of its own in the conversation, and a simulator failure (`sim_error`) before that; any reply with no other text is a failure | The rule is that the marker alone after a real goodbye in an earlier message is a client ending, and only an empty or failed turn is an error. The library cannot tell whether that earlier message was a goodbye, so any earlier message of the client's counts | A marker-only reply after a client message that was not a goodbye ends the conversation as `client` instead of `sim_error`; tighten `empty_reply` in `workers/adapterlib/src/evals_adapter/sim.py` |
| A11 | A config's system prompt does not depend on the task, so one probe on a built-in single-question task (`prompt-probe`) shows the prompt every task of that config gets | Harnesses build the system prompt from the config (Hermes once per session, before the first user message); the user message travels separately | A task-dependent prompt would need a probe per task; the rendered prompt would be per (config, task) |
| A12 | The conflict check's cache key includes the config's settings as well as the brief's (rendered prompt, checker version, model); awaiting Rishi's view | The settings are part of the checker's input, so leaving them out would let two configs share findings that name the other's settings | Drop `settings` from `checkInputSha` in `apps/api/src/preflight/conflict-check.ts` |
| A13 | Only `done` trials (agent-labelled, not probes) are graded; infra failures and abandoned attempts get no grading job | They are infra events to report, not agent outcomes (CLAUDE.md, R10.2); grading them would score the platform | Queue jobs for `infra_failed` trials too in `GradingService.queueFinishedTrials` |
| A14 | Superseded on 4 Nov (framework 0.2.0): the `provenance` grader first read a guessed `checks.json` shape; it now reads `contract/v2/checks.schema.json` (`amounts`, `unsupported`, `required_tools`) and refuses anything else | The check's shape was not fixed when the grader was built; it is now | Nothing: the number stays so older references resolve |
| A15 | A grading job's lease is 120 s with no heartbeat, and a job whose lease lapses 3 times is `failed` | Grading reads local files and runs unit tests capped at 120 s each, so a live grader finishes well inside the lease; a crash loop must not repeat forever | A task with several slow unit tests can outlive the lease: a second grader claims the job and the first one's report is refused as `claim_lost` (nothing is lost, the work is done twice); raise `GRADING_LEASE_S` or add a heartbeat |
| A16 | D36 on the own loop: the re-send is made only when the cap can go higher (a cap was sent and is below 8,192) and a step is left; otherwise a cut-off reply ends as `token_limit` at once. Each cut-off model call gets its own one re-send; later calls go back to the configured cap | D36 says "re-send once with the cap doubled (up to 8,192)" and that `max_output_tokens` is the first attempt's cap. Re-sending at the same cap would be a plain retry (R10.11), and the re-send is a model call, so it counts against `max_steps` (D17) | Change `raised_cap` and the step check in `workers/ownloop/src/ownloop/adapter.py`; `tests/test_token_cap.py` pins each case |
| A17 | Number provenance (`checks.json`): `supported_by: client` means the task's client file and `user` means a task or simulated-client message; an amount matches at the precision shown when rounded half-up or cut to its digits, and trailing zeros may be rounding within 1% with two significant digits left; tool results count only from the same or an earlier agent turn | The brief named three sources (tool result, user or client message, client file) and three labels, and gave two rounding examples ("about ₹8,997" for 8997.26, "₹1.23 lakh" for 1,23,456). Cutting and trailing zeros are how the 4 Nov answers rounded ("₹1,667" for 1,667.50, "about ₹49,500" for 49,483); the 1% bound keeps round figures from matching unrelated numbers | Change the rules in `workers/adapterlib/src/evals_adapter/checks.py`; `tests/test_checks.py` pins them, and its real-run test shows how the counts move |
| A18 | A judge's rubric is read as it is now from `configs/rubrics/`, also when a trial is graded with its own old task (`grader_source: trial_task`); its bytes are hashed whole, review header included | The rubric is a config file, not part of the task, and rubric files are versioned by name like prompts | Pass no repo reader for `trial_task` in `GradingService.queueJob`, so those rubrics are `null` like old grader files; or strip the header before hashing on both sides |
| A19 | LiteLLM keeps a deleted key's spend-log rows, so `GET /spend` can still read a revoked judge approval's spend | LiteLLM's `/spend/logs?api_key=` reads its spend-log table by the key's hash, apart from the keys table; not checked against the pinned v1.99.4 | A revoked approval shows `revoked_spend_usd`, what the log held when it was revoked, which misses calls whose rows landed after that (rows are written in batches) |
| A20 | The judge's `base_url` in a grading claim is the same URL a trial spec gives workers, `LITELLM_URL` + `/v1` (`http://litellm:4000/v1` in compose) | The ask was to use the value trial claims use; the grader is on the trials network, as the harness workers are | The Python judge strips `/v1`, or `GradingService.claim` sends `LITELLM_URL` alone |
| A21 | `GET /spend`'s `total_usd` adds judge spend when it is known; `task.summary` in a grading claim is the trial's own task summary, as the labelling queue shows it | Judge calls are real spend against the same overall budget; the judge should see what the blind labeller sees | Take `judge_usd` out of `total_usd` in `SpendService.totals`; read the summary of the job's `task.sha256` instead |
| A22 | The judge's call: one request per trial for all of a grader's criteria, no temperature, `max_tokens` 8,000, a 300 s timeout, no retry beyond LiteLLM's (D16); a reply that does not parse is an `error` grade | The brief asks for a judge with a rubric and the SPEC fixes blind, pinned and a verdict with quoted evidence per criterion; nothing says how the call is made. The Claude 5.5 models reject temperature (known-limits), Sonnet 5.5 spends part of its cap thinking (the conflict check needed 6,000), and a retry inside the grader would hide a model that cannot follow the format | Change the constants in `graders/src/evals_graders/judge.py` and bump `FRAMEWORK_VERSION`; `tests/test_judge.py` pins each case |
| A23 | The guided builder's "Evaluate it" (`#/build`) puts the baseline in arm A and the new agent in arm B. A saved agent counts as the obvious baseline only when the Run screen's own rule (`axisFromDiff`) finds exactly one difference from the new one, the oldest such first; with none, the link names arm B only and the Run screen starts arm A on the newest other saved agent, the same harness first (A30) | The comparison reads B minus A, the Run screen calls the oldest config the baseline, and the Config screen's "Save and set up a run" already passes (baseline, new). The request asked for the new agent in `a` with an optional baseline in `b`, which would flip the sign of every result | Swap the two hashes in `runLink` in `apps/ui/src/views/BuildView.vue` |
| A24 | The front door (three ways in and the five-step guide) is the root route `#/`, and the experiments list moved to `#/experiments` | Rishi's direction of 4 Nov: the UI's front door offers a finished example, the guided builder, and the full platform as it is | Change the root case in `parseHash` and `href.start` in `apps/ui/src/router.ts` |
| A25 | "Example rows stay apart from the reviewer's own work" means a loaded example's trials are left out of `GET /spend`'s `trials_usd`, the estimate's history, the labelling queue and baseline reuse, besides never being claimed, re-graded, judged or run; its content-addressed rows (configs, prompts, toolsets, tasks) are shared | The brief asked for the flag on experiments so the UI can label them, and for examples never to be claimable or runnable; counting another machine's spend or another run's history as yours, or labelling its trials into `labels/`, would mix them in | Drop `NOT_EXAMPLE_TRIAL` (from `apps/api/src/examples/example-guard.ts`) from the query concerned, or mark shared rows too |
| A26 | An example's trials keep their ids and stored folders (`runs/<experiment>/<trial>/attempt-<n>/`), and its grades and stored events get new ids | Trial ids are text and unique; grade and event ids are serial numbers that would collide with this database's own | Rewrite trial ids and folders on load, and the trial ids inside specs, reports and files with them |
| A27 | With no history, a trial on a fake model (`fake/*`) takes 10 s from claim to report (`fake_wall_s_per_trial`), and one on a real model 60 s as before | Measured on the 4 Nov fresh-clone QA: 30 own-loop trials on fake/finance-emi and fake/finance-malformed took 8.0 s each, claim to report, on one worker. Other harnesses were not measured; Hermes starts more slowly | The first estimate of a fake run is off until it has history; change `ASSUMPTIONS.fake_wall_s_per_trial` in `apps/api/src/experiments/estimate.ts` |
| A28 | A run on fake models only (every arm's model, and the simulator's when a task needs one, is `fake/*`) is never refused for its budget; a budget below the estimate's high end is raised to it, and the experiment stores the raised one | The lead's direction of 4 Nov: fake prices are made up for testing, so a spending limit protects nothing; raising it rather than keeping the lower figure means LiteLLM's cap and the spend guard cannot stop a free run part-way | A fake run keeps the budget given and can be stopped by LiteLLM's cap; drop the raise in `ExperimentsService.create` |
| A29 | D32's futility check counts an arm's first `after` graded trials, in the order their grades arrive, and skips trials whose grading is incomplete or not finished; it runs on every trial report and every grades report while the run is running | D32 counted `agent` plus `answered` as a pass until graders existed; the lead's direction of 4 Nov is to use the grading outcome now. Grades arrive after the trial and not always in claim order, but the claim order is already a random sample (D32) | If "first" must mean the first claimed, select the arm's first `after` trials by `order_index` among the graded ones in `applyFutility` (`apps/api/src/experiments/rules.ts`) |
| A30 | The Run screen's arm defaults (`defaultArms` in `apps/ui/src/lib/runSetup.ts`): with one arm in the address, the other is the newest other config, the same harness first, never the given one; with neither, the oldest config and the next, as before; with one config, a one-arm pilot with a note that a second agent is needed (link to `#/build`); the same config on both arms is refused in words, so no A/A run is offered | The lead's direction of 4 Nov (QA blocker 3) covers the one-arm-given case; whether an A/A calibration run should exist is Rishi's separate question; the no-arm case was not part of it, so it keeps its old behaviour | Change `defaultArms`; `runSetup.spec.ts` pins each case |
